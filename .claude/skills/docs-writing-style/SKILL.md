# 文档写作规范（clouisle-docs）

本 skill 是 clouisle-docs 的通用写作规范，参照头部产品文档站的做法提炼而成。核心原则：**页面一题一义、概念先行图片跟随、界面路径加粗、变量反引号、参考表用表格、教程分步带验证点**。

## 一、菜单分栏模式

### 顶层按读者目标分栏

按读者目标分栏，而非按产品模块：

| 顶层栏 | 内容 | 排序逻辑 |
| --- | --- | --- |
| 快速开始 | 入门教程 | 用户第一站 |
| 学习/概念 | 核心概念 + 系列教程 + 案例教程 | 概念 → 由浅入深 |
| 使用/指南 | 产品功能全生命周期 | 按使用阶段 |
| API/参考 | 端点/选项参考 | 按资源分组 |
| 开发者专题 | CLI、插件、部署 | 按受众 |

「使用/指南」栏内部按**使用阶段**分（而非按 UI 菜单）：

```
入门 → 概念/编排 → 参考 → 调试 → 发布 → 监控
         └─ 资源栏：知识库、工作空间（集成/账号/设置）
```

关键规则：

1. **参考型内容单独成栏**：节点/参数/端点数量多时，全部扁平列出一页一个条目，不塞进「概念」页。
2. **概念与参考分离**：概念页讲「X 是什么、怎么搭」；参考页讲「每个字段怎么配」。概念页不堆配置细节。
3. **每栏有索引页**（`introduction`/`readme`/`overview`），用 Card 网格导航到子页，配一句副标题。
4. **教程独立于功能文档**，系列按数字编号（`lesson-01`…`lesson-10`），单篇教程自包含可跟做。
5. **FAQ 独立成页**，按主题分 `##`，问题即标题（`###` 用疑问句式），每个问题一答即止。

### 落到本项目

- `content/docs/` 下按此结构组织目录：`get-started/`（教程+概念）、`guide/`（功能，按阶段分文件夹）、`reference/`（参数/选项参考，扁平）、`faq.mdx`。
- 目录顺序用 `meta.json` 的 `pages` 控制，分组用 `---Label---` 分隔符。
- 文件夹索引页 `index.mdx` 用 `<Cards>` 网格列出子页面，每卡一句描述（见 §四）。
- 单页内容超过约 500 行或出现多个无关主题 → 拆页。页面标题即功能名（如「模型参数」），不写「模型参数详解」这类冗余后缀。

## 二、页面类型与骨架

### 1. 索引页（栏目首页）

```
frontmatter title（栏目名）
> 一句话副标题：这个栏目解决什么问题
开头段：栏目定位 + 读者能得到什么
<Cards> 网格：每个子页面一张卡，title + 一句描述（复用页面 description）
```

副标题示例：「在工作空间中构建、发布并监控 AI 应用」。卡片：编排/知识库/发布/监控/集成/获取帮助。

### 2. 概念页

```
frontmatter title
> 一句话副标题
### 概念一（三级标题）
  定位段：这是什么（1-2 句）
  关键事实 + 关联链接（[相关页](/docs/xxx) 内链交叉引用）
  <Callout type="info">补充背景</Callout>
  截图（可选，展示长什么样）
### 概念二
  ...
```

- 概念用 `###` 而非 `##` 细分，一个概念一个标题。
- 每个概念先定位（「变量是存储信息的标记容器」），再展开行为与约束，最后给图或链接。
- 概念间的差异（如 Workflow vs Chatflow）用表格或 Tabs 对比，不写两段长文。

### 3. 功能参考页

```
frontmatter title（功能名）
> 一句话副标题：这个功能做什么（如「调用语言模型进行文本生成和分析」）
开头段：是什么 + 核心能力概述（2-3 句，不展开）
前置条件 <Callout type="info">（「使用前先配置 X」）
## 功能维度一（按能力分节，不是按 UI 菜单分节）
  解释段 → 截图（见 §五）→ 参数说明 → 代码示例
## 功能维度二
  ...
## 错误处理 / 边界情况（若有）
```

- 分节按**读者要完成的事**组织（模型选择/提示词配置/上下文变量/结构化输出/记忆），不是照抄界面标签。
- 每个可配置项：名称（加粗或代码）+ 取值范围/选项 + 默认值 + 影响；多个参数用表格。
- 多实现方案用 Tabs（如「可视化编辑器 / JSON Schema / AI 生成」三 tab）。
- 兼容性/反例 → `Callout type="warn"`；破坏性/危险 → `error`。
- 文末给「错误处理/重试/边界」小节，参考页必须有失败路径。

### 4. 教程页

```
frontmatter title（含时长：如「30 分钟快速入门」）
> 一句话副标题：读者将做出什么
<Callout type="info">前置说明：环境、账号、版本</Callout>
开头段：结果导向（学完拥有什么），先放最终成品全景截图
## 开始之前
<Steps>
  <Step>### 准备一（注册账号/安装/配置）</Step>
  ...
</Steps>
## 步骤 1：创建 X
### 1. 小节名：操作/对象名
  <Callout type="info">为什么需要这一步（动机先行）</Callout>
  编号操作列表（1. 2. 3.，每步一个动作，含界面路径与字段值）
  配置项用 <Accordion> 折叠细节（字段类型/变量名/选项）
  该步完成后的截图
## 步骤 2：…
```

- **每步先说「为什么」**：一个 Info 块解释这一步解决的问题，再给操作。
- 操作列表编号连续，字段名用反引号（`gpt-5.2`）、界面路径用加粗（**集成** > **模型供应商**）。
- 步骤间截图不断档：每完成一步给一张结果截图。
- 明确「保持未提及的设置为默认值」（`<Callout type="note">` 或 Tip）。
- 结尾给出成品验收标准或下一步链接。

### 5. FAQ 页

```
frontmatter title
> 一句话副标题
## 主题分组一
### 为什么 …？ / 怎么 …？
  直接回答（结论第一），必要时给代码/链接
```

- 问题即标题，疑问句式，直接回答不铺垫。
- 每个问题 1-5 行，多步骤答案用编号列表或代码块。

## 三、写作语言规范

1. **副标题必写**：frontmatter `description` = 一句话做什么，同时渲染在标题下方；索引页、TOC、搜索、OG 均复用。写法：「调用语言模型进行文本生成和分析」——动词开头，不含「本文介绍…」。
2. **开头定位段**：第 1 段回答「这是什么 + 能做什么」，2-3 句，术语先行、不铺垫历史。
3. **界面路径**：加粗 + `>` 连接（`**集成** > **模型供应商**`），节点/按钮名加粗（`**启用推理标签分离**`）。
4. **变量/字段/文件名**：反引号（`` `{{user_input}}` ``、`` `gpt-5.2` ``、`manifest.yaml`）。
5. **数字与单位**：写具体值（默认 `50MB`、`0-1`），不写「较大」「较小」。
6. **句子**：短句、陈述句、结论在前。每段一个要点。避免「请注意」「值得一提的是」等填充语。
7. **语气**：直接命令（「前往…」「将…设为…」），不客套。
8. **内链交叉引用**：相关概念/节点用相对链接互相引用（`[开始节点](/docs/…/start)`），但一页内不重复解释已链接内容。
9. **中文正文**：界面文本/代码/专名保留英文原样；翻译保持术语统一（一页内同一概念不换译名）。

## 四、表现组件

本项目（Fumadocs）可用组件与用途：

| 组件 | 用途 | 可用性 |
| --- | --- | --- |
| `<Callout type="info">` | 前置条件、背景、技巧 | 默认 |
| `<Callout type="warn">` | 兼容性、反例 | 默认 |
| `<Callout type="error">` | 破坏性变更、常见错误 | 默认 |
| `<Callout type="success">` / `idea` | 教程验证点、最佳实践 | 默认 |
| `<Cards><Card>` | 索引页导航 | 默认 |
| 代码块（```ts、```json 等） | 代码示例，语言标识即高亮 | 默认 |
| `<Steps><Step>` | 开始之前、分步教程 | import `fumadocs-ui/components/steps` |
| `<Accordions><Accordion>` | 教程配置细节折叠、FAQ | import `fumadocs-ui/components/accordion` |
| `<Tabs><Tab>` | 多方案对比、多场景表格 | import `fumadocs-ui/components/tabs` |
| `<TypeTable>` | 参数/选项参考表 | import `fumadocs-ui/components/type-table` |
| `<Figure>`（自定义） | 带 caption 的图片 | 需注册，见 §五 |

组件 import 路径按已装包 exports 核实（详见 config-docs 组件速查）。

## 五、图片规范（重点）

图片是表现形式的核心，规则如下：

### 放置规则

1. **图随文走**：截图紧跟所描述的文字段落之后，绝不集中堆在页面末尾。段落提到「界面」或「配置面板」时，该处就应有图。
2. **先概念后图**：先一句话解释「这是什么/这一步做什么」，再放图展示长什么样；不要先图后文。
3. **一图一事**：每张截图只说明一个要点。截图裁剪到关键区域（配置面板、画布局部），不整屏截图；重点处用标注（框线/箭头）指向，图内文字保证可读。
4. **数量节奏**：概念页每个概念至多 1-2 图；功能参考页每个功能维度 1 图；教程每完成一步 1 图（结果截图），教程开头放 1 张最终成品全景图让读者知道目标。
5. **教程步骤图**：展示「做完这一步的界面状态」，与操作步骤严格对应，让读者能对照检查。

### 每张图的组成

```
<figure>
  <img src="/images/xxx.png" alt="模型选择和参数配置" />
  <figcaption>模型选择和参数配置</figcaption>
</figure>
```

1. **caption 必写**：一句话说明「这张图展示什么」。没有 caption 的图 = 缺说明。
2. **alt = caption 内容**：`alt` 与 `figcaption` 一致（无障碍 + LLM 消费 `/llms.txt` 时保留语义）。
3. **命名**：图片放 `public/images/`，文件名 kebab-case 描述内容（`model-selection-parameters.png`），不用无意义名（`img1.png`）。
4. **尺寸**：截图宽度对齐正文（约 800px 内），长截图可整宽；`<img>` 不写死宽高由 CSS 约束，避免拉伸。

### 当前项目实现方式

base-ui 16.14.3 无 Frame/Figure 组件，二选一：

- **A（推荐，一劳永逸）**：在 `components/mdx.tsx` 注册自定义 `Figure` 组件（`<figure>` + `<img>` + `<figcaption>`，caption 可选），之后 MDX 里用 `<Figure src="/images/x.png" alt="…" caption="…">`。注意 `defaultMdxComponents` 已把 `img → Image`，自定义组件里直接用 `Image` 或原样 `<img>` 均可。
- **B（零改动）**：原生 HTML `<figure>/<figcaption>`，MDX 中可用。

> 注意：`includeProcessedMarkdown: true` 会把页面 stringify 供 LLM 读取——图片只体现为 alt 文本，所以**图片说明必须写进 caption/alt 或正文**，不能只靠视觉传达（如「看图中红色按钮」这类依赖像素的表述要配文字说明位置）。

## 六、表格使用

- **参数/变量参考表**：列 = 名称 | 类型 | 默认值 | 说明 |（可选备注）。
- **对比表**：两列（维度 | 差异），用于概念对比。
- **多版本差异**（同一内容不同场景）：用 `<Tabs>` 包表格，每 tab 一个场景。
- 表格适合：结构化参考（字段、枚举、映射、限制）。不适合：叙述性内容——写段落。
- 行数 > 15 的参考表拆成多个小表按 `###` 分组，或改 `<TypeTable>`（配置类见 config-docs）。

## 七、写作流程

1. 先定**页面类型**（索引/概念/参考/教程/FAQ），套对应骨架。
2. 规划**分节**：按读者要完成的事，每节一个 `##`。
3. 写每节：定位句 → 细节 → 图（caption+alt）→ 表格/代码示例。
4. 检查点：每张图都有 caption 且紧邻对应文字？每个参数有默认值？教程每步有「为什么」+ 结果图？参考页有错误处理？交叉链接到位？
5. 关键信息（默认值、限制、必填）写进正文，不只放在组件 props/折叠里（LLM 消费）。

## 八、验证

- `npm run dev` 后逐页检查：标题+副标题渲染、TOC 层级、侧边栏顺序与分组（meta.json）、卡片网格、表格可滚动、Tabs/Accordion/Steps 交互、图片加载与 caption 显示。
- 教程页按步骤实际跟做一遍，确认每步结果与截图一致、无缺步骤。
- 检查 `/llms.txt` 或 `/docs/<路径>.md`：副标题、关键值、图片 alt、折叠内容是否完整可读。
- 涉及组件 import / mdx.tsx 改动时跑 `npm run types:check`。
