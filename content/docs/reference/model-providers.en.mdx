## Model Type Classification (`ModelType`)

`model_type` describes a model's capability class and is independent of the provider; a given provider typically supports only some of these types.

| Model Type (`model_type`) | Description |
| --- | --- |
| `chat` | Chat and text completion LLMs (streaming and function calling supported) |
| `embedding` | Text embedding models (used for knowledge base RAG and memory retrieval) |
| `rerank` | Rerank models that rescore initially retrieved text chunks |
| `tts` | Text-to-Speech |
| `stt` | Speech-to-Text |
| `audio_generation` | Prompt-to-audio generation |
| `text_to_image` | Text-to-image generation |
| `text_to_video` | Text-to-video generation |

## Embedding Provider Support

`model_type: embedding` is not valid for every provider identifier. The backend embedding adapter dispatches providers across three paths:

| Adapter Path | Covered Providers | Behavior |
| --- | --- | --- |
| `OpenAICompatibleEmbeddingAdapter` | `openai`, `openai_responses`, `deepseek`, `moonshot`, `zhipu`, `qwen`, `baichuan`, `minimax`, `volcengine`, `siliconflow`, `xai`, `ollama`, `custom` | Calls the OpenAI-compatible `/embeddings` endpoint directly and captures upstream `usage` |
| `FallbackEmbeddingAdapter` | `google`, `azure_openai`, and other providers not listed above | Generates vectors via LangChain Embeddings; `usage` is empty |
| Unsupported | `anthropic` | No embedding adapter exists; creating a `model_type: embedding` model with `provider: anthropic` raises `Unsupported provider for embedding` at runtime |

For the detailed embedding mechanics (fallback strategy, token metering, dynamic dimensions, and Qdrant collection partitioning), see [Embedding Adapters & Vector Dimensions](/reference/embedding-adapters).

## Model Definition Fields

| Field | Type | Required | Default | Description & Validation |
| --- | --- | --- | --- | --- |
| `name` | string | Yes | None | Display name, `1-100` characters |
| `provider` | enum | Yes | None | Provider identifier (the 22 enum values above) |
| `model_id` | string | Yes | None | Upstream model ID, `1-100` characters |
| `model_type` | enum | Yes | None | Model type (the 8 types above) |
| `provider_display_name` | string/null | No | `null` | Provider name shown to end users |
| `base_url` | string/null | No | `null` | Custom API URL (at most 512 characters), constrained by the endpoint allowlist policy |
| `api_key` | string/null | No | `null` | Access key (may be empty for local providers such as Ollama); encrypted server-side |
| `context_length` | integer/null | No | `null` | Maximum context length (must be `>= 1`) |
| `max_output_tokens` | integer/null | No | `null` | Maximum output tokens (must be `>= 1`) |
| `input_price` | decimal/null | No | `null` | Price per million input tokens (non-negative, up to 6 decimals) |
| `output_price` | decimal/null | No | `null` | Price per million output tokens (non-negative, up to 6 decimals) |
| `default_params` | object/null | No | `null` | Default inference parameters (such as `temperature`, `top_p`) |
| `capabilities` | object/null | No | `null` | Capability flags: `vision`, `function_calling`, `streaming`, etc. |
| `is_enabled` | boolean | No | `true` | Whether the model is globally enabled |
| `is_default` | boolean | No | `false` | Whether it is the default model of its type |
| `sort_order` | integer | No | `0` | Sort weight, ascending |

## Model Endpoint Security & Connectivity Testing

### Endpoint Allowlist Policy (`model_endpoint_allowlist`)

All outbound requests to model providers are strictly validated against the system endpoint allowlist:
- The system ships with 19 pre-configured official provider Origins (such as `https://api.openai.com`, `https://api.deepseek.com`).
- If an administrator configures a custom private Base URL (for example self-hosted vLLM or a private Ollama node), its full Origin (`scheme + host + port`) must be explicitly registered under **Site Settings > Model Endpoint Allowlist**.
- Validation ignores request paths, query parameters, and credentials, but non-standard ports (such as `:11434`) are matched strictly.

### Connectivity Test Endpoint

When adding or saving a model in the admin console, a test endpoint verifies connectivity:
- The test performs a lightweight upstream call using the credentials the administrator submits at that moment; credentials are not saved automatically during the test.
- The response contains:
  - `success` (bool): whether connectivity succeeded
  - `message` (string): success information or upstream error detail
  - `latency_ms` (float/null): network and response round-trip time in milliseconds
