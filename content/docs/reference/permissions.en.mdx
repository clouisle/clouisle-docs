Permissions are checked uniformly by the backend. Hidden frontend menus are a UX layer only; the API still returns permission errors.

## Permission Catalog

### Special Permissions

| Permission | Description |
| --- | --- |
| `*` | Wildcard permission code; the runtime bypass is actually `is_superuser` |
| `admin:dashboard:access` | Dashboard access; the key permission distinguishing "admin" from "regular user" |

## Built-in Role Matrix

The backend initializes 4 global built-in roles at startup with the following default permissions:

| Role Name | Role Type | Core Permission Characteristics | Typical Persona |
| --- | --- | --- | --- |
| **Super Admin** | Global built-in | Holds wildcard permission code `*`; completely bypasses permission checks and can perform system configuration, role management, and audit exports | Operations lead, system owner |
| **Admin** | Global built-in | Includes `admin:dashboard:access` and all administrative and operational permissions for resources, but excludes create/update/delete of system roles/permissions themselves and modification of global site settings | Workspace administrator, team technical lead |
| **Member** | Global built-in | No `admin:dashboard:access`; has full collaborative create/edit/run permissions for Agents, workflows, knowledge bases, tools, and Skills within the team | Developer, workflow builder |
| **Viewer** | Global built-in | Read-only role; can view and chat/run published Agents and workflows within the team, and read/execute tools and Skills | Business auditor, observer |

### Team Membership Role Mapping

Team member roles (`owner`, `admin`, `member`, `viewer`) use a scope-mapping mechanism:
- `owner` and `admin` map to the `Admin` role at team scope
- `member` maps to the `Member` role at team scope
- `viewer` maps to the `Viewer` role at team scope
- Team-level roles do not implicitly grant global dashboard access (`admin:dashboard:access`)

## Check Order

Super administrators pass directly. Administration permissions use global roles; regular resource permissions additionally check the team/resource scope role. Requests fail when the resource does not belong to the current team, the user is not a member, the user status is invalid, or the API Key does not list the target resource.

## Role Limits

System roles and system permissions cannot be deleted; the default team, owners, and super administrators have additional protection. Operations such as transferring ownership, removing an owner, or modifying system permissions are explicitly rejected.
