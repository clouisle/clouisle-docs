Tools let Agents and workflows perform external actions; Skills package reusable instructions and resources into installable capabilities. Tools come in three forms, and custom tools have three execution methods.

### The three tool forms

| Form | Source | Ownership and permissions |
| --- | --- | --- |
| **Built-in tools** | Provided by the platform, updated with each release | Nothing to create; cannot be deleted or shared; some need a site switch or credentials |
| **Custom tools** | Created by a team, as HTTP, code, or database | Owned by the team; visibility, testing, and sharing supported |
| **MCP servers** | Connect to an external MCP server | Owned by the team; connection details depend on the transport |

### Built-in tools

Built-in capabilities include current time and date formatting, calculation and unit conversion, web search, web page fetching, document conversion, feed reading, and, in the sandbox, artifact viewing, command execution, and file read/write.

- Web search engines and credentials are configured once by administrators on the site capabilities page; teams and Agents no longer store search keys. Only engines enabled at the site level are available, and a failing engine does not fail over to another provider automatically.
- Image generation, video generation, and asking the user are implemented by the platform but **do not appear in the tool picker**: they are injected by workflow media nodes and the Agent's question switch respectively.
- The built-in document converter appears together with uploaded file parsers in the file parser selector.

### Custom tools

- **HTTP request**: configure method, URL, headers, query parameters, body template, timeout (`30` seconds by default, `1-300`), and response value path. The URL must be static and cannot contain variables; variables belong in query parameters, headers, or the body, and a URL with variables is rejected on save or execution.
- **Code**: run Python or JavaScript in a restricted sandbox, install **exact pinned** dependency versions (such as `requests==2.32.3`), and declare artifacts under `/workspace`.
- **Database**: connect to PostgreSQL, MySQL, Redis, or MongoDB and save connection details and queries. Query timeout defaults to `15` seconds (`1-120`), and at most `100` records are returned (`1-1000`). Before saving, click **Test connection** to confirm the network and credentials work.

Before saving a custom tool, run it with the test feature: pass parameters as JSON and get back the result, logs, artifacts, and duration. If execution fails, read the error in the test result first, then check whether the target is in the outbound network allowlist.

### MCP

MCP servers support three transports: `stdio` (local command), `sse`, and `http` (remote address). Before saving, fetch the server's tool list to confirm it is reachable and inspect tool names, descriptions, and parameter shapes. `stdio` takes a command, arguments, and runtime environment settings; `sse` and `http` take a URL and optional headers.

### Visibility and permissions

- **Private**: only the creator can see and use it; other team members cannot.
- **Team**: team members can view and use it; editing requires the creator or a team administrator, and regular members have read-only access.
- **Deletion**: only team administrators or owners can delete a tool. Built-in tools are platform resources and cannot be deleted.

### Sandbox boundaries

Code tools time out after `30` seconds by default, with `1-600` seconds allowed in saved configuration and `1-60` seconds for direct execution. The default disk is `1024MB`, and standard output and error are `256KB` each. Artifacts must be written under `/workspace`; writes elsewhere are rejected. See [Code Sandbox](./sandbox.mdx) for isolation details and the full limits.

### Sharing

Custom tools can be shared with other teams, subject to hard constraints:

1. Only **administrators of the owning team** can start a share.
2. A private tool cannot be shared, and a tool cannot be shared with its own team; a duplicate share is rejected.
3. There are two permission levels: **read-only** (view and use the tool) and **read-only with execution results** (additionally view execution results).
4. The receiving team sees these tools in its "shared with me" list, along with the source team and permission. Sharing is one-way and is created and revoked by the owning team.

Built-in tools cannot be shared.

### Outbound security

Custom HTTP tools, workflow HTTP request nodes, Knowledge Base URL imports, and database connection tests all pass through a unified outbound check: targets that are internal, loopback, link-local, or cloud metadata addresses are refused, and are allowed only after an administrator adds them to **Settings** > **Security** > **Outbound network allowlist**. Cloud metadata addresses are permanently blocked and cannot be allowlisted.

<Callout type="warn">
  Before exposing an internal service to tool calls, confirm the target is registered in the outbound network allowlist. Otherwise it shows up as a tool execution failure rather than a configuration error on save, which is easily mistaken for "the code is wrong".
</Callout>
