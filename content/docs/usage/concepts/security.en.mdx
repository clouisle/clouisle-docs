Clouisle isolates Agents, workflows, Knowledge Bases, model authorization, tools, and Skills by team. The current team determines the boundary for querying and creating resources in the platform workspace.

### Team isolation

A team is the boundary for resources and data: team resources are visible to team members by default, and cross-team access is rejected rather than returning empty data. Private resources are narrower still — private Agents, workflows, and tools are usable only by their creator; legacy private resources whose creator no longer exists are handled by team administrators.

Cross-team sharing covers tools and Knowledge Bases: a custom tool can be shared read-only or with execution results, and a Knowledge Base is shared read-only. Sharing is one-way, initiated and revoked by the owning team. Agents and workflows have no per-team authorization layer.

### Roles and permissions

Authorization combines two layers:

- **Global roles** decide *what* someone can do — enter the admin console, create Agents, change site settings.
- **Team roles** (owner, administrator, member, viewer) decide *where and at what level*. Team roles carry no permissions by themselves; team-management and deletion actions additionally require owner or administrator in that team.

Super administrators bypass every check. Five built-in roles exist (Super Admin, Admin, Team Admin, Member, Viewer), and custom roles can combine permissions. Authorization is enforced server-side; hiding menus and buttons in the frontend is only convenience: calling the service directly is rejected all the same, and a visible button does not guarantee success.

See [Roles and permissions](../guides/administration/roles-permissions.mdx) for who can do what, and the [permissions reference](../../reference/permissions.mdx) for the permission catalog and role matrix.

### Session and data isolation

Regular users see only their own conversations and data. Administrators with admin console access can view all team conversations, and team-scoped queries additionally require the team owner or administrator role. API keys belong to users: users can view and manage only their own keys, and only super administrators can view all keys across teams.

### Authentication and account security

A site can combine password sign-in, email verification, administrator approval, click-based human verification, password policy, password expiration, single session, TOTP, and SSO. SSO supports multiple connections, and administrators can disable password sign-in. Active sessions last `30` days by default.

Human verification is a **one-time click challenge**, not an image-text CAPTCHA: users complete a click before submitting the sign-in form, and a missing or expired challenge rejects the sign-in. The Security page has exactly this one switch — no failure threshold, validity window, or difficulty setting. It is a supplementary anti-automation measure, not a substitute for lockout and TOTP.

What actually stops brute force is the lockout logic:

- After the configured number of consecutive failures, an account is locked for a period; while locked, even a correct password is refused and the remaining time is shown.
- A successful sign-in resets the failure counter.
- Consecutive TOTP verification failures also trigger a short lockout, counted per user; a successful verification resets the counter.

All thresholds live under **Settings** > **Security**; see [Site settings](../guides/administration/site-settings.mdx).

### Outbound network protection

Three independent protections govern outbound access. All can be switched under **Settings** > **Security** and are on by default. Turning one off never clears its saved list, and enforcement resumes as soon as it is turned back on.

- **External fetching protection**: custom HTTP tools, HTTP request nodes, Knowledge Base URL imports, and database connections cannot reach internal, loopback, or cloud metadata addresses by default. To call internal services, an administrator adds the target to the outbound network allowlist, which accepts single addresses, ranges, exact hostnames, and wildcard domains, up to `200` entries. Cloud metadata addresses and global wildcards can never be added. With the switch off, targets are unrestricted, though URL and port format checks still run — format checks are not a security boundary.
- **Model egress**: the request address entered when registering a model provider must match the model endpoint allowlist (scheme, hostname, and port exactly). The list is preloaded with common providers and local model addresses, up to `200` entries. Model traffic goes only through this list and is not subject to the blocked ranges of external fetching protection — so running a local model service only needs a model endpoint entry, not open internal access.
- **Sandbox egress**: applies only to the code sandbox, accepts exact hostnames only, defaults to the official Python and npm package hosts, and an empty list blocks all outbound traffic. It never shares entries with the outbound network allowlist: allowlisting an internal host for tools does not open it to the sandbox, and vice versa. Turning the switch off affects new jobs only; filesystem isolation and resource limits remain.

Each protection judges differently: external fetching resolves the hostname before evaluating addresses, so aliases or DNS tricks cannot slip past; model egress compares the full address; sandbox egress permits only HTTPS to allowlisted hosts. If any switch cannot be read, it is treated as on, so blocking continues.

For exact fields, defaults, and matching rules, see the [site settings reference](../../reference/site-settings.mdx).

### API keys

API keys start with `clou_` and are sent as the access credential. A key can be bound to specific Agents and workflows (both lists empty means access to everything), and can carry an expiration time and an enabled state. Binding is enforced server-side, so a key reaching an unauthorized Agent or workflow is rejected.

The interface lets you enter a per-minute request limit and scopes, but the current version neither throttles nor narrows permissions accordingly — do not treat them as effective security controls. Keys belong to users: users can view and manage only their own keys, and only super administrators can view all keys across teams.

### Audit and notifications

The admin console records resource operations, actors, and change snapshots, with filtering by event, user, team, and time. Sensitive fields are masked when recorded and displayed, so raw secrets never appear in logs.

Notifications can stay in-app or be sent via email, Webhook, or Feishu; DingTalk, WeCom, and Slack channels were removed.
