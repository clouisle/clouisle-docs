A Workflow pins a multi-step task onto a directed node graph: the start node defines inputs, intermediate nodes transform data or call capabilities, and the output node decides the final result. Unlike an Agent, which figures things out as it goes, a workflow has its order, branches, and parallelism pre-arranged, so the same input follows the same path — which is what makes it suitable when results must be repeatable and auditable.

### Drafts and publishing

- The workflow you are editing is a **draft**. Save it and debug-run it whenever you like; a debug run executes the current draft and does not affect what is live.
- Only a **published** version can run for real: run forms, triggers, and external calls all target the published version.
- Every publish creates a version snapshot and marks it published; previously published versions move into history and can be reviewed or restored.
- Restoring an old version does not erase history: the current version is archived as a backup and the target version is copied into a **new** published version, so old records remain.
- The publish page offers two presentation modes: **Form & Result** shows only inputs, status, and the final result, suitable for exposing as an app; **Result & Details** shows the result first and lets viewers expand node-level traces, suitable for debugging and internal review.

### What run statuses mean for you

| Status you see | Meaning | What to do |
| --- | --- | --- |
| Queued | Submitted, not yet picked up | Wait; if nothing moves for a long time, capacity is short or the execution service is unavailable — contact operations instead of resubmitting |
| Running | Nodes are executing in order | Wait for the result; cancel the run if you need to stop it |
| Waiting for approval | Paused at an approval node, awaiting an approver | Open the run details and submit feedback; it will not continue otherwise |
| Completed | Final output and each node's trace are available | Review or download the result |
| Failed | Stopped at a node; its details show the error for that node | Fix the configuration and run again |
| Cancelled / timed out | Cancelled on purpose, or exceeded the run time limit | Run again if you need the result |

Nodes have their own statuses too: waiting, running, completed, failed, and **skipped** (a branch whose condition did not match). Run status and node status mean different things — check the right level when troubleshooting instead of mixing them.

### Waiting for approval

- When a run reaches an approval node the whole run pauses at "waiting for approval" and downstream nodes do not execute.
- After an approver submits feedback, the run continues from the pause point; **completed nodes are not re-run**, and earlier model calls and tool results are reused.
- You can require every approver to agree before continuing, or let any single approval pass it; any rejection ends the run.
- The approval prompt and the fields to fill in are set when the workflow is orchestrated, so approvers see exactly what the author asked for.
- It is safe to close the page while waiting — the state and the pending task stay in the run record.

### Node traces

Run details show the whole run's inputs and final output, plus each node's inputs and outputs, status, duration, tokens, errors, and the branch taken. Parallel branches appear in the trace at the same time, so you can tell whether a run was slow at a node, failed at a node, or took a different branch at a condition.

- **Comment nodes** are canvas documentation only; they do not execute and do not appear in traces.
- **Iteration** and **Loop** are container nodes whose inner subgraphs have their own start and exit: iteration runs once per array item, and a loop repeats until its condition is met. Loop counts are capped and force-terminated beyond the cap.
- Full node and field descriptions are in the [Workflow node reference](/reference/workflow-nodes).

### Two ways to start

- **User input**: generates an interactive run form, suitable for manual initiation.
- **Trigger**: started by an external call, a schedule, or a webhook, suitable for integrations and automation.

Each workflow has exactly one start node, and it cannot be deleted (the canvas rejects the delete and shows a toast).

### Note on legacy workflows

<Callout type="warn">
Early workflows passed textual data between nodes, which is incompatible with how data flows today. When you open a legacy workflow, **save it once manually before running**; otherwise you may get results that differ from what you expect. The pre-publish checklist flags references to nonexistent variables, missing required inputs, and type mismatches — resolve those before running.
</Callout>
