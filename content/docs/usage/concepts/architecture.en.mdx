This page answers three questions: what the platform is made of, what stages a chat or workflow run goes through in your UI, and what multi-user use and scaling feel like. The service list, deployment topology, and internal addresses belong to operations — see [Deployment Architecture](../../self-host/architecture.mdx). Here we only cover behavior you can observe.

### Three parts, three jobs

| Part | What it does | What you notice |
| --- | --- | --- |
| Interface | Pages, forms, streaming output, previews, and downloads | Works right away; content survives a refresh or a device change |
| Application layer | Actually runs Agents, workflows, and knowledge retrieval, and decides permissions and team scope | Determines who can see and change what; stop, approval, and re-run all act here |
| Data layer | Stores conversations and run records, approvals and settings, knowledge chunk indexes, uploaded attachments, and generated artifacts | Runs continue after you leave the page; artifacts can still be opened and downloaded later |

The data layer is split across several kinds of storage: business records, retrieval indexes, and file assets each live where they fit best. Which components are used and how they are backed up is covered in [Deployment Architecture](../../self-host/architecture.mdx) and [Storage](../../self-host/operations/storage.mdx).

Separating the interface from execution makes the page a viewing window: closing it does not affect a task, and results never live only in one browser or one machine.

### Stages of a chat

```text
Send message → queue → execute (thinking / retrieval / tools / generation) → stream back → done
```

1. **Send**: the message appears in the conversation immediately and the run starts on the platform side; your page does not need to stay open.
2. **Queue**: when many runs happen at once, the UI shows "queued" first. Normally it starts quickly; if nothing moves for a long time, execution capacity is likely insufficient or the execution service is unavailable — contact operations instead of pressing send repeatedly.
3. **Execute**: the model reasons turn by turn, retrieving knowledge, calling tools, and generating images or video as needed. Thinking steps, tool cards, and citations appear in the conversation as they happen.
4. **Stream back**: the reply appears while it is being generated. Closing the page, refreshing, or switching conversations does not interrupt the run; when you return, the remaining output continues and what you already saw is not rendered twice.
5. **Needs your answer**: when the model asks you a question, the run pauses at "waiting for answer" instead of guessing. Submit the form and the same turn continues from where it paused rather than starting over.
6. **Done**: only **Stop** truly ends the turn. Runs you stop manually, runs that fail, and runs that were interrupted are not retried automatically — a retry would repeat tool calls with side effects — so send again yourself.

<Callout type="info">
"Queued" and "disconnected" are different things: queued means the task has not been picked up yet, while disconnected only means your page temporarily lost sight of progress. After a reconnect the run is usually still going.
</Callout>

### Stages of a workflow run

1. **Submit**: through a run form, or triggered by an external call, a schedule, or a webhook. Only a published workflow can run for real; a draft can only be debugged.
2. **Queue**: like chat, it waits for execution capacity; insufficient capacity shows up as longer queues.
3. **Execute along the graph**: independent branches run at the same time; nodes whose dependencies are unmet wait for upstream. Each node records its inputs, outputs, status, and duration.
4. **Wait for people**: at an approval node the whole run pauses at "waiting for approval" and continues from that point once feedback is submitted; completed nodes are not re-run.
5. **Done**: the final output, each node's trace, durations, tokens, and errors can all be reviewed in the run details.

### What replicas and scaling mean for you

- **State is not in the page**: the platform can run several identical copies of the same services on different machines. Whichever copy handles your request, conversations and run records come from the same data, so a refresh, a device change, or being picked up by another copy after queueing shows exactly the same content.
- **Scaling buys concurrency, not single-run speed**: more capacity means more people can run tasks at once; one run is still limited by the model and tools themselves. When capacity is short, the first symptom is longer queues.
- **Different work queues separately**: chat runs, document processing, and workflow runs each have their own execution lane, and a deployment can scale one of them independently. Whether one backlog affects another depends on whether capacity is allocated in line with real usage.
- **Results are reproducible**: a workflow's path is defined by its orchestration, so the same inputs and the same published version produce the same order and output regardless of which machine executes it.

Capacity planning, replica counts, and high availability are covered in [High Availability and Scaling](../../self-host/operations/high-availability.mdx).

### Permissions and data boundaries

- Resources belong to teams: team members access them by role, and access outside the team is invisible by default.
- Private resources are visible only to their creator; cross-team sharing is read-only by default (knowledge bases, for example).
- Super admins can cross team boundaries but still leave an operation record.
- Deleting, publishing, restoring versions, and approving are written to the audit log with the actor and the before/after content.

See [Teams and Security](./security.mdx) and the [Permissions reference](/reference/permissions).
