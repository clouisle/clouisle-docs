Clouisle models use a **two-level structure**: a platform administrator first registers global models in the **admin panel** > **Models** (provider, model ID, credentials, capabilities, pricing), then authorizes them to teams with quotas. The **Models** page a team sees, along with the model selectors in Agents and workflows, only lists models authorized to that team.

<Callout type="info">
Custom API endpoints (self-hosted gateways, internal Ollama nodes) must be added to **Site Settings** > **Security** > **Model Endpoint Allowlist** first. Otherwise saving, testing, and runtime requests are rejected. See [Endpoint Allowlist](./providers.mdx#endpoint-allowlist).
</Callout>

## Registering a global model

Go to **admin panel** > **Models** and select **Add Model**. The form has three parts: **Basic Info**, **Parameters**, and **Advanced**. Fill it in, select **Test Connection**, then save. A saved model appears in the list, enabled by default.

### Basic info

| Field | Required | Values and defaults | Notes |
| --- | --- | --- | --- |
| **Model Name** | Yes | 1–100 characters | Shown in the model list, selectors, and usage stats |
| **Provider** | Yes | One of 23 providers, see [Supported Providers](./providers.mdx#supported-providers) | Determines the call protocol and default endpoint |
| **Model Type** | Yes | Chat, embedding, rerank, decision, TTS, STT, audio generation, text-to-image, text-to-video | Determines how the model is called and which test action runs |
| **Model ID** | Yes | 1–100 characters | The provider's real model name or deployment name; a typo surfaces as "model not found" at call time |
| **API Base URL** | No | ≤ 512 characters | Empty uses the provider/type default; custom addresses must be allowlisted |
| **API Key** | Required for every provider except Ollama | ≤ 1024 characters | Stored encrypted; the UI only shows "API key is configured" afterwards |
| **Provider / Gateway Name** | No | ≤ 100 characters | With **OpenAI-compatible**, replaces the provider name shown in lists |

<Callout type="warn">
**Provider**, **Model ID**, and **Model Type** cannot be changed after saving. To change the provider, model ID, or type, create a new model, authorize it to teams, and repoint the knowledge bases, Agents, and workflows that referenced the old one.
</Callout>

### Parameters

- **Context Length** and **Max Output Tokens** are used for display and capacity checks only; they do not truncate. An Agent-level or per-call max-token value can still override the output cap.
- **Input Price** and **Output Price** are recorded as USD per million tokens. They are reference values and do not drive billing or quotas.
- **Inference parameters** (frequency penalty, presence penalty, default max tokens) fall back to provider defaults when left empty.
- **Input modalities** and **output modalities** declare what the model accepts and can generate (text, image, audio, video, file). Ticking **image** under input is what allows image uploads in chat; output modalities are only a declaration and do not enable image or video generation.
- The three **Model Capabilities** switches are described in [Model capabilities](#model-capabilities).

### Advanced

Sections appear based on provider and model type: **Thinking / Reasoning** (enable thinking, thinking budget, reasoning effort), **Image Settings**, **Video Settings**, **Audio Settings**, **Azure Configuration** (API version, deployment name), plus three JSON inputs — **Extra Request Body**, **Default Params Extension**, and **Config Extension** — for provider-specific parameters. Common setups:

| Scenario | How to fill it in |
| --- | --- |
| Azure OpenAI | Set API version and deployment name under **Azure Configuration**; put the deployment name in **Model ID** as well |
| Volcengine Ark | Fill `X-Api-Key` and `X-Api-Resource-Id` in the **API Key** area |
| Self-hosted gateway | Pick **OpenAI-compatible** as the provider and fill **API Base URL** plus **Provider / Gateway Name** |
| Reasoning model | Turn on **Enable thinking**, then set a **thinking budget** or **reasoning effort** if needed |

Exact field names, ranges, and defaults are in [Model Definition Fields](/reference/model-providers#model-definition-fields).

## Auto-discovering provider models

When creating a model, after you fill in **Provider**, **API Base URL**, and **API Key** (local providers such as Ollama need no key), the form automatically fetches the provider's available models: the **Model ID** input becomes a searchable dropdown listing what the provider returned (shown as "name (ID)"). Picking one fills in the name, context length, max output tokens, modalities, and capability switches, so you never mistype the model ID. The hint under the field reports fetching, success, or failure.

- Discovery only runs when **creating** a model; editing an existing model does not re-fetch.
- Providers without a model-list API (Azure OpenAI, Runway, Pika, Luma, Kling, Stability AI, Midjourney) show no list — enter the model ID manually.
- A failed fetch only costs convenience: a manually entered model ID still saves and works.
- The credential used for discovery is used for that request only and is not stored because of it.

Supported providers, address rules, and failure reasons are in [Remote Model Discovery](./providers.mdx#remote-model-discovery).

## Credentials and endpoints

- **API Keys are stored encrypted.** After saving, every page shows only "API key is configured" — the plaintext is never displayed. To rotate, enter a new value in the edit form; leaving it empty keeps the current key.
- Key formats follow a convention: OpenAI-style keys start with `sk-`, Anthropic keys with `sk-ant-`. When the format clearly does not match, **Test Connection** reports a format error. **Ollama** is the only provider that needs no key.
- The effective request address falls back in this order: the model's **API Base URL** → the type's default → the provider's default. It must match the [endpoint allowlist](./providers.mdx#endpoint-allowlist).

## Model capabilities

The three capability switches decide whether Agents and workflows can use specific model behavior:

| Switch | Effect when on | Cost of getting it wrong |
| --- | --- | --- |
| **Function Call** | Lets the model call tools | Off: Agents cannot use tools. On for a model that does not support it: protocol errors during tool calls |
| **Streaming** | Streams the answer as it is generated | Off: answers arrive in one shot and long answers feel slower to start |
| **JSON Mode** | Supports structured JSON output | Off: JSON-dependent nodes and parameter extraction fall back to text parsing |

Before enabling tools for an Agent, confirm the chosen chat model really supports **Function Call**: read the provider's declaration from the **Model ID** dropdown while creating the model, then correct it by hand if needed.

## Testing connections

**Test Connection** in the dialog sends one minimal request upstream using the current form contents and reports success or failure plus the **latency**:

| Situation | What is tested |
| --- | --- |
| New, unsaved model | The credentials currently in the form; they are not persisted |
| Editing a saved model | The saved configuration; a newly entered key is used as-is |

Test actions per model type:

| Model type | What the test does |
| --- | --- |
| Chat | Sends `Hi` and requires non-empty text back |
| Embedding | Embeds a fixed string and requires a vector |
| Rerank | Reranks two documents against a fixed query and requires results |
| Decision | Sends one minimal decision request to TypeSafe and requires an answer |
| Text-to-image | Generates one test image |
| Text-to-video | Really creates a video task and waits for the render |
| TTS / audio generation | Synthesizes a fixed clip of audio |
| STT | Validates the key format only; no real transcription |

<Callout type="warn">
- **Passing the test does not mean the quota is sufficient**: when upstream throttles, every type except text-to-video still reports success together with a rate-limit notice.
- **The text-to-video test creates a real task and incurs provider charges**, waiting up to 120 seconds by default. If the provider renders slower, the test reports a timeout — raise the wait seconds in **Advanced** > **Config Extension**.
</Callout>

<Callout type="info">
Only single-request connection checks exist. There is no multi-request load test, concurrency test, or p95 latency statistic.
</Callout>

## Enabling, disabling, and default models

Use the row actions in the model list to **Enable** / **Disable** a model, or change **Status** and **Set as default model for this type** in the edit dialog.

- Disabling is the only way to retire a model: it disappears from every selector while its configuration and team authorizations are kept, and re-enabling restores it.
- **The default model is unique per type**: **Set as Default** clears the default flag from other models of the same type. Knowledge base embedding and the Agent fallback when no model is chosen both rely on it.
- The list can be filtered by status and deleted in bulk.

## Authorizing models to teams

Only a superuser can authorize models:

1. Go to **admin panel** > **Teams** and open the target team.
2. Switch to the **Model Authorization** tab and select **Authorize Model**.
3. Tick one or more globally enabled models in the dropdown (already authorized ones are not listed). You can authorize several at once.
4. Set daily / monthly token limits and request limits plus priority for each model. Leave a field empty for unlimited.
5. Select **Authorize** to save.

Team members can then see the model on their **Models** page.

- A team has exactly one authorization per model; authorizing the same model twice is rejected.
- Authorized models can be adjusted via **Edit Authorization** (quotas, priority) or removed with **Revoke Authorization**.
- Team administrators can view **Authorized Models** and usage, but authorizing, changing quotas, and revoking are superuser-only.

### What a team sees

- The team **Models** page lists every authorized model, including globally disabled ones, and can filter by status.
- Model selectors in Agents, workflows, and elsewhere only offer models that are both authorized and enabled.

## Quotas and usage

All four limits can be left empty (unlimited); **`0` is a valid value** and means immediately exhausted.

| Limit | Default | Meaning |
| --- | --- | --- |
| Daily token limit | Unlimited | Tokens available per day |
| Monthly token limit | Unlimited | Tokens available per month |
| Daily request limit | Unlimited | Requests allowed per day |
| Monthly request limit | Unlimited | Requests allowed per month |

Enforcement differs, so configure with care:

- **Token limits** reject only when "used + estimate for this call" exceeds the limit, so hitting the limit exactly does not fail until a bit more is used.
- **Request limits** reject when "used ≥ limit": request number `limit` still succeeds and request `limit + 1` is blocked.
- Usage resets on the site timezone: after 00:00 each day and after 00:00 on the 1st of each month, the next quota check zeroes the counters.
- Once exhausted, chat reports "Model quota exceeded" — raise the limit or wait for the next reset.

The progress bar in the authorization list counts **token** limits only. To check request quotas, compare used requests with the daily / monthly request limits yourself.

## Priority

**Priority** defaults to `0` and only affects the ordering of same-type models in selectors, never availability: a larger value sorts earlier. Edit it together with quotas in **Edit Authorization**.

## Updating, revoking, and deleting

| Action | Effect |
| --- | --- |
| Edit model | Name, API key, base URL, capabilities, pricing, parameters, and status can change; provider, model ID, and model type cannot |
| Disable model | Globally hidden, team authorizations kept, restorable at any time |
| Revoke team authorization | The team immediately loses the model and its usage records are removed |
| Delete model | The global entry is deleted and **every team's authorization for it is deleted too** |

<Callout type="error">
Deleting a global model also deletes all team authorizations and cannot be undone. To retire a model for one team only, revoke that authorization instead of deleting the model.
</Callout>

## Troubleshooting

### Connection test fails

1. **Check the allowlist**: confirm the custom endpoint's scheme + host + port is in **Site Settings** > **Security** > **Model Endpoint Allowlist**. Non-default ports such as `:11434` are compared too.
2. **Check the key format**: OpenAI-style keys need the `sk-` prefix, Anthropic keys `sk-ant-`; confirm the key is valid and may access the target model.
3. **Check provider/type matching**: combinations such as Anthropic + embedding or Stability + text-to-video may save but fail at call time.
4. **Check the network**: a 15-second timeout applies and redirects are not followed; confirm internal addresses are reachable.
5. **Check upstream status**: provider throttling or outages also show as test failures, though throttling usually still reports success.

### "Model quota exceeded"

1. Open **admin panel** > **Teams** > target team > **Model Authorization** and find which limit was hit.
2. Raise the limit, switch to a same-type model with headroom, or wait for the daily / monthly reset.
3. If you suspect a false positive, look for one oversized request: token limits compare used plus estimate.

### Slow responses or timeouts

1. Review **Context Length** and **Max Output Tokens**; an oversized output cap noticeably lengthens responses.
2. Lower the Agent's max tokens, turn on **Streaming**, or switch to a faster model.
3. Video models that render slower than the test wait time report a timeout during testing.
