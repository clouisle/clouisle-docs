Authorization in Clouisle combines **global roles** with **team gates**. The frontend hides menus and buttons by permission, but the backend re-checks every request — "I can't see the entry" is not a security boundary, and calling the service directly is rejected the same way.

See the [permissions and roles reference](../../../reference/permissions.mdx) for the permission catalog and built-in role matrix. This page covers **how to operate, who has permission, and what happens on failure**.

## Permission Model

### Two authorization layers

- **Global roles** decide *what* someone can do: enter the admin console, create Agents, change site settings, export audit logs.
- **Team gates** decide *where and at what level*: team roles are owner, administrator, member, and viewer, and carry no permissions themselves.

The layers are combined with AND. A user with permission to create Agents must still belong to a team to create one there, and a team owner does not gain admin console access from the role.

### Check order

Requests scoped to a team are checked in this order; any failed step rejects the request:

1. Does the team exist?
2. Is the user a super administrator? If so, allow — no role or membership lookup.
3. Is the user a member of the team?
4. Is this a team-management action? If so, require owner or administrator in that team.
5. If the user is a viewer in that team, allow only read and use actions.
6. Do the global roles include the required permission?

Failures report no permission, team administrator required, or not a team member, instead of returning empty data.

### Permission categories

**Admin console permissions** cover admin features: users, roles, permissions, teams, models, capabilities (tools and Skills), Knowledge Bases, site settings, integrations, conversations, memory, notifications, and audit logs. Entering the admin console requires admin console access; each page then checks its own view or update permission.

**Resource permissions** cover Agents, workflows, Knowledge Bases, tools, Skills, conversations, and memory within a team. They are granted through global roles and then combined with the team gate. API keys are the exception: they belong to individuals.

<Callout type="info">
  Tools and Skills are reached through the **Capabilities** page in the admin console; there is no separate Tools navigation item.
</Callout>

## Built-in Roles

Five global roles are built in. They cannot be renamed or deleted, and their permission sets cannot be changed.

| Role | Admin console | Key permissions |
| --- | --- | --- |
| **Super Admin** | Yes, and bypasses all checks | Everything; the first registered user becomes Super Admin |
| **Admin** | Yes | Admin read/write, full team resource permissions, read-only integrations and audit; **cannot** create or modify roles, change site settings, change integration configuration, or modify/delete memory |
| **Team Admin** | No | All Member permissions plus changing team information and managing members |
| **Member** | No | Create, edit, and run resources in the team; manage own API keys; cannot delete teams, delete or publish Agents, delete or publish workflows, or delete tools |
| **Viewer** | No | Read and use/execute only; no write permission and no API key permission |

### Super Admin

Holds every permission. The first registered user is promoted automatically. Super administrators are allowed through team endpoints directly, but still need a team membership record to appear in member lists.

### Admin

Can manage all teams and team members, but team-management actions still require owner or administrator **in that team**. Admin is the day-to-day operations role: users, teams, models, capabilities, Knowledge Bases, conversations, and audit, but not role design or site-level configuration.

### Team Admin

Permissions equal Member plus changing team information and managing members. On startup the system grants this role to everyone who is an owner or administrator in any team. Therefore **grant the Team Admin role before making someone a team administrator**, otherwise the missing team-management permission rejects the action.

### Member

Creates, edits, and runs Agents, workflows, Knowledge Bases, tools, and Skills within a team, and manages own API keys. Note: even though Member holds the delete-tool permission item, actual deletion still requires a team administrator and is rejected.

### Viewer

Read-only role and the default global role for new users. Can view the team, chat with Agents, run workflows, retrieve from Knowledge Bases, and execute tools and Skills, but cannot create or modify resources or manage API keys.

<Callout type="warn" title="Built-in role permissions are maintained by the platform">
  On every startup the platform aligns built-in role permission sets with the built-in list: manually added permissions are removed and missing ones restored. Create a custom role when you need a different combination.
</Callout>

## Two Operating Interfaces

Two interfaces involve teams and roles, with different requirements:

| Interface | Location | Who can enter | What they can do |
| --- | --- | --- | --- |
| Admin team list | Team switcher → **Manage all teams (system admin)** | Administrators with team-view permission or super administrators | List all teams, create, edit, delete teams, bulk delete |
| Team settings | Team switcher → **Manage current team** | Team owners or administrators | View members, add members, change roles, remove members, leave, transfer ownership, view authorized models (read-only), change team information |

Regular members and viewers do not see **Manage all teams**; their only entry is **Manage current team**, where regular members can only view. The **Model authorization** tab is read-only for team administrators and states that the system administrator assigns it.

## Integration and Delivery Log Permissions

Integration interfaces are authorized by domain, and the login domain is independent of the built-in services domain:

| Interface | Who can view | Who can modify |
| --- | --- | --- |
| Integrations overview and login identity sources | Anyone with view permission in either domain | The login domain is controlled by login-management permission |
| Email / Webhook / Feishu / WeChat iLink | Built-in services view permission | Built-in services management permission |
| Delivery log | Built-in services view permission | Read-only |

- The global SSO switch appears on the **Security** page but is authorized under the login domain, not general site settings.
- The delivery log sits in the **Monitoring** sidebar group, which also requires admin console access; a user with only delivery-log view permission does not see the entry, but opening the page address directly is still allowed under that permission.
- The built-in Admin role can view integration configuration and the delivery log but cannot change them — changing configuration needs Super Admin or a custom role with the matching update permission.

## Role Management

The admin **Roles** page lists all roles. The built-in Admin role can only view roles, so **only Super Admin (or a custom role with role-management permission) can create, modify, and delete custom roles**.

### Create a custom role

1. Sign in as Super Admin and go to **Admin** → **Roles**.
2. Click **Create Role** and fill in **Name** (globally unique) and **Description**.
3. Select permissions by category in the permission list.
4. Save.

Custom roles are global roles assignable to any user, independent of team membership. A duplicate name reports that the role already exists.

**Example:** Content manager — needs only team view, Knowledge Base management, and Agent chat permissions, with no admin console access.

<Callout type="warn">
  When creating a role, selecting a permission that does not exist is silently ignored; when replacing a permission set later, an unknown permission raises an error. The two behaviors differ — keep this in mind when troubleshooting.
</Callout>

### Edit a role

You can change a custom role's name and description, and **replace** its permission set wholesale — saving submits the complete list, not a delta. Built-in roles cannot be renamed, re-described, or have permissions changed.

### Delete a role

Two hard constraints apply:

- Built-in roles cannot be deleted.
- A role still assigned to users cannot be deleted; the page reports how many users still hold it.

<Callout type="error">
  Deleting a role has **no** "migrate users to another role" option. To delete a custom role in use, first change each affected user on the **Admin** → **Users** edit panel, then delete the role. The list page supports selecting several custom roles for bulk deletion.
</Callout>

### Custom permissions

The permission catalog can also be maintained on the **Permissions** page, which requires permission-view permission; creating, modifying, and deleting each require their own permission.

Built-in permissions cannot be modified or deleted; a duplicate custom permission identifier reports that it already exists.

<Callout type="warn">
  A new custom permission is only a data record: unless the platform happens to check that permission somewhere, selecting it for a role unlocks nothing.
</Callout>

## User Permissions

### View user permissions

**Admin** → **Users** opens the user list. The detail/edit panel shows:

- The user's **global roles** (multi-select)
- Team membership and team roles (maintained on the team page)
- Sign-in method, account status, and whether the user is a super administrator

There is no aggregate "effective permissions" view: actual permission is the union of all global roles combined with team gates, so compare against the [permissions and roles reference](../../../reference/permissions.mdx) manually.

### Change a user's global roles

1. **Admin** → **Users**, click **Edit** on the target user.
2. Select or clear roles in the **Role** area (multi-select).
3. Save.

Saving **replaces** the role list: roles not listed are dropped, and unmatched role names are ignored.

<Callout type="warn">
  **Protection rule:** if the user is still an owner or administrator of any team and the new roles no longer include team-management permission, saving is rejected. To remove team-administrator capability, first downgrade their member role in every team.
</Callout>

Role changes apply to subsequent requests immediately. Signed-in sessions are not kicked out, but the next restricted action is rejected.

Roles **cannot** be assigned when creating a user: a new user has no global role and must be assigned one afterwards.

## Team Permissions

### Team roles are gates, not grants

Team roles have four fixed values: owner, administrator, member, and viewer. They carry no permissions and answer only two questions: is this person a member of the team, and is their level sufficient for a management action?

Team-management actions (changing team information, member management, deleting a team, deleting tools) require both the global permission **and** owner/administrator in that team.

### Team roles with typical global combinations

Actual capability = global role permissions ∩ team gate. The most common combinations (assuming the member holds the corresponding global role):

| Capability | Owner + Team Admin | Administrator + Team Admin | Member + Member | Viewer + Viewer |
| --- | :-: | :-: | :-: | :-: |
| View team and members | ✓ | ✓ | ✓ | ✓ |
| Change team information (name/description/avatar) | ✓ | ✓ | ✗ | ✗ |
| Add members | ✓ | ✓ | ✗ | ✗ |
| Change member roles | ✓ | ✗ | ✗ | ✗ |
| Remove members | ✓ | ✓ (not other administrators or the owner) | ✗ | ✗ |
| Transfer ownership | ✓ | ✗ | ✗ | ✗ |
| Delete team | ✗ (admin console only) | ✗ | ✗ | ✗ |
| Create/edit Agents, workflows, Knowledge Bases | ✓ | ✓ | ✓ | ✗ |
| Delete Agents, publish Agents and workflows | ✓ | ✓ | ✗ | ✗ |
| Chat with Agents, run workflows | ✓ | ✓ | ✓ | ✓ |
| Create/edit own tools and Skills | ✓ | ✓ | ✓ | ✗ |
| Edit others' tools/Skills | ✓ | ✓ | ✗ | ✗ |
| Delete tools | ✓ | ✓ | ✗ (team gate) | ✗ |
| Retrieve/test Knowledge Bases, upload/delete documents | ✓ | ✓ | ✓ | Read-only retrieval |
| Execute tools and Skills | ✓ | ✓ | ✓ | ✓ |
| Manage API keys | Own only | Own only | Own only | ✗ |
| View audit logs / admin console | Needs extra global permission | Same | ✗ | ✗ |

A team viewer and the global Viewer role are different things: the former only means "lowest level in this team" and does not grant global Viewer permissions; conversely, when adding a global Viewer to a team, also set them as viewer.

<Callout type="warn" title="API keys are not team resources">
  API keys belong to individuals: anyone other than a super administrator sees and manages only their own keys, and team owners or administrators **cannot see or revoke** someone else's keys. Only super administrators can view all API keys.
</Callout>

See [Teams and members](./teams.mdx) for the full constraints on team-management actions.

### Resource visibility

Beyond the two layers, each resource's own visibility also gates access:

| Visibility | Who can view | Who can edit or delete |
| --- | --- | --- |
| Team | Team members | Creator or team owner/administrator |
| Private | Creator only (team owner/administrator when the creator is missing) | Creator only (team owner/administrator when the creator is missing) |

Agents and workflows follow the same rule. Other teams cannot view or call the resource even if they know its address.

### Shared resources

Cross-team sharing covers **tools** and **Knowledge Bases**:

- A custom tool can be shared by an administrator of the owning team with another team; the receiving team sees it under "shared with me", with either read-only or read-and-view-results permission.
- A Knowledge Base can be shared **read-only** with another team by an administrator of the owning team; the receiving team can view and search it but cannot modify it.
- Private resources cannot be shared, and a resource cannot be shared with its own team. Sharing is one-way, created and revoked by the owning team.
- Agents and workflows have no per-team sharing layer: cross-team visibility follows the resource's own visibility, and everything else stays team-isolated by default.

## API Key Ownership

API keys belong to users. They can carry an expiration time, bind specific Agents and workflows, and are managed on the page or in personal settings. The interface lets you enter a request limit and scopes, but the current version neither throttles nor narrows permissions accordingly — do not treat them as effective security controls. Key access is still constrained by bound objects and team isolation; see the [API key reference](../../../reference/api-keys.mdx).

## Permission Audit

There is no dedicated permission-change audit view, and audit logs have no "grant" or "revoke" action type. Current coverage:

| Audited | Not audited |
| --- | --- |
| User create, update, delete, activate, deactivate, force password change | **Role create, update, delete** |
| Team create, update, delete, member add and remove, ownership transfer | **Permission create, update, delete** |
| Team model authorization and bulk grant/revoke | **Member role changes, leaving a team** |

Audit logs are filtered by resource and operation on the **Audit Logs** page and require audit-log view permission. See [Audit logs](./audit-logs.mdx).

## Troubleshooting 403

### Permission denied

**Symptom:** a feature is unavailable and the page reports no permission, team administrator required, or not a team member.

Check in order:

1. **Is the global permission missing?** Edit the user under **Admin** → **Users** and check whether any role includes the capability (compare with the [permissions reference](../../../reference/permissions.mdx)). The error usually names the missing permission.
2. **Is the team gate too low?** For team-management actions the user must be owner or administrator; a team viewer's write actions are always rejected.
3. **Is the user a team member?** "Not a team member" means the user is not in that team at all.
4. **Is the resource private?** Private resources return a permission error to non-creators regardless of role permissions.
5. **Is it someone else's API key?** Only the owner or a super administrator can read or write a key.

### Over-privileged users

1. Check the target user's roles under **Users** against the [permissions reference](../../../reference/permissions.mdx).
2. Check each role's permission set under **Roles** — the built-in Admin already covers all team resources, so stacking broad custom roles is usually unnecessary.
3. Before downgrading, check whether the user is still an owner or administrator of any team, or the protection rule rejects the role change.
4. Review regularly. Role changes are not audited, so keep your own record when changing roles.

### Inconsistent permission behavior

1. **Identify the check layer**: team-scoped requests combine global permission with the team gate; only admin console endpoints check admin permissions.
2. **Identify the source of roles**: a user may hold several roles, and permissions are the union; the user may also have been granted Team Admin at startup.
3. **Built-in roles cannot be edited by hand**: their permission sets are restored on every startup.

## Best Practices

**Recommended:**

- Use custom roles for job responsibilities instead of stacking built-in roles.
- Grant the Team Admin global role before setting someone as a team administrator (the reverse order is rejected).
- Combine a team viewer with the global Viewer role for read-only staff.
- Create and rotate API keys per integration instead of sharing a personal key.
- Review role holders and team owner/administrator lists quarterly.

**Avoid:**

- Using Super Admin as an everyday account.
- Trying to modify built-in role permissions.
- Treating "the button is hidden" as a security boundary.
- Running several integrations from one shared account.

## Protection Rules

- The five built-in roles and built-in permissions cannot be deleted, renamed, or have their permission sets changed.
- Unassign a custom role before deleting it.
- A super administrator account cannot be deleted or deactivated.
- The default team cannot be deleted; a team owner cannot leave or be removed until ownership is transferred.
- Permission changes apply to subsequent requests immediately; signed-in sessions do not cache permissions.
