User management lives on the **Users** (`/users`) page of the Admin area, with permissions split by action: viewing the list, adding users, editing/activating/deactivating/password policy, and deleting users. The built-in **Admin** role holds all of these.

This page covers interface actions, visible results, and what to do when a step fails. For account fields, endpoints, and error codes see the [Users API](../../../api/users.mdx). How **roles** affect permissions is covered in [Roles & Permissions](./roles-permissions.mdx).

## List and Filters

The user list is paged with `10` rows per page by default, switchable to `20` / `50` / `100`, and offers:

- **Search box**: fuzzy match by username or email, case-insensitive.
- **Status filter**: **Active** / **Inactive** / **Pending**, multi-select.
- **Role filter**: filter by global role name.
- A **Reset** button appears once any filter is active, clearing search and filters at once.

There are no summary cards at the top, but whenever pending users exist a banner reads "N users are waiting for review"; **View pending** switches straight to that filter.

Each row shows: username (with a Super Admin badge), email, SSO icons, status badge, primary role, password status badge, creation time, and the row action menu.

The three states mean:

| Status | Meaning |
| --- | --- |
| **Active** | The account is usable and can sign in. |
| **Inactive** | An administrator closed the account; sign-in is blocked but data is kept. |
| **Pending** | Registered and awaiting administrator approval; cannot sign in until approved. |

## Adding a User

1. Click **Add User**.
2. Fill in **Username** (globally unique), **Email** (globally unique, must be valid), **Password**, and **Confirm Password**, and set the **Active** switch.
3. Save.

Validation and defaults:

| Case | Result |
| --- | --- |
| Username already exists | Reports that the username is taken |
| Email already exists | Reports that the email is taken |
| No interface language chosen | Uses the default language from site settings (English by default) |
| — | The new user is created **active**; no approval needed |

<Callout type="warn">
  The creation form does **not** accept roles: a new user has no global role and must be assigned one by **editing** the user afterwards, otherwise they only see public resources and cannot operate inside a team.
</Callout>

### Bulk Import / SSO Provisioning

> **Not implemented / Roadmap.** There is no CSV/JSON/Excel user import. Add users one by one, or let SSO create them on first sign-in.

SSO provisioning is controlled by an administrator under **Site Settings** → **Security**:

| Setting | Description |
| --- | --- |
| Auto-create users | When on, the first SSO sign-in creates an account automatically |
| Default global role | The initial role for new users; the first-run default is **Viewer** |
| Default team and default member role | The team new users join and their role; accepts only Viewer/Member/Admin, defaults to Member; Owner is never assigned automatically |
| Match existing accounts by email | Link to an existing account with the same email instead of creating a new one |
| New accounts require approval | When on, new accounts are **pending** and cannot sign in until approved |

> **Not implemented / Roadmap**: SSO provisioning has no email-domain allowlist.

## Editing a User

Choose **Edit** from the row menu:

| Field | Description |
| --- | --- |
| **Username** | Read-only; cannot be changed after creation |
| **Email** | Change to a new email |
| **Password** | Optional. Entering one changes the password (validated against the password policy, with reasons listed when it fails); leaving it blank keeps the current password |
| **Global roles** | Multi-select, **replaced as a whole** |
| **Active** | Activate/deactivate switch |

<Callout type="error">
  **Usernames cannot be changed**: the username input is read-only while editing. A mistyped username can only be fixed by deleting and recreating the user.
</Callout>

### Role Change Safeguards

Roles are replaced as a whole: saving clears the existing set first and writes the new one, so any role not selected is lost; unmatched role names are ignored.

If the target is still an **Owner/Admin** of some team and the new role set no longer includes team management permission, saving is rejected. **Downgrade the team role first, then remove the global role** — the reverse order is blocked.

Submitting a password sends a notification to that user.

## Account State

From the row menu:

| Operation | Behavior |
| --- | --- |
| **Activate** | Restores the account; if it is already active, the interface says so |
| **Deactivate** | Sign-in is blocked immediately; Super Admins cannot be deactivated; if already inactive, the interface says so |

What deactivation actually does:

- Sign-in is blocked: both password login and API keys are rejected with "account inactive" or "pending approval".
- Integrations using that person's API keys **fail immediately** — the keys themselves are not modified, but authentication is rejected because the owner is inactive.
- Resources, team memberships, and sessions are all kept; reactivating restores access.

Activation and deactivation both notify the user and write an audit log entry.

## Deleting a User

Choose **Delete** from the row menu; the confirmation dialog shows the target username and states that the action cannot be undone.

The one hard block: **Super Admin accounts cannot be deleted**.

Deletion impact:

| Deleted | Cleared / kept |
| --- | --- |
| The account itself, password history, notifications and read records | Agents / knowledge bases / documents / tools / Skills they created (resources kept, creator cleared) |
| Personal conversations and messages, Agent run records | Teams they own (team kept, owner cleared) |
| Their API keys and personal memories | Audit logs (compliance; not deleted with the account) |
| All team memberships and scoped role records | Shared resources and other members in those teams |

<Callout type="error" title="Deleting a team Owner leaves the team without an owner">
  Deleting a team's Owner also deletes their membership, leaving the team with no Owner — only a Super Admin can change member roles or grant ownership afterwards. To remove a team Owner, transfer ownership in the team first, then delete the account.
</Callout>

## Passwords and Password Expiration

There is **no** "reset to a temporary password" or "send a reset email from the Admin area" flow. Administrators combine these row actions with the global password policy:

| Operation | Behavior |
| --- | --- |
| **Force Password Change** | Flags the user to change their password at next sign-in and sends a high-priority notification |
| **Reset Password Expiration** | Recomputes the password expiry from now and clears the expiry reminder |
| **Grant Password Exemption** / **Remove Password Exemption** | Exempts the user from the expiration policy; granting also clears the force-change flag |
| Bulk **Force Password Change** / grant or remove exemption | Applies to each selected user and notifies them |

These actions appear only for **local accounts** (SSO users have no local password). When the expiration policy is enabled, the Admin **Dashboard** overview shows a **Password Security** card with counts of expired, expiring-soon, and force-change users; with the policy disabled, all counts are 0.

The global policy is configured under **Site Settings** → **Security**.

## TOTP (Two-Factor Authentication)

- **Adoption statistics**: the TOTP card on the Admin **Dashboard** shows enabled users, total users, and the adoption rate.
- **Per-user status or disabling**: there is **no interface entry**; a Super Admin handles it through the management interface (for example when a user loses both authenticator and backup codes). See the [Admin API](../../../api/admin.mdx).

Users configure, enable, and disable TOTP themselves in personal settings (see [Sign-In and Account Security](./authentication.mdx)).

<Callout type="warn">
  User management has **no** per-user TOTP switch and **no** "require 2FA for this person" toggle; the available capabilities are adoption statistics plus administrator fallback disabling. Requiring 2FA for everyone is a global switch in site settings.
</Callout>

## Bulk Operations

Selecting several users opens a floating toolbar at the bottom:

| Operation | Description |
| --- | --- |
| Send Notification | Opens the notification dialog and sends an in-app notification to each selected user |
| Activate | Activates each user |
| Deactivate | Deactivates each user |
| Delete | Deletes each user; cannot be recovered after confirmation |
| Force Password Change | Flags all selected users and notifies them |
| Grant / Remove Password Exemption | Sets each user individually |

Bulk operations have no transaction rollback: a single failure does not roll back the rest, and the final count may not match the actual number of successes. Recheck users with permission or state conflicts before retrying.

> **Not implemented / Roadmap**: no bulk add/remove from teams, no bulk export, no CSV import/export, and no bulk email entry in the interface (that capability is currently available only through the management interface — see the [Users API](../../../api/users.mdx)).

## User Roles

Global roles (multi-select) determine system-level and Admin-area capabilities; team roles determine the level inside a team. The five built-in roles and their permission sets are covered in [Roles & Permissions](./roles-permissions.mdx):

| Role | Rough capability |
| --- | --- |
| **Super Admin** | Every permission; bypasses all checks |
| **Admin** | Admin-area read/write plus all team resource permissions |
| **Team Admin** | Member plus team settings and member management |
| **Member** | Create/edit/run resources inside a team |
| **Viewer** | Read and use only; the default role |

Team roles (Owner/Admin/Member/Viewer) are maintained on the **team** page, not in the user edit dialog.

## Best Practices

**✅ Do:**

- Review the user list regularly and deactivate departing staff promptly (deactivation immediately blocks sign-in and API keys)
- Assign the minimum necessary global role right after creation
- Require 2FA for privileged accounts and give them a normal password rotation policy
- Watch the Dashboard password security card and handle expiring accounts early instead of firefighting after lockout
- Keep a trail around deactivate, delete, and role changes (the audit log does this)

**❌ Don't:**

- Share administrator accounts (the audit log cannot tell who did what)
- Delete a team Owner's account (the team ends up without an owner)
- Replace a role set wholesale and miss a role
- Rely on "the frontend hides the button" for access control — the backend validates independently

## Troubleshooting

### Cannot Add a User

1. Check whether the username or email is already taken.
2. Check that the email format is valid.
3. Check that your role has user creation permission.

### A User Cannot Sign In

1. Confirm the account is **Active** (inactive or pending accounts cannot sign in).
2. Confirm the password is correct; if needed, **force a password change** or set a new one.
3. Confirm the account is not locked by the sign-in policy (5 failures locks for 15 minutes by default).
4. Check the TOTP state; if the user lost their authenticator, a Super Admin disables TOTP through the management interface.
5. Review **Audit Logs** filtered by user for suspicious sign-ins.

### Cannot Delete a User

- The target is a Super Admin → remove the Super Admin flag first, or deactivate instead.
- The target is a team Owner → the backend does **not** block deletion, but the team loses its owner; transfer ownership in the team first.
- Otherwise deletion succeeds — confirm the cascade list above (conversations, API keys, memberships all disappear).

### Changing Roles Is Rejected

The user is still an Owner/Admin of some team and the new role set lacks team management permission. Downgrade their team role first, then change the global role.
