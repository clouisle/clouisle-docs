The notification center aggregates site-wide, team, and personal notifications, with search, unread filtering, and bulk mark-as-read. Automatic notifications are triggered by system events: administrators decide **which event types produce a notification** and **which external channels deliver it** — regular users can only view and mark as read.

## View notifications

Notifications have three scopes, and visibility is computed from team membership:

| Scope | Who sees it |
| --- | --- |
| Global | Every signed-in user |
| Team | Members of the target team |
| Personal | One specific user |

Priority levels are **Low** / **Medium** / **High**. **Read state is per-user**, so marking something read never affects anyone else. Expired notifications are hidden by default — so a notification "disappearing" usually means it expired, not that it was deleted.

The page filters by scope, type, and priority, searches title, content, and type case-insensitively, and can show unread only or filter by creation time. The list is paginated at up to `100` per page, `20` by default.

<Callout type="warn">
  This version only supports **bulk** mark-as-read (mark all, or select rows and mark them). Regular users cannot delete individual notifications; only administrators can delete. The way to "clear one item" is to filter and then mark that batch as read.
</Callout>

## Configure channels

Configure channels under **Site Settings** > **Notification Channels**. A channel delivers only when **both** conditions hold: its switch is on *and* the required fields are filled in. Every channel is off by default.

| Channel | What to fill in | How to test |
| --- | --- | --- |
| Email | SMTP host, port, encryption (None / SSL / TLS), username and password (optional), sender name and address | Enter a test mailbox in the email channel and **Send test** |
| Webhook | Webhook URL, HTTP method (`POST` / `GET`), custom headers (JSON), body template (JSON), signing secret (optional) | **Send test** in the Webhook channel |
| Feishu | The Feishu integration is enabled with **Notification** turned on; the App ID and App Secret are saved; recipients have a directory-sync Feishu identity binding | On the Feishu page's **Notifications** tab, choose recipients and send a test message |

<Callout type="note">
  There are exactly three external notification channels: **email**, **Webhook**, and **Feishu** (legacy third-party chat channels were removed). Feishu notifications require the separate **Notification** feature and are sent only to users whose Feishu identity was bound through directory sync; unlinked or deactivated recipients receive nothing. WeChat iLink is a [messaging integration](../integrations/wechat.mdx) for Agent chat and knowledge collection — it is **not** a notification channel.
</Callout>

After saving, send a test message and only then enable the channel in Automatic Notifications. **Never put a signing secret in a URL query parameter** — query strings end up in proxies, gateways, and browser history.

When a Webhook channel has a signing secret configured, outgoing requests carry `X-Webhook-Signature: sha256=<hex>` and `X-Webhook-Signature-256: <hex>`, both HMAC-SHA256 over the **raw request body**. Receivers must verify against the unparsed, unmodified raw body using a constant-time comparison, otherwise verification fails or gives false positives.

<Callout type="info">
  The body template supports the placeholders `{{title}}`, `{{content}}`, and `{{link_url}}`. If a receiver rejects the payload, that external send is recorded as failed — but the in-app notification has already been created, so an external channel outage never loses the message.
</Callout>

## Automatic notifications

The **Automatic Notifications** page controls two things:

- **External channels**: which channels participate in delivery (multi-select; selecting none keeps notifications in-app only)
- **Event types**: which events create a notification

Viewing requires site-settings view permission; saving requires update permission. Submitting an unknown event type is rejected rather than silently dropped.

There are **25** available types, of which **19 are enabled by default**:

| Group | Event types | Enabled by default |
| --- | --- | --- |
| Team | Member added, member removed, role changed, ownership transferred, model granted, model grant revoked | yes |
| User | User activated, user deactivated, password reset, pending approval | yes |
| Knowledge base | Document indexed, document processing failed | yes |
| Workflow | Workflow failed, workflow approval | yes |
| Workflow | Workflow succeeded | no |
| Agent | Agent published, Agent unpublished | no |
| API key | API key expiring, API key expired | yes |
| Security | Login anomaly, account locked, password changed | yes |
| Password expiry | Password expiring, password expired | no |
| Password expiry | Force password change | no (no current trigger) |

<Callout type="warn" title="Disabling a type drops the event permanently">
  If a type is not enabled, the notification is **never created** when the event fires (the check happens before creation), and enabling it later cannot backfill the missed events. Workflow success is off by default on purpose — notifying on every successful run quickly drowns the notification center; turn it on only if you genuinely need per-run confirmation. Agent publish and unpublish are similarly high-volume and meant to be enabled on demand.
</Callout>

### Scheduled checks

These automatic notifications are checked daily by the platform, in the server timezone:

| Check | Time | Behaviour |
| --- | --- | --- |
| API key expiry | Daily at `09:00` | Finds keys expiring within `7` days and reminds only at exactly `7`, `3`, and `1` day remaining; already-expired keys send "API key expired" |
| Password expiry | Daily at `08:00` | Expired passwords send "Password expired"; inside the warning window (`7` days by default) it reminds only at `7`, `3`, and `1` day remaining |

The "remind only at 7/3/1 days" rule is deliberate de-duplication — without it the same user would be pinged every single day.

### Login anomaly detection

Login anomaly notifications are not a rules engine; they compare against a stored login fingerprint:

- Each user keeps the last **30** days of at most **10** IPs and **10** browser identifiers (oldest entries are evicted).
- Seeing an IP or browser identifier **outside the known set** flags the login and sends a "Login anomaly" notification.
- **A first-ever login is never flagged** (there is no history to compare against), so a brand-new account produces a clean first record.
- Login history is kept on the platform; when storage is unavailable the check is skipped rather than reporting a false anomaly.

<Callout type="warn">
  A single proxy egress IP hides the real origin, and shared NAT egress makes "new IP" unreliable. High-security deployments should pair anomaly notifications with the "login succeeded" and "login failed" entries in the audit log instead of relying on anomaly detection alone.
</Callout>

### Delivery states

External delivery states are **Pending**, **Sending**, **Sent**, **Failed**, and **Skipped** (no eligible recipients). Failures record a retry count; when Feishu delivery is partially successful, the notification detail shows the success and total counts (for example, "Sent to 2 of 5 recipients"). These records are separate from the messaging integration's delivery records — see the [Delivery log](../integrations/delivery-log.mdx).

<Callout type="warn">
  Do not rely on external channels alone. Confirm important security events in both the notification center and the [audit log](./audit-logs.mdx): the audit log is the authoritative persisted record, while an external channel can fail silently due to expired credentials or network problems.
</Callout>

### Administrator notes

- **Users:** check the notification center regularly; act on security notifications immediately and change the password when prompted.
- **Administrators:** configure and successfully test a channel *before* selecting it in Automatic Notifications — selecting an unconfigured channel sends nothing and creates a false sense of coverage. Feishu also needs each recipient to have a directory-sync Feishu identity binding; otherwise the delivery is recorded as Skipped or partially successful.
- Choose enabled types deliberately: workflow success and Agent publish/unpublish are high-volume and should be enabled only when truly needed.
- A non-global administrator can only manage their own team's notifications: they cannot choose the site-wide scope, must name a team, and must pass that team's admin check — so other teams' notifications are neither visible nor manageable.
