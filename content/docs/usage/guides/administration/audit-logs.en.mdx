Audit logs record resource operations in the system: the actor, action, resource, before/after snapshots, and source IP. Sensitive fields are masked when recorded and displayed, so raw secrets never appear in logs.

Viewing audit logs requires audit-log view permission, and exporting requires export permission; administrators assign these through roles, see [Roles and permissions](./roles-permissions.mdx).

## What Audit Logs Record

Every event records the actor, time, resource, operation type, status, and change details. Events fall into these categories:

### Authentication events

Successful sign-ins, failed sign-ins, sign-outs, and registrations. Records the account, time, source IP, browser identifier, authentication method, whether two-factor authentication was used, plus failure reason and attempt count.

### User management events

Administrators creating, updating, deleting, activating, or deactivating users. Update events keep before/after field snapshots.

### Team management events

Creating teams, changing team information, adding or removing members, and transferring ownership.

### Agent and workflow events

Creating, updating, publishing, and deleting Agents and workflows. Update events keep before/after fields such as the prompt or iteration limit.

### Sandbox task events

The lifecycle of code sandbox jobs: start, completion, failure, cancellation, and recovery. Only the job identifier, source, and result are recorded — **never** the code, parameters, output, or raw error text. Failures carry a stable error category rather than a stack trace.

### API key events

Creating, activating, and deactivating API keys. Records the name, scope, number of bound Agents/workflows, and expiration time.

### Site settings events

Single updates, bulk updates, and resets of site settings. Records the settings and their before/after values.

### Security events

Changing a password, resetting a password, activating or deactivating an account. Records the actor, target user, and source IP.

## Viewing and Filtering

Go to **Admin** > **Audit Logs**. Each record shows: time, user, action, resource type, resource name, operation (create/read/update/delete), status, IP address, and details.

Filters:

| Filter | Description |
| --- | --- |
| User | By actor |
| Team | By team |
| Action | Exact match on one or more actions; no wildcards |
| Resource type | User, team, Agent, workflow, and so on |
| Resource ID | By specific resource |
| Status | Success, failure, and so on |
| Date range | Start and end dates |
| Keyword | Case-insensitive substring match on resource name, resource ID, and IP address |

<Callout type="info">
  There is no IP-only filter, but the keyword matches IP fragments (such as `192.168.1.`). The keyword does not interpret `*` or other wildcards.
</Callout>

<Callout type="warn">
  **Roadmap:** you cannot filter by changed field or value; field-level snapshots appear only in details and exports, and filter conditions cannot be saved.
</Callout>

### Viewing log details

Click an entry to see the full details:

- **Basic information**: record ID, time, actor, action, status
- **Resource information**: resource type, resource ID, resource name, operation type
- **Request information**: source IP, browser identifier, authentication method
- **Change details**: field-level before/after snapshots (sensitive values masked)
- **Metadata**: team, model, execution duration, and so on

<Callout type="warn">
  **Roadmap:** there is no related-logs view. To find related entries, filter by the same user, resource ID, or date range.
</Callout>

## Sensitive Data Masking

Snapshots are sanitized before they are stored, so raw secrets never appear anywhere in audit logs:

- Password, key, access-token, refresh-token, and private-key fields are fully masked, keeping only a short identifiable prefix.
- Emails show only the first and last characters, for example `a***e@example.com`.
- Sensitive fields inside nested structures are masked too.
- Long text becomes a preview: a single value over `500` characters, or a whole snapshot whose serialized form exceeds `500` characters, is stored as the first `500` characters plus an ellipsis. Details and exports therefore show a **preview**, not the full original.

## Exporting Audit Logs

CSV and JSON are supported. Exports use the same filters as the list (except resource ID), return at most `10,000` rows, and are ordered newest first. CSV contains ID, time, user, action, resource type, resource name, operation, status, IP, and error message; JSON keeps the full entries and change snapshots.

<Callout type="warn" title="Export keyword scope is slightly narrower">
  The list keyword matches resource name, resource ID, and IP address; the **export keyword matches only resource name and IP address**, and exporting by resource ID is not supported. Searching by resource ID and then exporting returns more rows than the list — use the resource name or IP as the export condition when troubleshooting.
</Callout>

Export is manual: there is no scheduled export or email delivery. Users without export permission do not see the export button.

## Retention and Archiving

### Retention policy

Audit logs are kept for `365` days by default, configurable to `30-3650` days.

**To configure:** go to **Admin** > **Site Settings** > **Storage** and change the **audit log retention** and **archive file path**.

### Manual archiving

1. Go to **Admin** > **Site Settings** > **Storage**.
2. In the **Audit logs** section, click **Archive** and confirm.
3. Archiving runs in the background and the page shows progress; if it takes longer than `5` minutes the page reports a timeout, and you can refresh later for the result.

> **Note:** the manual archive entry lives on the **Storage** settings page, not the audit log page — the audit log page only views, filters, and exports.

Archiving selects logs past the retention cutoff and writes them to monthly JSON files under the archive path; an existing file for the same month is appended to. Once archiving completes, the archived logs are **deleted from the database**.

<Callout type="warn">
  Archiving deletes the original records, leaving only the archive files. The archive path must be on persistent storage, otherwise a container rebuild loses the only copy; confirm the retention period meets compliance requirements before triggering.
</Callout>

<Callout type="warn">
  **Roadmap:** there is no scheduled automatic archiving — it is always manual; the archive target can only be a local path, not object storage directly; and there is no restore workflow.
</Callout>

## Statistics and Limitations

The audit log page shows four statistic cards at the top: total logs (all time), today's count, failure count, and active users over the last 7 days, for a quick read on system activity.

**Not implemented (Roadmap):** an audit report generator, a real-time monitoring dashboard, and automatic alerts for failed sign-ins or bulk deletions. For security alerts, use the security events and external channels in [Automatic notifications](./notifications.mdx).

## Best Practices

- Review failed sign-ins, permission-related events, and bulk deletions regularly.
- After a key change, filter by resource ID and confirm the change matches expectations.
- Grant audit view and export permissions to designated people only, not everyday business accounts.
- Before archiving, confirm the archive path is on persistent storage with backups, and keep access records for archive files.
- When using audit logs for compliance, confirm the retention period covers the regulatory window.
