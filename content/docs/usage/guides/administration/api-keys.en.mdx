API keys call the Clouisle API from contexts without a user session. Every key authenticates as its **owning user**, so the owner's role permissions and team memberships apply to every request; the key can additionally narrow access to specific Agents or workflows.

<Callout type="info">
  Prerequisites: your role needs permission to view and create API keys (Super Admin has every permission by default). A key can only be bound to Agents and workflows you can already access — otherwise creation or saving is rejected. See the [permissions and roles reference](../../../reference/permissions.mdx) for the full catalog.
</Callout>

## Accessing API Keys

1. Click your **profile icon** in the top-right corner.
2. Select **API Keys** in the user menu.
3. Or navigate directly to `/app/api-keys`.

Each row shows the name, a status badge (**Active** / **Inactive** / **Expired**), the key prefix (the first 12 characters of the full key), rate limit, expiration, last-used time, and creation time. The page has only a **search box**, which filters instantly by name or prefix.

Visibility follows your role: **only Super Admins** see and manage everyone's keys. Every other user sees only their own keys, and editing or deleting someone else's key is rejected.

## Creating a Key

<Steps>
  <Step>### Open the creation form</Step>
  Go to **API Keys** (`/app/api-keys`) and click **Create Key**.
  <Step>### Fill in the configuration</Step>

  | Field | Required | Description |
  | --- | --- | --- |
  | **Name** | Yes | Descriptive name, `1`–`100` characters |
  | **Rate Limit** | No | Requests per minute; `0` means unlimited. The form **starts at `0`** — see [Rate Limits](#rate-limits) |
  | **Expiration** | No | Date picker; leave empty for a key that never expires |
  | **Allowed Agents** | No | Checkbox list that loads **published Agents only**, up to `100`; empty = all Agents allowed |
  | **Allowed Workflows** | No | Checkbox list that loads **published workflows only**, up to `100`; empty = all workflows allowed |
  <Step>### Save and copy the key</Step>
  Click **Create** (**Save** when editing). The **API Key Created** dialog then shows the full key — the only time it is ever displayed. Use the copy button and store it in a password manager or environment variable.
</Steps>

<Callout type="error">
**The full key is shown exactly once.** Lists and details show only the prefix (the first 12 characters), and the server stores just an irreversible hash, so the key cannot be recovered. A lost key can only be replaced by a new one.
</Callout>

Scopes are **not settable in the interface**, so keys created there always use the default scope; see [Scopes](#scopes).

## Editing a Key

Choose **Edit API Key** from the row menu to edit the **name**, **rate limit**, **expiration**, the **Active** switch, and its **Agent / workflow bindings**. Clearing the bindings (selecting nothing) opens the key back up to "everything accessible".

Editing and deleting require the owner (or a Super Admin); **the key string itself cannot be changed**, and there is no rotation action. Rotate by creating a new key, migrating callers, then deactivating the old one.

<Callout type="warn">
  The date picker submits the expiration as **`00:00:00` UTC on the chosen day**. Choosing `2026-01-01` means the key stops working at midnight UTC on 2026-01-01, not at the end of that day.
</Callout>

## Deactivating / Reactivating a Key

Deactivation makes the key fail authentication immediately while keeping the record and its audit history: choose **Deactivate** from the row's **...** menu to turn it off, and **Activate** to restore it. Repeating an operation reports that the key is already inactive or already active.

## Deleting a Key

Delete the key from its row and confirm. You do not need to deactivate first, and deletion cannot be undone. An audit log entry is written before the delete, so the actor, timestamp, and deleted key prefix remain discoverable.

## Using API Keys

Put the full key in the caller's `Authorization` header — the same format as the sign-in token:

```
Authorization: Bearer clou_your_api_key_here
```

For the exact request and response formats, see the [API Keys API](../../../api/api-keys.mdx).

### Authentication and Preconditions

A key must satisfy all of the following; otherwise the call is rejected (authentication failure or insufficient permission):

1. **The key must exist and be correct** — a typo or missing character fails.
2. **It must be enabled** — a deactivated key behaves exactly like a nonexistent one.
3. **It must not be expired** — no expiration date means it never expires.
4. **The owner must still be valid** — deactivating the owner or leaving the account pending approval invalidates the key too.
5. **The binding must allow this call** — a key bound to Agents may only call those Agents; a key bound to workflows may only trigger those workflows. Empty bindings mean no restriction.

Every successful call refreshes the **last-used time** in the list, which is what you check to tell whether a key is still being used.

<Callout type="info">
  Bindings are enforced at the **call entry points**: Agent conversations, iframe embedding (Agent and workflow runs), and the workflow webhook trigger (which accepts only API keys and requires a published workflow with the webhook trigger enabled).
</Callout>

## Scopes

A scope is a recorded label that **does not currently participate in authorization**:

- There is no field for it in the interface, so keys created there always use the default scope.
- Scopes written through the management interface are not validated against an enumeration and have no wildcard semantics.
- Updates replace the whole set; there is no "add-only" rule.

<Callout type="warn">
  Do not use scopes for access control. What actually decides authorization is the owning user's role permissions, team memberships, and the key's Agent / workflow bindings.
</Callout>

## Rate Limits

The rate limit stores a per-key "requests per minute" value; `0` means unlimited.

**Nothing in this version enforces it**: no step of the call path performs rate limiting, and the `1000/min` or **Unlimited** shown in the interface is purely informational.

There is also an easy-to-miss default mismatch: the server default is `1000`, but the **creation form starts at `0`** (unlimited). Since the form always submits the field, keys created from the interface are effectively unlimited rather than `1000`.

<Callout type="warn">
  For real call constraints, use bindings (narrow the callable Agents / workflows), expiration dates, and role permissions — or enforce limits at your own gateway.
</Callout>

## Expiration Reminders

The system checks key expiration once a day at 09:00 and sends in-app notifications to key owners:

- **Expiring soon**: enabled, not-yet-expired keys with fewer than `7` days left — sent only when the remaining days are exactly **7, 3, or 1**, so it does not repeat daily.
- **Expired**: enabled keys that expired **within the last 24 hours**.

The notification does not change key state — an expired key still carries the "active" flag and is only stopped by its expiration date during authentication. Deactivating a key before it expires stops these notifications.

## Best Practices

**✅ Do**

- Create one key per purpose (production, CI, each partner) so it can be revoked alone.
- Set an expiration and replace long-lived keys with time-boxed ones.
- Bind keys to the Agents / workflows they actually call.
- Keep them in a secret manager or environment variables, never in a repository.
- Periodically review the last-used time and clean up keys that are no longer used.

**❌ Don't**

- Use one person's key to carry several people's traffic (authorization follows that person).
- Ship keys in frontend code, browser extensions, or public docs.
- Treat scopes or rate limits as a security boundary.

## Troubleshooting

### Key Does Not Work (Authentication Failure)

1. Confirm the key is **Active**: a deactivated key behaves exactly like a nonexistent one.
2. Check whether the **expiration** date has passed.
3. Check the header format: `Bearer clou_...` with no line breaks or extra spaces.
4. Compare the **key prefix** (first 12 characters) in the list against the key you are using to rule out a wrong-environment key.
5. If the full key is lost, create a new one — it cannot be recovered.

### Key Is Valid but the Request Is Denied (Insufficient Permission)

1. The key may be bound to specific Agents / workflows: confirm the target is in the binding list, or clear the bindings and retry.
2. The owner's role permissions may be insufficient: verify the same operation works while signed in as the owner.
3. The owner account may be deactivated or pending approval, which invalidates the key too.

### Other Users' Keys Are Not Visible

Only Super Admins see every key; everyone else sees only their own keys, regardless of their permissions.

### Suspected Key Leak

1. **Deactivate** the key from the list first (faster than deleting and it keeps the audit trail).
2. Create a replacement, update the callers, and delete the old key once no traffic remains.
3. Cross-check creation, updates, and deletions in the [audit log](./audit-logs.mdx).
