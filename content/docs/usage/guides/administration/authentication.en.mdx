Clouisle's authentication flow is shaped by site settings: password, email verification, administrator approval, CAPTCHA, forced password changes, TOTP, and SSO can all apply at once. This page walks through each step in order of use, covering defaults, failure outcomes, and recovery paths. For the full list of site-level switches see the [site settings reference](../../../reference/site-settings.mdx); for endpoint fields and error codes see the [authentication API](../../../api/auth.mdx).

## Registration and Email Verification

### Self-Service Registration

1. Open the sign-in page at `https://your-domain.com` and click **Sign up**.
2. Fill in the registration form:

   | Field | Constraint |
   | --- | --- |
   | **Username** | Required, globally unique, up to `50` characters |
   | **Email** | Required, globally unique, must be a valid address |
   | **Password** | Validated against the site password policy (8 characters minimum by default — see [Password Requirements](#password-requirements)) |
   | **Confirm Password** | Must match the password |

3. If CAPTCHA is on, click **Click to verify you are human**.
4. If "require terms acceptance on registration" is on, accept the terms of service and privacy policy.
5. Click **Register**.

The result depends on site settings:

| Site setting | Default | Behavior after submitting |
| --- | --- | --- |
| Allow registration | On | When off, the registration entry reports that registration is disabled |
| New accounts require approval | On | The account enters **Pending**; administrators are notified and sign-in is blocked until approval |
| Email verification | On | The email must be verified before signing in |
| CAPTCHA | Off | When on, the registration page shows click-based human verification |
| Require terms acceptance | Off | When on, the terms must be accepted |
| Force password change on first sign-in | Off | When on, new users must change their password immediately after signing in |

<Callout type="info">
  The **first** user registered on a site bypasses every limit: they are activated immediately, their email is marked verified, and they receive the **Super Admin** role. Register the first administrator before opening registration.
</Callout>

<Callout type="note">
  Clouisle has no invite-based registration. Accounts come from self-registration, an administrator creating them ([User Management](./user-management.mdx)), or SSO auto-creation ([SSO](./sso.mdx)).
</Callout>

### Email Verification

- Verification email is sent through the site's configured mail service; **if no mail service is configured, sending fails** and the page says so.
- The email contains a 6-digit code and a verification link, **valid for 10 minutes**.
- Resending has a **60-second** cooldown (same email + purpose); the button shows the remaining seconds.
- A wrong code or an expired link rejects verification.
- Signing in with an unverified email is intercepted; the sign-in page switches to the verification step and automatically sends a new code.

## Sign-In Methods

### Password Sign-In

1. Open the sign-in page and enter a **username or email** (with `@` it matches by email, case-insensitively; without `@` it matches the username exactly).
2. Enter the **password**.
3. If CAPTCHA is on, click **Click to verify you are human**.
4. Click **Log In**.

Sign-in checks the following in order; any failure stops the rest:

1. **SSO-only mode**: when the site disables password sign-in, password attempts are rejected outright.
2. **CAPTCHA** (when on).
3. **Account existence**: a missing account and a wrong password return the same message, so account existence is not leaked.
4. **Lock state**: while locked, the page reports the lock and the remaining wait.
5. **Local password presence**: accounts auto-created through SSO have no local password and cannot sign in with one — the same "incorrect username or password" message.
6. **Password check**: a failure reports incorrect credentials plus the remaining attempts; reaching the threshold locks the account (see [Account Lockout](#account-lockout)).
7. **Account state**: a deactivated account reports it is inactive; a pending one reports it is awaiting approval.
8. **TOTP**: with TOTP bound, sign-in moves to the second step, valid for **5 minutes**.
9. **Force TOTP**: when the site requires 2FA and the user has not bound it, the user is sent to the setup wizard (valid for **30 minutes**).
10. **Email verification** (when on; Super Admins are exempt).
11. **Password expiration / forced change**: the user still signs in but is sent to the change-password page with the reason (expired or required).

After a successful sign-in, the failure count and lock state reset, and the last sign-in time is refreshed.

### SSO Sign-In

If your organization has configured SSO, you can sign in with corporate credentials.

1. Open the sign-in page and click the SSO provider button (the label comes from the integration's **Button Text**, e.g. "Continue with Google").
2. Authenticate at the identity provider.
3. You are redirected back to Clouisle and signed in.

**First SSO sign-in:**

- With "match existing accounts by email" on (the default) and an existing email, the SSO connection links to that account.
- Otherwise an account is created when auto-creation is allowed. The new account has **no local password**, its email counts as verified, and it enters pending approval when configured.

Supported protocols are OAuth2/OIDC, SAML 2.0, CAS, and Feishu (the Feishu button appears only after an administrator explicitly turns on Feishu sign-in). Configuration and troubleshooting are covered in [SSO Configuration](./sso.mdx).

<Callout type="warn">
  Disabling password sign-in switches the site to SSO only. Before switching, confirm that at least one Super Admin has an SSO connection, or nobody may be able to reach the Admin area.
</Callout>

### First Sign-In

After the first successful sign-in:

1. **Welcome Screen**: shows a welcome message.
2. **Profile Setup**: complete your profile (optional).
3. **Team Assignment**: you may be added to the default team with the default member role (Member by default).
4. **Dashboard Access**: ordinary users enter the platform interface; administrators also see the Admin entries.

## Sign-In Protection

### CAPTCHA

The switch is off by default and applies to **both sign-in and registration** forms. It verifies a real click and pointer trajectory, not typed characters.

- The challenge and its credential are kept for **5 minutes** and are **single-use**.
- A failed check reports an invalid or missing verification, and the page automatically fetches a new challenge.
- The sign-in page loads CAPTCHA only after a username and password are entered, so not seeing it on an empty page is normal.

### Account Lockout

Failures accumulate **per account**, with no rolling window:

- **5** consecutive failures lock the account by default.
- The lock lasts **15 minutes** by default; even a correct password is rejected while locked.
- Below the threshold, the error reports the remaining attempts.
- The count does **not** reset over time: only a successful sign-in, or the first attempt after the lock expires, clears it.
- A lock triggers a high-priority security notification stating the lock duration.

<Callout type="warn">
  This version locks accounts only; there is **no per-IP sign-in rate limiting**.
</Callout>

### Sign-In Anomaly Detection

The system records each account's recently used IPs and devices (up to `10` each, kept for 30 days):

- Once history exists, signing in from a **new IP or new device** triggers a high-priority security notification containing the IP, time, and device information.
- The first sign-in (no history yet) does not alert, so new accounts do not produce false alarms.

## Password Management

### Password Requirements

| Requirement | Default |
| --- | --- |
| **Minimum length** | `8` characters (site settings allow `6`–`32`) |
| **Uppercase** | At least 1 (A-Z) |
| **Number** | At least 1 (0-9) |
| **Special character** | Not required |
| **No reuse** | Cannot match the last `5` passwords |
| **Minimum age** | `0` days (can change immediately) |

<Callout type="note">
  There is no dictionary/weak-password check and no strength indicator — validation results come back as field errors.
</Callout>

**Valid password example** (satisfies the default policy):

```
MySecure#Pass2026!
```

**Invalid password examples**:

```
❌ 12345678       (no uppercase letter)
❌ abcdefgh       (no number)
❌ Pass123        (only 7 characters, below the default 8)
```

### Changing Your Password

1. Open **Profile** (avatar menu) → **Account** tab.
2. Find the **Change Password** area and fill in **Current Password**, **New Password**, and **Confirm New Password**.
3. Click **Update password**.

Outcomes:

- A wrong current password reports that the current password is incorrect.
- Not meeting the minimum age reports how many days remain.
- A policy violation or a reused password lists per-field reasons.
- On success, the password timestamp refreshes, expiration is recomputed, the forced-change flag clears, and a high-priority security notification is sent.

**Tips for strong passwords**: mix character types, use at least 12 characters, avoid personal information, and use a password manager.

### Resetting a Forgotten Password

<Callout type="info">
  Prerequisite: the site must have a mail service configured. Otherwise "Forgot Password?" immediately reports that the mail service is not configured.
</Callout>

1. Open the sign-in page and click **Forgot Password?**.
2. Enter the **email address** and click **Send Reset Email**. To prevent enumeration, it reports success whether or not the email exists.
3. Check the email and use either method:
   - Click the **reset link** in the email;
   - Or expand **or enter the code manually** on the page and enter the 6-digit code from the email.
4. Enter a **new password**, confirm it, and click **Reset Password**.
5. Sign in with the new password.

- The code/link is **valid for 10 minutes**; resending has a **60-second** cooldown.
- Resetting does not require the current password (the credential is the authorization), but the password policy and history still apply; on success the account's failure count and lock state are cleared.

### Password Expiration

If an administrator enables the expiration policy (off by default):

| Setting | Default | Meaning |
| --- | --- | --- |
| Password expiration policy | Off | Master switch |
| Password validity | `90` days | How long a password lasts |
| Warning window | `7` days | How many days ahead reminders start |
| Password history | `5` | Number of past passwords that cannot be reused |
| Minimum age | `0` days | Minimum days between changes |

**Who is exempt**: SSO accounts, individually exempted users, and Super Admins do not participate in expiration or forced changes.

**Timeline**:

- An expiration check runs daily at 08:00: reminders go out at exactly **7 / 3 / 1** days remaining; an expired password triggers an expiration notice and sets the forced-change flag (at most one reminder per user per day).
- If the password is already expired at sign-in, the user is sent straight to the change-password page with the reason.
- The **Account** tab in personal settings shows the **password expiration time**; expired shows a red alert, fewer than 7 days remaining shows a yellow warning.

## TOTP Two-Factor Authentication

### Setting Up TOTP

1. Open **Profile** → **Account** tab and click **Enable two-factor authentication**.
2. The wizard first explains what 2FA does; the second step shows a QR code (issuer `Clouisle`) to scan with an authenticator app (Google Authenticator, Authy, Microsoft Authenticator, 1Password, and so on), or lets you **enter the secret manually**.
3. Enter the authenticator's current 6-digit code to verify (window ±1 period, i.e. ±30 seconds).
4. Save the one-time backup codes: the wizard generates **10**, formatted `XXXX-XXXX`, downloadable (`clouisle-backup-codes.txt`) or copyable.
5. Click **Done**.

Generating the secret **does not enable** 2FA yet; only a successful code check enables it.

<Callout type="warn">
  TOTP secrets are stored encrypted by the platform. **Changing the platform encryption key invalidates every bound TOTP secret**, and users must be unbound by an administrator and re-bind.
</Callout>

### Signing In with TOTP

1. Enter your username and password; the system asks for the second step (valid for 5 minutes).
2. Enter the 6-digit code from your authenticator (or click **Use a backup code** and enter a backup code).
3. Click **Verify**.

A failed check reports an invalid code; when rate-limited, the page shows the remaining seconds. **Rate limit**: **5** failures within a 300-second window starting from the first failure lock verification for **900 seconds** (15 minutes); a success resets the count.

### Backup Codes

- 10 are generated at a time, formatted `XXXX-XXXX`, and **each works only once**.
- The Account tab shows how many backup codes remain.
- **Regenerate backup codes** with the current 6-digit code invalidates the old set immediately and issues a new one.

### Disabling TOTP and Administrator Actions

- **Self-service disable**: click **Disable two-factor authentication** and provide **both** the account password and the current code (or a backup code) in the confirmation dialog — both must pass.
- **Administrator unbind**: a Super Admin can disable TOTP for a user directly, for cases where the user lost both authenticator and backup codes (there is no interface entry for this yet; it is done through the management interface — see the [Admin API](../../../api/admin.mdx)).
- **Force TOTP site-wide**: when the site requires 2FA for everyone, users without it are redirected to the setup wizard and cannot enter the system until they bind it.

## Session Management

### Session Duration

- Sessions last as configured in site settings (**30 days** by default); there is no idle timeout and no "remember me" option.
- The sign-in state is kept in the current browser, survives closing the browser, and lasts until expiry or sign-out.

### Single-Session Mode

With single-session mode on, a new sign-in attempts to invalidate the previous session.

<Callout type="warn" title="Known limitation">
  Single-session mode actually rejects the old session for only about **5 seconds**; afterwards the old session keeps working until it expires. Do not treat single-session mode as a way to kick out sessions.
</Callout>

### Signing Out

1. Click the profile icon in the top-right corner.
2. Select **Log out**.
3. You are redirected to the sign-in page.

Signing out invalidates the current session quickly, but **a copy of the same sign-in credential taken elsewhere is still accepted after about 5 seconds**, until it expires. The measures that truly take effect are changing the password (together with single-session mode), deactivating the account, or shortening the session duration.

## Account Security

### Security Notifications

The following events produce in-app security notifications:

| Event | Trigger | Level |
| --- | --- | --- |
| Password changed | Successful password change | High |
| Account locked | Consecutive failures trigger a lock | High |
| Login anomaly | Sign-in from a new IP / device | High |
| Password change required | Administrator requires a change at next sign-in | High |
| Password reset | Administrator set a new password for the user | Medium |
| Password expiring / expired | 7/3/1 days before expiry / already expired | Medium |

**Reviewing the [notification center](./notifications.mdx) regularly** is the most direct way to spot unauthorized access.

### Account Compromise

If you suspect unauthorized access:

1. **Change your password immediately.** This does **not** invalidate sessions already signed in (see [Signing Out](#signing-out)) and does not affect existing API keys.
2. **Enable TOTP**, or regenerate backup codes.
3. **Check sign-in notifications** for unfamiliar IPs / devices, and deactivate suspicious keys in the [API keys](./api-keys.mdx) list.
4. **Contact an administrator** to deactivate the account — deactivation immediately rejects every request from that account at authentication and is the only instant stop-gap.

### An Administrator Setting a New Password

An administrator can set a new password for a user directly in [User Management](./user-management.mdx):

1. The administrator sets a new password (validated against the password policy, but **password history is not checked**).
2. The system sends the user a password-reset notification — **no email containing a temporary password is sent**, so the administrator must convey the new password through a secure channel.
3. The user should change it themselves right after signing in.

Related administrator actions: **force a password change** (required at next sign-in), **reset the expiration timer**, and **grant an expiration exemption**.

## Troubleshooting

### Cannot Reach the Sign-In Page

1. Check the network connection and the URL.
2. Try another browser and clear cache and cookies.
3. Confirm the site domain is configured correctly (SSO callbacks use it too).
4. Contact an administrator.

### "Incorrect Username or Password"

A missing account, a wrong password, and an SSO account attempting password sign-in all return the same message — that is anti-enumeration design, not a system fault.

1. Confirm you are using a **username** (exact match) or **email** (case-insensitive).
2. If the account was created through SSO and never had a local password, sign in with SSO instead.
3. If the message includes the remaining attempts, avoid triggering a lock.
4. Use [Forgot Password](#resetting-a-forgotten-password) to reset.

### Account Is Locked

1. Wait for the lock to expire (15 minutes by default) and sign in again; the failure count then resets.
2. Administrator activation/edit actions **do not** clear the lock, and there is no "unlock now" button; if access is urgent, use the **forgot password** flow — a successful reset also clears the failure count and lock state.
3. If you are locked repeatedly, check whether an old script is retrying a wrong password.

### No Verification / Reset Email

1. Confirm the site has a mail service configured — sending fails outright without one.
2. Check the spam folder and wait a few minutes.
3. Note the 60-second resend cooldown (the page shows the remaining seconds).
4. Confirm the address matches the one on the account.

### Email Still Unverified Because No Code Arrived

Sign-in interception takes you straight to the verification step and sends a new code; the **Resend** button on the page is subject to the 60-second cooldown.

Because the Admin area has no "mark email verified" switch, if the user never receives mail, first have an administrator confirm the mail service configuration; if it remains unavailable, temporarily disable email verification so the user can sign in, then re-enable it once the mail channel recovers.

### TOTP Cannot Be Verified

1. Check that the device time syncs automatically (±30-second window).
2. When rate-limited, wait as instructed — up to 15 minutes.
3. Use a one-time **backup code** to sign in.
4. When backup codes run out, contact an administrator to unbind and re-bind.

### Asked to Change Password

This means the password is flagged as requiring a change (expired, or forced by an administrator). Enter the current and new passwords on the change-password page; the flag clears automatically afterwards.

### SSO Sign-In Fails

1. Confirm the provider and account state (deactivated/pending accounts are redirected to the callback page with the corresponding message).
2. Check the provider configuration and callback address (see [SSO Configuration](./sso.mdx)).
3. Clear browser cookies and retry, or switch to password sign-in if the site allows it.

## Best Practices

**✅ Do**

- Use a strong, unique password and enable TOTP.
- Use a password manager and never reuse a password.
- Keep your email address valid — it is the only password recovery channel.
- Act on security notifications instead of clearing the list.
- Prefer SSO sign-in to reduce password exposure.

**❌ Don't**

- Share accounts or passwords.
- Stay signed in on public devices (signing out affects only the local session, and see the limits in [Signing Out](#signing-out)).
- Disable TOTP on a shared device.
- Ignore login anomaly alerts.
