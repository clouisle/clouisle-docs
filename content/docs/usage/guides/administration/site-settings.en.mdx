Site settings determine the logged-out pages, authentication flow, resource limits, and runtime policies. Only administrators with permission to view site settings, or super administrators, can see the matching categories.

This page covers the switches, fields, and visible effects in the interface; for exact defaults, the complete field list, and matching rules, see the [Site settings reference](../../../reference/site-settings.mdx).

## Accessing System Settings

1. Log in as an administrator.
2. Navigate to **Admin** → **Site Settings** (Settings section in the sidebar).
3. Choose a category from the settings sub-navigation.

Settings categories:

- **General**
- **Security**
- **Notification channels**
- **Storage**
- **Parsing**
- **Memory**
- **Integrations** (login identity sources, email, Webhook, Feishu, WeChat iLink)

Login integrations and built-in service configuration are authorized separately: someone who can change sign-in methods cannot necessarily change email, Webhook, or messaging integrations, and vice versa.

## General Settings

### Site Information

Configure site name, URL, description, icon, default language, and authentication page layout:

| Setting | Default | Description |
| --- | --- | --- |
| Site name | `Clouisle` | Shown on the sign-in page, browser title, and notifications |
| Site URL | empty | Public address used for callbacks and share links |
| Site description | empty | Short description on the sign-in page and share cards |
| Site icon | empty | Site icon image URL |
| Default language | English | Interface language for new visitors and users who have not chosen one |
| Authentication page layout | Centered | Centered or split layout |

Click **Save changes** after editing; public pages use the new values immediately.

### Theme and Display

Configure the default theme mode, primary color, and branding:

| Setting | Default | Description |
| --- | --- | --- |
| Theme mode | Follow system | Users can override it in personal settings |
| Primary color | empty | Empty uses the built-in palette |
| Branding display | Icon and name | Icon and name, name only, icon only, or hidden |

You can also customize primary-foreground, background, card, sidebar, navbar, accent, and chart colors. Colors use hexadecimal notation, for example `#3b82f6`.

### Language Settings

The default language controls what logged-out visitors see. Signed-in users can switch the interface language in personal settings, and notification messages are generated in the recipient's language.

### Legal and Compliance

Configure ICP filing, terms of service, and privacy policy:

| Setting | Default | Description |
| --- | --- | --- |
| ICP filing number / link | empty | Shown in the page footer when filled in |
| Enable terms of service | Off | Once on, an entry appears on the sign-in and sign-up pages |
| Terms link / text | empty | Text is used when no link is provided (Markdown supported) |
| Enable privacy policy | Off | Same as terms |
| Privacy link / text | empty | Text is used when no link is provided |
| Require accepting terms on sign-up | Off | When on, registration requires checking the agreement |

## Security Settings

### Registration and Approval

| Setting | Default | Description |
| --- | --- | --- |
| Allow registration | On | Turning it off removes the sign-up entry; existing accounts are unaffected |
| New users require administrator approval | On | New accounts wait for approval and cannot sign in before it |
| Email verification | On | Users must verify their email after registering |
| Allow account deletion | On | Turning it off removes the delete-account entry in personal settings |
| Default role | Viewer | Global role granted to new users |
| Default team / default team role | empty / Member | Team and role new users join automatically |

### Password Policy

| Setting | Default | Description |
| --- | --- | --- |
| Minimum length | `8` | Shorter new passwords are rejected |
| Require uppercase letter | On | At least one `A-Z` |
| Require number | On | At least one `0-9` |
| Require special character | Off | When on, punctuation and similar symbols are required |

The policy only applies to new passwords; changing it does not expire existing ones.

Password expiration:

| Setting | Default | Description |
| --- | --- | --- |
| Enable password expiration | Off | When on, users must change an expired password before continuing |
| Password validity | `90` days | Expiry period |
| Warning before expiry | `7` days | Days during which sign-in shows a reminder |
| Remember password history | `5` | Recently used passwords cannot be reused |
| Minimum password age | `0` days | When above 0, users cannot change the password again immediately |
| Force password change on first sign-in | Off | New accounts and accounts after a reset must change the password |

### Sessions and Sign-in Lockout

| Setting | Default | Description |
| --- | --- | --- |
| Session validity | `30` days | Users must sign in again afterwards |
| Allow a single session only | Off | When on, a new sign-in signs out the previous session |
| Maximum sign-in attempts | `5` | Consecutive failures before the account is locked |
| Lockout duration | `15` minutes | While locked, even a correct password is refused; the page reports the account is locked |

A successful sign-in resets the failure counter.

There is no "maximum concurrent sessions" setting; concurrency is controlled by the single-session switch and session validity.

### Two-Factor Authentication

| Setting | Default | Description |
| --- | --- | --- |
| Require all users to enable TOTP | Off | When on, users without TOTP must bind it during sign-in |

Administrators can see whether each user has bound TOTP and reset or disable it for them.

### Human Verification

| Setting | Default | Description |
| --- | --- | --- |
| Enable human verification | Off | Shows a click challenge on the sign-in page |

When enabled, users must complete a click challenge before signing in; a missing or expired challenge rejects the sign-in and the page asks the user to complete it again.

<Callout type="warn" title="This is the only CAPTCHA switch">
  The Security page has no failure threshold, validity window, or difficulty setting. Human verification is a supplementary anti-automation measure, not a substitute for lockout and TOTP: brute-force protection comes from the maximum attempts, lockout duration, and TOTP.
</Callout>

### Network Access Limits: Three Independent Switches

The Security page has three independent restriction switches, all on by default. Each can be turned off without affecting the others:

| Switch | Effect when off |
| --- | --- |
| Model endpoint allowlist | Saving or testing a model no longer checks whether its address is in the list |
| Outbound network allowlist | Custom HTTP tools, HTTP request nodes, URL imports, and database connections can reach internal addresses |
| Sandbox egress allowlist | Newly started code jobs can reach any network target |

Turning a switch off never clears its saved list: entries remain visible and editable, and enforcement resumes immediately when the switch is turned back on and saved.

#### Model Endpoint Allowlist

A model provider's request address must exactly match an entry (same scheme, hostname, and port; path is ignored). The list is preloaded with known providers such as OpenAI, Anthropic, DashScope, SiliconFlow, and local `http://localhost:11434`, and holds up to `200` entries.

Before saving or testing a model with a new address:

1. Go to **Settings** > **Security**.
2. Add the request address to the **Model endpoint allowlist**, one per line.
3. Enter only the scheme, hostname, and non-default port, for example `https://gateway.example.com` or `http://ollama.internal:11434`.
4. Save the security settings, then save or test the model again.

An address outside the list makes the model save or connection test fail with a message that the endpoint is not allowlisted. Removing an entry immediately blocks subsequent model discovery, connection tests, and chat requests; no restart is needed.

Prefer HTTPS for remote addresses. Use HTTP only for endpoints on a trusted private network, because API keys and model traffic are sent without transport encryption.

#### Outbound Network Allowlist (Internal Access Exemptions)

Clouisle denies internal, loopback, and cloud metadata addresses by default. These operations fail outright when the target is refused:

- Custom HTTP tools
- HTTP request nodes in workflows
- URL import and web page preview in Knowledge Bases
- Connection tests for database tools

To call an internal API, microservice, or database, add each approved target under **Settings** > **Security** > **Outbound network allowlist**:

| Entry form | Example | Matching rule |
| --- | --- | --- |
| Single IP | `192.168.1.50` | Exact address |
| CIDR range | `10.10.0.0/16` | Allowed when the resolved address falls in the range |
| Exact hostname | `api.internal.service` | Must contain a `.`; case-insensitive |
| Wildcard domain | `*.corp.internal` | All subdomains of the suffix, plus the base domain itself |

<Callout type="error" title="Targets that can never be allowlisted">
  Rejected on save: `*`, `0.0.0.0`, `::`, `169.254.169.254`, `metadata.google.internal`, and any range overlapping cloud metadata, multicast, or unspecified addresses (including `0.0.0.0/0` and `::/0`). Invalid entries produce an error instead of being ignored silently.
</Callout>

Other behavior:

- Up to `200` entries, duplicates removed automatically. A hostname without a `.` (such as `localhost`) cannot be an entry; use an IP or range instead.
- An empty list blocks every internal target.
- The check re-reads settings on every request, so changes take effect immediately without a restart.
- With the switch off, private, loopback, and cloud metadata targets are reachable; URL and port syntax checks still run, but they are not a security boundary. While it is off, these capabilities can be used to probe internal networks or read cloud instance credentials — narrow the allowlist instead of turning the switch off.

#### Sandbox Egress Allowlist

The sandbox egress allowlist is a separate policy from the outbound network allowlist above, and neither applies to the other: it only controls outbound traffic from programs inside the code sandbox.

- Accepts exact hostnames only, matched case-insensitively; wildcards, IP addresses, and ranges are rejected.
- Defaults to `pypi.org`, `files.pythonhosted.org`, `pypi.python.org`, `registry.npmjs.org`; up to `200` entries, duplicates removed.
- An empty list blocks all outbound traffic; only HTTPS on port `443` to allowlisted hosts is permitted.
- Custom package indexes must use HTTPS and their hostnames must be in the list.
- Changes apply to the next job without restarting services.
- Turning the switch off affects **new jobs only**; running jobs keep their policy, filesystem isolation and resource limits still apply, and the list is kept for re-enabling.

<Callout type="warn">
  With the sandbox egress allowlist off, sandbox code can reach any target, protocol, and port; node network policy still constrains what is actually reachable. See [Code Sandbox](../../concepts/sandbox.mdx) for details.
</Callout>

## Notification Settings

### Email (SMTP)

| Setting | Default | Description |
| --- | --- | --- |
| Enable SMTP | Off | Email is sent only after enabling and filling in the server details |
| Server / port | empty / `587` | Mail server address and port |
| Encryption | TLS | None, SSL, or TLS |
| Username / password | empty | Mail server credentials |
| From name / address | `Clouisle` / empty | Sender information recipients see |

To configure: go to **Settings** > **Integrations** > **Email**, fill in the server details, click **Test** to confirm a test email arrives, then click **Save changes**.

When SMTP is not configured or enabled, email notifications **silently stay in-app**: no error is raised and nothing is sent later.

### External Notification Channels

There are exactly three external notification channels: **email**, **Webhook**, and **Feishu**, configured under **Settings** > **Integrations**. The former DingTalk, WeCom, and Slack channels were removed; WeChat iLink is a messaging integration (Agent chat and knowledge collection), not a notification channel.

| Channel | Configuration | How to test |
| --- | --- | --- |
| Email | Mail server, sender, and credentials | The **Test** button on the integration page sends a test email |
| Webhook | URL, method, headers, body template, and signing secret | The **Test** button on the integration page |
| Feishu | The notification capability on the Feishu integration card, bot credentials, and test recipient | The test-message button on the card |

Feishu notifications are an explicit capability on the Feishu integration; enabling the integration alone does not send notifications. See [Feishu integration](../integrations/feishu.mdx).

### Automatic Notifications

**Automatic notifications** (**Settings** > **Notification channels**) controls which events create notifications and which external channels receive them. See [Notifications and External Channels](./notifications.mdx).

### Email Templates

<Callout type="note">Not implemented. There is no email template editor; notification bodies use built-in localized copy.</Callout>

## Notification Preferences

Notification delivery is configured globally by administrators; there are no per-user notification preferences. Regular users cannot choose which notifications they receive.

Users can view notifications in the notification center, mark one or all as read, and filter by type, level, scope, unread state, and keyword. Notification scopes are global, team, and specific users.

Administrators configure external channels under **Settings** > **Integrations** and choose event types under **Automatic notifications** on **Settings** > **Notification channels**. A channel sends only when selected in the global configuration and enabled/configured; otherwise notifications stay in-app. When volume is high, enable only the types you need to follow up on.

Available event types include team member and role changes, team model authorization changes, account activation/deactivation, administrator password resets, pending registrations, Knowledge Base document processing results, workflow failures, workflow approval waits, API key expiry warnings, anomalous sign-ins, account lockouts, and password changes.

## Memory Settings

The **Memory** page controls background memory extraction: content from user conversations is extracted into memories after a cooldown, or immediately when the pending-turn threshold is reached. The Agent itself must also enable memory; if either switch is off, nothing is extracted.

| Setting | Default | Description |
| --- | --- | --- |
| Enable background extraction | Off | Extraction outside conversations happens only when on |
| Extraction model | empty | When empty, falls back in order: the Agent's model → the system default chat model → the first available chat model |
| Cooldown | `180` seconds | `10-3600`, prevents frequent extraction |
| Pending-turn threshold | `6` | `1-50`, triggers extraction immediately when reached |

| Storage backend | Local | Local files or S3-compatible object storage |
| Knowledge Base single-file upload limit | `50MB` | `1-1024`; uploads over the limit are rejected |

### Object Storage (S3-Compatible)

After choosing object storage, fill in:

| Setting | Default | Description |
| --- | --- | --- |
| Endpoint | empty | Object storage service address |
| Bucket / region | empty | Target bucket and region |
| Access key / secret key | empty | Credentials stored server-side only |
| Path-style access | On | For services that do not support virtual-hosted bucket names |

### Audit Log Retention

| Setting | Default | Description |
| --- | --- | --- |
| Audit log retention | `365` days | `30-3650`; older logs can be archived |
| Archive file path | `/var/log/clouisle/audit_archives` | Local path where archive JSON files are written |

Administrators archive logs past the retention period manually; archived logs are deleted from the database. See [Audit log management](./audit-logs.mdx).

### Audit Alerts

The settings page has no working audit alert feature: no automatic detection of failed sign-ins or bulk deletions, and no alert delivery. For security alerts, use the security events and external channels in [Automatic notifications](./notifications.mdx).

## Parsing Settings

The **Parsing** page (`/site-settings/parsing`) controls whether images inside knowledge-base documents are sent to a vision or OCR model. The feature is off by default and only affects documents processed **after it is enabled**; existing documents are not reprocessed automatically.

| Setting | Default | Range | Description |
| --- | --- | --- | --- |
| Enable document image parsing | Off | On/off | When off, images are never sent to a model |
| Vision model | empty | Enabled image-input model | Produces text and visual descriptions; must be authorized for the document's team |
| OCR model | empty | Enabled image-input model | Text-only extraction; empty reuses the vision model |
| Fetch external images | Off | On/off | Whether to fetch image URLs referenced by documents, still subject to SSRF checks |
| Max images per document | `8` | `1-20` | Images beyond this are not analyzed |
| Max bytes per image | `10485760` | `1-52428800` | Larger images are rejected |
| Max pixels per image | `20000000` | `1-40000000` | Images above this are rejected |
| Concurrent image requests | `2` | `1-8` | Maximum simultaneous analysis requests per document |

- Enabling requires a vision model, an OCR model, or both; clearing the last model fails to save.
- Images go to the model provider, cost money, and may leave your deployment; confirm policy before processing sensitive documents.
- Results include OCR text and factual descriptions, written into chunks with page, slide, or sheet references; original images remain behind the protected file endpoint.

For the full flow, supported sources, and failure handling, see [Image and Scanned Document Parsing](../knowledge/image-understanding.mdx).

## Site Search

The built-in **Web Search** tool is configured once at the site level by administrators; teams and Agents no longer store their own search credentials.

1. Go to **Capabilities** in the admin console and find the built-in **Web Search** tool.
2. Click configure to open the site search dialog.
3. Select the search engines to enable, enter their credentials, and choose the default engine.
4. Click **Test** to confirm results come back, then save.

- Supported engines: Tavily, Bocha, SearXNG, and DeepSeek. There is no keyless engine, and no automatic failover to another provider when an engine fails.
- Engines are enabled or disabled individually at the site level; only enabled engines appear in tool configuration.
- Saved keys show only as configured and are never displayed again; leaving a field empty keeps the current value, while a new value replaces it.
- Disabling an engine makes tool calls using it fail immediately; switch the tool or Agent to another enabled engine.

Engine capabilities and limits: [Built-in tools](../tools/built-in.mdx).

## Integration Settings

Login identity sources, email, Webhook, Feishu, and WeChat iLink are managed under **Settings** > **Integrations**. Login integrations and built-in services are authorized separately: whoever manages sign-in owns SSO and login methods, while whoever manages built-in services owns email, Webhook, Feishu, WeChat iLink, and the delivery log.

### Global SSO Policy

Configure it in the SSO section of **Settings** > **Security**:

| Setting | Default | Description |
| --- | --- | --- |
| Enable SSO | Off | When on, the sign-in page shows buttons for enabled identity sources |
| Allow password sign-in | On | When off, only SSO works — confirm at least one identity source is usable first |
| Auto-create users | On | Creates an account on the first SSO sign-in |
| Require approval | Off | When on, auto-created accounts need administrator approval |
| Match existing accounts by email | On | When off, the same email is not linked to an existing account automatically |

### Login Integrations and Feishu Sign-in

Login integrations (OAuth2/OIDC, SAML2, CAS) are created and managed on the integration page. Feishu sign-in is an optional capability on the Feishu integration; the sign-in page shows the Feishu button only after you enable it explicitly. See [Configure single sign-on](./sso.mdx).

### Feishu Directory Sync

Under **Settings** > **Integrations** > **Feishu directory sync**, use the app's App ID and App Secret to import members of selected Feishu departments as Clouisle accounts. Sync is one-way: nothing is written back to Feishu, and departures or deactivations in Feishu do not deactivate local accounts.

1. Create a custom app in the Feishu developer console, grant directory read permissions, and add the departments to sync (including members) to the app's data scope; reading the root department requires the all-employee scope.
2. To read the company name, member ID, name, and email, grant `tenant:tenant:readonly`, `contact:user.employee_id:readonly`, `contact:user.base:readonly`, and `contact:user.email:readonly`.
3. Save the App ID and App Secret on the Feishu integration card, browse the department tree, and save the sync scope. The top-level **Company** node is the root department; selecting it means everyone. Other departments include themselves and descendants.
4. Click **Sync members of selected departments**. The result reports created, updated, and skipped accounts and new teams.

New accounts have no local password and use the default role and default team. Existing local accounts are not merged by email alone; repeated syncs match and update by Feishu member ID, and skip email conflicts.

When sync fails, check the Feishu error code shown on the card first:

| Feishu error | Meaning | Fix |
| --- | --- | --- |
| `41050` (no user authority) | Member is outside the app's directory data scope | Add the user or department to the data scope in Feishu, then retry |
| `40004` (no dept authority) | Department is outside the data scope | Add the department to the data scope |
| `40011` / `40012` | Invalid pagination parameters | Retry; contact support if it persists |
| Missing member ID reported | No permission to read member IDs | Add `contact:user.employee_id:readonly` |
| Secret cannot be decrypted | The site secret was changed | Save the App Secret again |

### Feishu Agent Chat

The **Agent chat** capability on the Feishu integration is an explicit switch; enabling the integration alone does not let the bot answer messages. Once the capability is on, the user has completed identity binding, and an Agent is published, users can chat with that Agent in Feishu.

Messages can be received in two ways:

- **HTTP callback**: point the Feishu event subscription at the callback address the site provides, and Feishu pushes messages.
- **Long connection**: choose long connection in the Feishu Agent chat configuration; the platform connects to Feishu, so no public callback address is needed.

The two modes can be used together. In personal settings, users can pause new messages, queuing, and unsent replies; pausing does not delete conversation history.

Feishu attachment limits: images `10 MiB`, MP4 `30 MiB`, other files `30 MiB`. See [Feishu integration](../integrations/feishu.mdx).

### Feishu Knowledge Sync

A Feishu Wiki space can sync to a chosen Knowledge Base on a schedule (only super administrators can configure it). Choose the source space and target Knowledge Base, set the interval (`1-43200` minutes), and click sync now at any time. Sync uses the app credentials saved in the Feishu integration.

### WeChat iLink

WeChat iLink is a single-instance integration with two platform switches: **Agent chat** and **knowledge collection**. Each person also authorizes via QR code; the platform switches and personal authorization are independent.

- Binding purpose can be none, knowledge collection, or a single published Agent — only one is active at a time.
- With the platform switch off, new messages, execution, and replies pause; existing connections, credentials, and pending records are kept, and processing resumes when it is turned back on.
- Knowledge collection saves WeChat content to a Knowledge Base and keeps each submission record and supported original files.

See [WeChat iLink integration](../integrations/wechat.mdx).

## Team Settings

Teams group users and resources (Agents, workflows, and Knowledge Bases). Team administrators manage **members** and **basic team information**; **model authorization can only be changed by a super administrator**.

### Accessing Team Management

There are two entry points with different permissions and capabilities:

| Entry | Location | Who can enter | What they can do |
| --- | --- | --- | --- |
| Admin team management | Team switcher → **Manage all teams (system admin)** | Administrators with team-view permission or super administrators | View, create, edit, and delete teams across teams; **only super administrators can change model authorization** |
| Team settings | Team switcher → **Manage current team** | Team administrators or owners | Manage the current team's members and basic information; view model authorization read-only |

Regular members and viewers do not see **Manage all teams** and can only open current-team settings; without team management permission, they cannot change members there either.

### Team Information

Only three fields are editable:

| Field | Description |
| --- | --- |
| **Name** | Team display name (required) |
| **Description** | Optional description (up to 500 characters) |
| **Avatar URL** | Optional avatar image URL |

There is no team slug or custom URL; teams are referenced by name in the interface.

### Model Authorization

**Only super administrators can change team model authorization.** Under **Manage current team** > **Model authorization**, team administrators and owners see a read-only view: authorized models, enabled state, and today's usage / quota progress. Super administrators assign quotas; `Unlimited` means no cap.

Only authorized models appear in the team's Agent and Knowledge Base model selectors. Contact a super administrator to add or adjust authorization.

### Member Management

Members must already have a Clouisle account; there is no email invitation or join-request flow.

**Add a member**

1. Open **Manage all teams** or **Manage current team** and select the team.
2. Open the **Members** tab.
3. Click **Add member**.
4. Select an existing user and a role (administrator, member, or viewer; owner cannot be assigned here).
5. Confirm.

**Change a member role**: choose **Change role** in the member list and pick the new role. Only the team owner can change another member's role.

**Remove a member**: click **Remove** and confirm. The owner cannot be removed or removed by another member.

**Leave a team**: confirm in **Members**. The owner must transfer ownership first.

**Transfer ownership**: confirm in **Members**. The previous owner becomes an administrator and the new owner gains full control.

### Team Roles

Roles are fixed: **Owner**, **Administrator**, **Member**, and **Viewer**. There are no per-team custom roles. See [Teams and members](./teams.mdx) and [Roles and permissions](./roles-permissions.mdx) for the full matrix.

### Not Implemented

These team-level features are not implemented: team slug / custom URL, team visibility and discovery, invitation approval and allowed email domains, member limits, team resource quotas, per-team password/2FA/session/IP policies, team APIs and rate limits, billing, data retention/export/deletion, audit alerts, custom domains, and branding.

## Feature Flags and Other Settings

<Callout type="note">The following are **not** configurable site settings:</Callout>

- Feature flags (enabling/disabling Agents, workflows, Knowledge Bases)
- Email templates
- Security headers, CORS, IP allowlists
- API rate limiting
- Maintenance mode
- Settings export/import and reset to defaults

## Key Defaults

A new site defaults to: site name `Clouisle`, centered authentication page, theme follows system, icon and name displayed, registration allowed, approval required, email verification on, human verification off, SSO off, password sign-in allowed, sessions `30` days, minimum password length `8`, lockout after `5` consecutive failures for `15` minutes, `50MB` Knowledge Base single-file upload, and audit log retention `365` days. All three network access limits are on by default.

## When Changes Take Effect

Page settings usually affect the public site and subsequent requests immediately after saving. Model endpoint, storage, and deployment-related settings are read by the server and take effect after restarting the relevant services according to your deployment. After saving, verify the sign-in and sign-up pages in an incognito window.

## Security Principles

- Sensitive credentials (email passwords, SSO client secrets, object storage keys, model API Keys) stay server-side and are never shown in the interface.
- All three network access limits default to on; confirm the blast radius before turning one off. The lists are retained and can be restored at any time.
- Model endpoints match on the full address; emptying the allowlist blocks every model request.
- The sandbox egress allowlist accepts exact hostnames only, and an empty list blocks all outbound traffic; it does not replace the outbound network allowlist.
- Before switching to SSO-only, confirm at least one identity source works and keep an administrator recovery path.
- Before changing audit log retention, confirm the archive path is on persistent storage and has backups.

See the [Site settings reference](../../../reference/site-settings.mdx) for field-level defaults and the complete list.
