Clouisle 的授权由**全局角色**和**团队门限**两层叠加决定。前端按权限隐藏菜单与按钮，后端会重新校验——「看不到入口」不是安全边界，绕过界面直接请求同样会被拒绝。

权限目录与内置角色矩阵见[权限与角色参考](../../../reference/permissions.mdx)；本页讲**怎么操作、谁有权限、失败时发生什么**。

## 权限模型

### 两层授权

- **全局角色**决定「能做什么」：能否进入管理台、能否创建 Agent、能否修改站点设置、能否导出审计日志。
- **团队门限**决定「在哪个团队、以什么级别做」：团队角色只有所有者、管理员、成员、观察者四种，本身不授予任何权限。

两层是「与」的关系。例如，一个用户即使拥有创建 Agent 的全局权限，也必须先属于某个团队才能在该团队创建；团队所有者也不会因为角色自动获得管理台权限。

### 检查顺序

带团队的请求按以下顺序校验，任何一步失败都会拒绝：

1. 团队是否存在。
2. 是否超级管理员——是则直接放行，不查角色和团队成员关系。
3. 是否该团队成员。
4. 该动作是否属于团队管理动作——是则要求在该团队内是所有者或管理员。
5. 如果在该团队内是观察者，只允许只读和使用类动作。
6. 全局角色是否包含所需权限。

失败时页面提示无权限、需要团队管理员或不是团队成员，而不是返回空数据。

### 权限分类

**管理台权限**覆盖管理后台的各功能：用户、角色、权限、团队、模型、能力（工具与 Skill）、知识库、站点设置、集成、会话、记忆、通知与审计日志。要进入管理台，至少要拥有管理台访问权限；之后每个页面再按各自的查看或修改权限拦截。

**资源权限**覆盖团队内的 Agent、工作流、知识库、工具、Skill、会话与记忆。资源权限通过全局角色授予，再叠加团队门限；API Key 例外，它按个人归属。

<Callout type="info">
  管理台里工具与 Skill 通过**能力**页面访问，没有独立的工具导航项。
</Callout>

## 内置角色

系统内置五个全局角色，不能改名、不能删除，权限集也不能修改。

| 角色 | 管理台访问 | 授权要点 |
| --- | --- | --- |
| **Super Admin** | 是，并绕过一切检查 | 拥有全部权限；首个注册用户自动成为 Super Admin |
| **Admin** | 是 | 管理台读写、团队内资源全套权限、集成只读与审计；**不能**创建或修改角色、修改站点设置、修改集成配置，也不能修改或删除记忆 |
| **Team Admin** | 否 | Member 的全部权限，另加修改团队信息和成员管理 |
| **Member** | 否 | 团队内创建、编辑、运行资源，管理自己的 API Key；不能删除团队、删除或发布 Agent、删除或发布工作流、删除工具 |
| **Viewer** | 否 | 只读与使用/执行；没有任何写权限，也没有 API Key 权限 |

### Super Admin

持有全部权限。系统第一个注册用户会被自动提升为 Super Admin。超级管理员在团队接口中直接放行，但仍需要有团队成员记录才会出现在成员列表里。

### Admin

可以管理全部团队与团队成员，但团队管理动作仍要求他在**该团队内**是所有者或管理员。Admin 是「日常运营」角色：能处理用户、团队、模型、能力、知识库、会话与审计，但不负责角色设计和站点级配置。

### Team Admin

权限等于 Member 加上修改团队信息与成员管理。启动时系统会给所有团队内角色为所有者或管理员的用户补授该角色。因此**把某人设为团队管理员前，他必须已经持有 Team Admin 角色**，否则会因缺少团队管理权限被拒绝。

### Member

在团队内创建、编辑和运行 Agent、工作流、知识库、工具与 Skill，可以管理自己的 API Key。注意：Member 即使拥有删除工具的权限项，实际删除仍要求团队管理员，操作会被拒绝。

### Viewer

只读角色，也是新用户的默认全局角色。可以查看团队、与 Agent 对话、运行工作流、检索知识库、执行工具与 Skill，但不能创建或修改任何资源，也不能管理 API Key。

<Callout type="warn" title="内置角色的权限由平台维护">
  平台每次启动都会把内置角色的权限集对齐到内置清单：手工加上的权限会被移除，缺少的会被补回。需要不同的权限组合时，请创建自定义角色。
</Callout>

## 两个操作界面

团队与角色相关的界面有两个，要求不同：

| 界面 | 位置 | 谁能进入 | 能做什么 |
| --- | --- | --- | --- |
| 管理台团队页 | 团队切换器 → **管理全部团队（系统后台）** | 有团队管理查看权限的管理员或超级管理员 | 列出全部团队、创建团队、修改团队、删除团队、批量删除 |
| 团队设置 | 团队切换器 → **管理当前团队** | 团队所有者或管理员 | 查看成员、添加成员、改变角色、移除成员、离开、转让所有权、查看已授权模型（只读）、修改团队信息 |

普通成员与观察者看不到**管理全部团队**，他们的团队入口只有**管理当前团队**，且普通成员在该页只能查看。**模型授权**标签对团队管理员是只读的，文案明确「由系统管理员分配」。

## 集成与投递记录权限

集成相关界面按域授权，登录域与内置服务域互相独立：

| 界面 | 谁能查看 | 谁能修改 |
| --- | --- | --- |
| 集成总览与登录身份源 | 拥有登录域或内置服务域任一查看权限 | 登录域由登录管理权限控制 |
| 邮件 / Webhook / 飞书 / 微信 iLink | 拥有内置服务查看权限 | 内置服务管理权限 |
| 消息投递记录 | 拥有内置服务查看权限 | 只读 |

- 全局 SSO 开关显示在**安全**页，但按登录域授权，不属于通用站点设置权限。
- 消息投递记录位于侧边栏 **Monitoring** 组，该组整体还要求管理台访问权限；只有投递记录查看权限而没有管理台权限的用户看不到入口，但直接访问页面地址仍会按该权限放行。
- 内置 Admin 角色能查看集成配置与投递记录，但不能修改——改配置需要 Super Admin 或带相应修改权限的自定义角色。

## 角色管理

管理台 **Roles** 页面列出全部角色。内置 Admin 角色只能查看角色，因此**只有 Super Admin（或带角色管理权限的自定义角色）能创建、修改、删除自定义角色**。

### 创建自定义角色

1. 以 Super Admin 登录，进入 **Admin** → **Roles**。
2. 点击 **Create Role**，填写**名称**（全局唯一）与**描述**。
3. 在权限列表中按分类勾选权限。
4. 保存。

自定义角色是全局角色，可以指派给任意用户，与团队归属无关。名称重复会提示角色已存在。

**示例：** 内容管理员——只需要团队查看、知识库管理与 Agent 对话权限，不进入管理台。

<Callout type="warn">
  创建角色时勾选不存在的权限会被静默忽略；之后替换权限集时，未知权限会报错。两者行为不同，排错时注意。
</Callout>

### 编辑角色

可以修改自定义角色的名称与描述，也可以**整体替换**权限集——保存时提交的是完整列表，不是增量。内置角色不允许改名、改描述或改权限。

### 删除角色

删除角色有两条硬性限制：

- 内置角色不能删除。
- 仍有用户持有该角色时不能删除，页面会提示还有多少用户在使用。

<Callout type="error">
  删除角色**没有**「把用户迁移到其他角色」的选项。要删一个正在使用的自定义角色，必须先去 **Admin** → **Users** 逐个用户的编辑面板里改掉该角色，再回来删除。列表页支持勾选多个自定义角色批量删除。
</Callout>

### 自定义权限

权限目录本身也可以在 **Permissions** 页面维护，需要权限查看权限；创建、修改、删除还分别需要对应权限。

系统内置权限不能修改或删除；自定义权限的标识重复时会提示已存在。

<Callout type="warn">
  新建的自定义权限只是一个数据记录：除非平台某处正好检查这个权限，否则给角色勾选它不会解锁任何功能。
</Callout>

## 用户权限

### 查看用户权限

**Admin** → **Users** 打开用户列表。用户详情/编辑面板展示：

- 用户拥有的**全局角色**（多选）
- 团队归属与团队内角色（在团队页维护）
- 登录方式、账号状态与是否超级管理员

没有「有效权限聚合视图」：实际权限是全部全局角色的并集再叠加团队门限，需要人工对照[权限与角色参考](../../../reference/permissions.mdx)判断。

### 变更用户全局角色

1. **Admin** → **Users**，点击目标用户的 **Edit**。
2. 在 **Role** 区域勾选或取消角色（可多选）。
3. 保存。

保存时**整体替换**角色列表：未列出的角色会丢失；匹配不到的角色名被忽略。

<Callout type="warn">
  **保护规则：** 如果该用户仍是某些团队的所有者或管理员，而新角色不再包含团队管理权限，保存会被拒绝。要摘掉团队管理员的权限，必须先把他在所有团队的成员角色降级。
</Callout>

角色变更立即对后续请求生效，已登录的会话不会被踢下线，但下一个受限操作就会被拒绝。

创建用户时**不能**指定角色：新用户没有任何全局角色，需要创建后单独指派。

## 团队权限

### 团队角色是门限，不是授权

团队角色只有四个固定值：所有者、管理员、成员、观察者。它不携带任何权限，只回答两个问题：这个人是不是这个团队的成员；他的级别够不够做管理动作。

团队管理动作（修改团队信息、成员管理、删除团队、删除工具）要求同时具备全局权限**且**在该团队内是所有者或管理员。

### 团队角色与典型组合

实际能力 = 全局角色权限 ∩ 团队门限。以下是最常见组合（假设成员已被授予对应全局角色）：

| 能力 | 所有者 + Team Admin | 管理员 + Team Admin | 成员 + Member | 观察者 + Viewer |
| --- | :-: | :-: | :-: | :-: |
| 查看团队与成员 | ✓ | ✓ | ✓ | ✓ |
| 改团队信息（名称/描述/头像） | ✓ | ✓ | ✗ | ✗ |
| 添加成员 | ✓ | ✓ | ✗ | ✗ |
| 改变成员角色 | ✓ | ✗ | ✗ | ✗ |
| 移除成员 | ✓ | ✓（不能动其他管理员或所有者） | ✗ | ✗ |
| 转让所有权 | ✓ | ✗ | ✗ | ✗ |
| 删除团队 | ✗（须在管理台操作） | ✗ | ✗ | ✗ |
| 创建/编辑 Agent、工作流、知识库 | ✓ | ✓ | ✓ | ✗ |
| 删除 Agent、发布 Agent 与工作流 | ✓ | ✓ | ✗ | ✗ |
| 与 Agent 对话、运行工作流 | ✓ | ✓ | ✓ | ✓ |
| 创建/编辑自己的工具与 Skill | ✓ | ✓ | ✓ | ✗ |
| 编辑他人的工具/Skill | ✓ | ✓ | ✗ | ✗ |
| 删除工具 | ✓ | ✓ | ✗（团队门限拒绝） | ✗ |
| 检索/测试知识库、上传/删除文档 | ✓ | ✓ | ✓ | 只读检索 |
| 执行工具与 Skill | ✓ | ✓ | ✓ | ✓ |
| 管理 API Key | 只能管理自己的 | 只能管理自己的 | 只能管理自己的 | ✗ |
| 查看审计日志 / 管理台 | 需额外全局权限 | 同左 | ✗ | ✗ |

团队内观察者与全局 Viewer 角色是两件事：前者只是「在这个团队里级别最低」，不会自动获得全局 Viewer 权限；反之把全局 Viewer 加进团队时，建议同时设为观察者。

<Callout type="warn" title="API Key 不是团队资源">
  API Key 归属个人：非超级管理员只能看到和管理自己的 Key，团队所有者或管理员**看不到也撤销不了**别人的 Key。「查看所有 API Key」只有超级管理员能做到。
</Callout>

团队管理动作的完整约束见[团队与成员](./teams.mdx)。

### 资源可见性

除了两层门限，资源自身的可见性也会拦截：

| 可见性 | 谁能查看 | 谁能修改或删除 |
| --- | --- | --- |
| 团队 | 团队成员 | 创建者或团队所有者/管理员 |
| 私有 | 仅创建者（创建者缺失时为团队所有者/管理员） | 创建者（创建者缺失时为团队所有者/管理员） |

Agent 与工作流的规则一致。其他团队即使知道资源地址，也无法查看或调用。

### 共享资源

跨团队共享覆盖**工具**与**知识库**：

- 自定义工具可以由所属团队的管理员共享给其他团队，接收团队在「共享给我」中查看，权限分为只读与可查看执行结果两档。
- 知识库可以由所属团队的管理员以**只读**方式共享给其他团队；接收团队可以查看和检索，不能修改。
- 私有资源不能共享，也不能共享给本团队；共享是单向的，由所属团队建立和撤销。
- Agent、工作流没有「按团队逐个授权」的共享层级：跨团队可见性由资源自身的可见性决定，其余情况默认团队隔离。

## API Key 归属

API Key 按用户归属，可设置过期时间、绑定指定 Agent 与工作流，并在页面或个人设置中管理。界面上可以填写每分钟请求上限与作用域，但当前版本不会实际限流，也不会据此收窄权限——不要把它们当成生效的安全措施。Key 的访问仍受绑定对象与团队隔离约束，详见 [API Key 参考](../../../reference/api-keys.mdx)。

## 权限审计

没有专门的权限变更审计视图，审计日志也没有「授权」或「撤销」动作类型。当前覆盖范围：

| 有审计日志 | 无审计日志 |
| --- | --- |
| 用户的创建、更新、删除、启用、停用、强制改密 | **角色的新增、修改、删除** |
| 团队的创建、更新、删除、成员添加与移除、所有权转让 | **权限的新增、修改、删除** |
| 团队模型授权与批量授权/撤销 | **成员角色变更、离开团队** |

审计日志在 **Audit Logs** 页面按资源与操作筛选查看，需要审计日志查看权限。详见[审计日志](./audit-logs.mdx)。

## 排查 403

### 权限被拒绝

**症状：** 功能不可用，页面提示无权限、需要团队管理员或不是团队成员。

按顺序排查：

1. **全局权限是否缺失？** 在 **Admin** → **Users** 编辑用户，看角色里有没有包含目标能力的角色（对照[权限参考](../../../reference/permissions.mdx)）。错误提示通常会指出缺少哪一项权限。
2. **团队门限是否不够？** 属于团队管理动作时，必须是团队所有者或管理员；团队观察者做写操作一定会被拒。
3. **是不是团队成员？** 「不是团队成员」表示该用户根本不在这个团队里。
4. **资源是否私有？** 私有资源对非创建者返回无权限，与角色权限无关。
5. **是不是别人的 API Key？** Key 只能由本人或超级管理员读写。

### 过度授权的用户

1. 在 **Users** 里查看目标用户的角色，对照[权限参考](../../../reference/permissions.mdx)逐条核对。
2. 在 **Roles** 里查看每个角色的权限集——内置 Admin 已覆盖全部团队资源，通常没必要再叠加宽权限的自定义角色。
3. 降级前先检查该用户是否仍是某些团队的所有者或管理员，否则角色保存会被保护规则拒绝。
4. 定期复核。角色变更不写审计日志，改角色时请自行留痕。

### 权限行为不一致

1. **确认检查层**：团队内请求是「全局权限 + 团队门限」两层；只有管理台接口才看管理台权限。
2. **确认角色来源**：用户可能有多个角色，权限取并集；也可能在启动时被补授 Team Admin。
3. **确认内置角色不能手改**：内置角色的权限集每次启动都会恢复。

## 最佳实践

**推荐：**

- 用自定义角色承载岗位权限，不用「多给几个内置角色」凑能力。
- 团队管理员先授予 Team Admin 全局角色，再在团队内设为管理员（顺序反了会被拒绝）。
- 团队只读人员同时使用团队观察者和全局 Viewer。
- API Key 按集成单独创建、单独轮换，不要共用个人账号的 Key。
- 每季度复核角色成员与团队所有者/管理员名单。

**避免：**

- 直接把 Super Admin 当日常账号使用。
- 试图修改内置角色的权限。
- 依赖「前端看不到按钮」当作安全边界。
- 用一个共享账户跑多个集成。

## 保护规则

- 五个内置角色与内置权限不可删除、不可改名，权限集也不可修改。
- 删除自定义角色前必须先解除指派。
- 超级管理员账户不能删除，也不能停用。
- 默认团队不能删除；团队所有者不能离开或被移除，必须先行转让所有权。
- 权限变更对后续请求立即生效，已登录会话不缓存权限。
