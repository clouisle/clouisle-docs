On the knowledge base detail page, select **Upload documents** to upload local files, or **Import URL** to add a web page or YouTube URL. Uploading only stores the file and creates a **Pending** record; you **must then process it** before it is parsed, chunked, embedded, and searchable.

## Supported Formats

| Type | Extensions | Parsing |
| --- | --- | --- |
| PDF | `.pdf` | Document converter → Markdown text |
| Word | `.docx`, `.doc` | Document converter → Markdown text |
| Excel | `.xlsx`, `.xls` | Document converter → Markdown text |
| PowerPoint | `.pptx` | Document converter → Markdown text |
| Plain text | `.txt` | Decoded as UTF-8 |
| Markdown | `.md`, `.markdown` | Decoded as UTF-8 and chunked by Markdown structure |
| HTML | `.html`, `.htm` | Document converter → Markdown text |
| CSV | `.csv` | Structured extraction |
| JSON | `.json` | Structured extraction |
| Web page | `url` | Fetched server-side |

<Callout type="warn" title="Unsupported cases">
  Legacy `.ppt`, XML, archives (ZIP/TAR/GZ), and folder uploads are unsupported, and scans or images require site image parsing — a PDF containing only images extracts nothing and fails processing when parsing is disabled.
</Callout>

Markdown files (and documents that keep Markdown structure after conversion) skip recursive character splitting and are **chunked by structural blocks**: level 1-2 headings force a split, oversized tables split by row with the header repeated, and code blocks stay intact or get a closing fence, with each chunk recording its section and type. See [Chunking and document processing](./chunking.mdx) for details and tunable parameters.

## Upload Files

1. On the knowledge base detail page, select **Upload documents**.
2. Drag files into the dialog, or click to choose files (multi-select supported).
3. The UI validates extension and size per file and immediately removes invalid files with an error.
4. Click **Upload** and watch the progress.
5. Each file becomes a document with **Pending** status.

The UI check is only for early feedback; **the server validates again**. Oversized files report “file too large” and unsupported formats report “unsupported type”.

## Upload Limits

- The default per-file limit is **`50MB`**, controlled by the site's document upload limit and adjustable from `1-1024MB`.
- The upload dialog reads that site setting and shows the current value (`Max file size: 50MB`), so refresh the page after an administrator changes it.
- The limit is **per file**: you can select multiple files, but each counts and creates a document independently.
- ZIP uploads are unsupported, and there is no per-knowledge-base storage quota; storage usage is observed at the team level.

## Status and Processing Stages

```text
Upload/import → Extract text → Clean → Chunk → Generate embeddings → Build full-text index → Completed
```

| Status | Meaning | What you can do |
| --- | --- | --- |
| **Pending** | File saved, awaiting processing | Preview chunks, start processing, quick process, delete |
| **Processing** | Extracting, chunking, embedding, or indexing | Wait for completion; progress is visible |
| **Completed** | Indexed and searchable | Hit testing, edit chunks, reprocess |
| **Failed** | Processing failed with an error message | View the error, retry failed chunks, reprocess |

There are three processing modes:

- **Quick process**: process with the knowledge base (or document) chunk settings as-is, without preview.
- **Start processing** (preview page): confirm or even edit chunks with **Preview chunks**, then submit them for embedding.
- **Bulk processing**: select several documents in the table and use the selection toolbar to **Quick process** pending ones.

### Batch preview and completion notifications

When you confirm several documents on the bulk preview page, the UI submits them in batches; when the whole batch finishes, **one aggregated notification** is sent instead of one per document.

- All succeeded sends an indexing-complete notice; all failed sends a failure notice.
- Partial success prefers the failure notice and states how many succeeded and failed; if only indexing notices are enabled site-wide, it falls back to the indexing notice.
- Single uploads and single-document processing still notify per document. Notification types are controlled by the switches under **Site settings → Automatic notifications**; with them off, nothing is sent.

<Callout type="warn">
  Upload and processing are separate stages. A document in the list is not necessarily embedded; only **Completed** documents are suitable for referencing in an Agent and only they are searchable.
</Callout>

## Import from a URL

1. On the knowledge base detail page, select **Import URL**.
2. Enter a full `http://` or `https://` address and a document name (`1-255` characters). The UI marks the name optional, but submitting it blank is rejected with a validation error, so fill it in.
3. Click **Import** — the system first runs a security check on the target (rejecting private networks, loopback, and cloud metadata addresses), then creates a URL document and opens the preview page.
4. Generate the chunk preview and submit for processing: the URL content is fetched server-side at that point, so **importing does not start processing automatically**.

If import fails (unreachable address, empty content, parse failure), the document keeps the error message; view the source URL or delete it and retry.

## Import from WeChat Collection

Besides manual upload and URL import, a personal WeChat account can collect messages straight into a knowledge base: scan the QR code under **Personal settings → WeChat iLink**, set the purpose to **Knowledge collection**, and pick an active, writable (not read-only shared) target knowledge base. Text, links, files, images, voice, and video you send are then parsed by type and automatically turned into documents and indexed. See [WeChat iLink integration](../integrations/wechat.mdx) for setup, supported content, and limits.

Unlike manual upload, collection creates documents and starts processing and indexing automatically — no extra “process” click and no “preview chunks” step; failures are reported back to WeChat with a failed status. A few boundaries:

- **Where originals are stored**: supported attachment originals are kept as protected files of that knowledge base with **no public address**; only the submitter or someone with access to the knowledge base can download them.
- **Size limits**: each attachment takes the smaller of the knowledge base upload limit (`50MB` by default) and **100MB**; audio/video must be at most 30 minutes.
- **Deduplication**: duplicate content within the same knowledge base is detected and the completed document reused, with that submission marked as a duplicate (submission records are still kept).
- **Failure messages**: blocked article bodies, unsupported content types, and similar cases are reported explicitly in WeChat, never silently dropped.

## Failures and Retries

| Symptom | Common cause | Fix |
| --- | --- | --- |
| File too large | Exceeds the site limit | Compress the file or ask an administrator to raise the limit |
| Unsupported type | Extension or content type not in the list | Convert the format |
| Extraction failed | Corrupt, encrypted, or image-only file | Re-export or remove the password and re-upload |
| All/partial embedding failures | Model credentials, quota, or dimension mismatch | Check model authorization and dimension, then **retry failed chunks** |
| Full-text index unavailable | Retrieval service problem | Ask an administrator to check the service |

**Retry failed chunks** is only available for a **Failed** document that has failed chunks; if the source text is fine (for example a temporary model outage), it costs less than reprocessing because successful chunks are kept.
