Chunking sets the granularity of knowledge base retrieval: chunks that are too large mix irrelevant text into results and eat the context budget; chunks that are too small lack complete meaning, so a hit still does not answer the question. **Preview first, then process** — do not enlarge chunks or overlap without verifying the result.

## Chunks Are Counted in Characters

**Chunk size** and **chunk overlap** are both measured in **characters**. The token count shown in the UI is a rough estimate for judging context budget and does not affect cutting. Chinese and English mix at very different ratios, so leave headroom when tuning by token count.

| Parameter | Default | Minimum | Suggested UI maximum | Description |
| --- | --- | --- | --- | --- |
| Chunk size | `1000` characters | `100` | `2000` | Target length of a chunk |
| Chunk overlap | `100` characters | `0` | `500` | Context kept between adjacent chunks |
| Custom separator | Empty | — | — | Accepts escape sequences, see below |
| Text cleaning | On | — | — | Turn off to keep original formatting |

## Markdown and Plain Text Take Different Paths

The system first decides whether the text contains Markdown structure (headings, code fences, tables, and lists are the main signals), then chooses a strategy:

- **Markdown mode**: split by structural blocks (headings, tables, code blocks, lists, paragraphs). Small tables stay intact, list items are not torn apart, and unclosed code fences are closed automatically. Each chunk records its section (such as `Chapter 1 > Section 2`) and type (table or code) so you can trace its source.
- **Plain-text mode**: try default separators in order — paragraph blank lines, newlines, Chinese full stop, exclamation mark, question mark, English sentence ends, semicolons, commas, spaces — and only then split by single characters.

### Structural boundaries and overlap

The Markdown path is stricter than plain text; learn these boundaries before tuning:

- **Level 1-2 headings are hard chunk boundaries**: if the current chunk has content, a level 1 or 2 heading ends it; level 3 and deeper headings do not force a break, they only update the section.
- **Oversized tables split by row**: a table larger than the chunk size is split row by row, with **the header repeated in every segment**, so a retrieved continuation is still readable.
- **Oversized code blocks split recursively**: code blocks stay intact; when over the limit they are split further, and each segment gets the language marker and a closing fence so no half fence appears.
- **No character overlap for tables and code blocks**: exact character overlap is applied only between adjacent text/list chunks; if either side is a table or code, no overlap text is prepended, preventing table rows or code from being cut into context.
- **Only tables and code carry a type marker**: plain text and list chunks have no type, so do not expect to filter list chunks by “list”.

<Callout type="info" title="Overlap is an exact character count">
  Chunk overlap is an **exact character count**, not an estimate by sentence or paragraph. Chinese sentences are often longer than the overlap value, so sentence-based overlap would exceed what you asked for; exact character overlap guarantees the length you set.
</Callout>

### A custom separator is a hard cut boundary

If you set the separator to something like `\n\n` or `---`, the system first splits the source at that separator, then splits each part further. Even text that would fit in one chunk is cut at the separator — this is the main difference from “default separators”, which only apply when long text must be shortened.

Escape sequences `\n`, `\r`, `\t`, and `\\` in the input are restored to real newlines, tabs, and backslashes, so you can type `\n\n` directly.

## Preview

Choose **Preview chunks** from the document actions (or open the bulk preview page from pending documents) and configure chunk size, overlap, custom separator, and **text cleaning**. The preview really reads and parses the document but writes nothing to the index.

The preview shows an overview (chunks / total tokens / total characters) and, for each chunk, its index, content, token count, character count, and overlap length; the overlapping prefix is highlighted in yellow so you can confirm the overlap lands sensibly. You can also edit or delete individual chunks right there.

<Callout type="warn" title="Text cleaning collapses blank lines">
  **Text cleaning** is on by default: it collapses consecutive blank lines into a single newline, squeezes extra spaces, and trims each line. For Markdown that uses blank lines to separate paragraphs, this changes chunk boundaries. If the structure depends on blank lines, turn text cleaning off in the preview and compare.
</Callout>

## Processing

There are two ways to start a pending document, differing in whether your confirmed chunks are used:

| Action | Behavior | When to use |
| --- | --- | --- |
| **Start processing** (preview page) | Submits **the chunks currently in the preview exactly as they are** and generates embeddings and the full-text index server-side | You have checked or edited the preview chunks |
| **Quick process** | Re-extracts and re-chunks using document metadata or knowledge base settings | Clean content with trusted defaults |

Processing runs in the background: extract text → clean → chunk → generate embeddings → build the full-text index. When it finishes, the document becomes **Completed**, and chunk and token counts are updated for the document and for the knowledge base totals.

Effective chunk settings follow this priority: **document-level settings (submitted with the preview/process) > knowledge base settings > built-in defaults `1000`/`100`**.

## Reprocessing and Rechunking

Both replace existing chunks, but differ in entry point:

- **Reprocess** (UI): chunk settings on a processed document are read-only, and the UI tells you to **reprocess**. It cancels running work, deletes old chunks and their vectors, clears counts, and runs the flow again from the preview with the new settings. **Every manually edited chunk is lost.**
- **Rechunk** (submitted programmatically): same semantics as reprocessing, submitting a new chunk size, overlap, and separator directly; it is rejected while the document is processing.

<Callout type="error" title="Confirm before reprocessing">
  Reprocessing cannot be undone: old chunks, old vectors, and all manual edits are replaced. A document is not fully searchable while processing; large batches consume background processing capacity, so process in batches.
</Callout>

## Editing Chunks

On the document detail or preview page you can edit chunk content, add a chunk after it, or delete chunks:

- Chunk content **cannot be empty**.
- Saving **strips HTML tags** (XSS prevention), so pasted raw HTML such as `<div>` keeps only its text; Markdown syntax (`**bold**`, tables, fenced code) is unaffected.
- Saving recomputes the chunk's token count and corrects the document's and knowledge base's token statistics.
- Saving regenerates that chunk's embedding and updates the full-text index; if either step fails, the content is rolled back and the failure reported.
- If a single chunk fails to embed, use **Retry this chunk**; if the whole document fails, use **Retry failed chunks**.

## Handling Failures

| Symptom | Possible cause | Fix |
| --- | --- | --- |
| Text extraction failed | Corrupt, encrypted, image-only (no OCR), or unsupported format | Convert or re-export and re-upload |
| Zero chunks | Extraction produced empty or whitespace-only text | Confirm the file has extractable text |
| Partial/all embedding failures | Embedding model credentials, quota, or dimension mismatch | Check model authorization and vector dimension, then **retry failed chunks** |
| Full-text recall unavailable | Retrieval service problem | Ask an administrator to check the service and confirm documents are completed |
| Jobs pile up and never finish | Insufficient background processing capacity | Ask an administrator to check background processing status and logs |

**Retry failed chunks** is only available when the document is **Failed** and really has failed chunks.
