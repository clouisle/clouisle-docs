**Hit testing** (the retrieval lab) runs real retrieval without touching production configuration and shows intermediate results for recall, fusion, reranking, and final ranking. Use it to verify whether chunking changes, mode switches, or parameter changes actually improve recall. Entry: knowledge base detail → **Hit testing** (requires permission to view the knowledge base and run retrieval tests).

## Retrieval Modes

| Mode | Channel | Default on a request | Default in knowledge base settings | Use for |
| --- | --- | --- | --- | --- |
| **Vector** | Semantic similarity (needs an embedding model) | — | Empty | Questions phrased differently from the source |
| **Full-text** | Keyword matching | — | Empty | Proper nouns, IDs, error codes, exact strings |
| **Hybrid** | Both channels, then merged ranking | **Hybrid** | Empty | General recommendation |

There are two layers of defaults: a **retrieval request** with no mode runs hybrid; the **knowledge base setting** is empty by default and only becomes the default mode for Agent/workflow retrieval once set explicitly. Field definitions are in the [Knowledge base settings reference](/en/reference/knowledge-settings).

## Where Hybrid Retrieval Is Available

Site administrators control hybrid availability: it may be on for all teams, off entirely, or rolled out per team (some teams on). The default is per-team rollout at full coverage.

- A team outside the rollout gets **pure vector results** even when it requests hybrid, and the UI does not label this as a downgrade; a degradation reason appears only when one channel fails.
- If “hybrid is selected but no keyword hits come back”, first ask an administrator whether the team is in the rollout, then check whether the degradation reason points at the vector channel failing.
- If the site retrieval settings cannot be read, hybrid is treated as on, so a configuration fault never takes retrieval down.

## Parameter Reference

The hit-testing panel can override the following (all optional):

| Parameter | UI default | Range | Description |
| --- | --- | --- | --- |
| Query | — | `1-1000` characters | Matched as-is; no boolean operators, wildcards, or field syntax |
| Retrieval mode | Hybrid | Vector / Full-text / Hybrid | See the table above |
| Result count | `5` | `1-20` | Number of results (knowledge base settings allow `1-100`) |
| Similarity threshold | `0` | `0-1` | Filters vector hits below this similarity |
| Reranking | On | On/off | Overrides knowledge base settings |
| Rerank candidates | `10` | `1-100` | Candidates sent to the reranker; the UI uses the larger of result count and this value |
| Rerank score threshold | Empty (disabled) | `0-1` | Filters results below this rerank score |
| Document scope | Empty | Document list | Search only within selected documents; currently the only retrieval filter |

<Callout type="info" title="Reranking requires a bound model">
  If the knowledge base has no rerank model bound, the UI does not send rerank parameters and the **Reranking** switch has no effect. Once bound, the knowledge base's rerank switch (on by default) and candidate count (default `10`) apply automatically, and request parameters override them only when you fill them in.
</Callout>

## How the Two Channels Merge

- **Hybrid mode**: vector and full-text results merge into one ranking by their respective ranks, with higher-ranked candidates first. Merging only happens when both channels succeed; if one fails, a degradation reason is returned.
- **Across knowledge bases**: when an Agent/workflow attaches several knowledge bases, each recalls concurrently with its own settings, all candidates go into one pool, and the pool is ranked globally rather than concatenating per-base rankings. The pool is then truncated to the candidate pool size (the larger of result count and rerank candidates).
- **One global rerank**: cross-base reranking is performed once by **the first active knowledge base in order that has a rerank model bound**, whose candidate count and score threshold define the pool and filtering. If reranking fails, the whole retrieval fails rather than returning unreranked fusion results.

## Follow-Up Query Rewriting

Agents in **Auto** mode rewrite follow-up questions that contain references into standalone queries before recall:

- Only Auto mode does this; Agentic mode and direct hit testing never rewrite.
- It triggers only for short follow-ups that contain a referring expression (“it”, “this”, “the above”); ordinary questions do not cost an extra model call.
- If rewriting fails (timeout, invalid output, missing model), the original query is used and retrieval still succeeds.

## A/B Comparison

**A/B comparison** runs the same query with two configurations side by side:

1. Configure sides A and B independently (mode, result count, thresholds, rerank parameters).
2. Results come back **independently per configuration**: a failure on one side never hides the other side's success, and the failing side reports its own reason.
3. The result panel shows both rankings, the number of overlapping results (`Overlap: N/total`), and per-stage scores.

## Reading Results and Diagnostics

Each result annotates its per-stage values so you can tell what decided the final order:

| Metric | Meaning |
| --- | --- |
| Vector score / rank | Similarity and rank from the vector channel (empty means the chunk was not vector-recalled) |
| Full-text score / rank | Keyword score and rank from the full-text channel (no fixed upper bound) |
| Fusion score / rank | Score and rank after merging both channels |
| Rerank score / rank / reason | Pairwise score from the rerank model (`0-1`) and its reason |
| Final ordering basis | Vector, full-text, fusion, or rerank |
| Degradation reason | Explanation when one channel failed but the other still returned results |

**Stage timings** break down into recall, rerank, context assembly, and total, so you can see whether recall or reranking is slow.

**Diagnostics** explain actionable causes:

| Diagnostic | Meaning | What to do |
| --- | --- | --- |
| Knowledge base not active | The knowledge base is not active | Activate it |
| Missing embedding model | Vector mode without an embedding model | Bind an authorized embedding model |
| Recall timeout | The recall stage timed out | Lower the result count, narrow the scope, or ask an administrator to check retrieval load |
| Recall failed | Recall, fusion, or rerank failed | Use the reported stage and category |

On failure, the UI reports the failure category and stage:

| Category | Typical cause | What to do |
| --- | --- | --- |
| Configuration mismatch | Embedding dimension differs from the index | Check the model and dimension; rebuild the index after switching models |
| Invalid model credentials | Provider credentials are wrong | Check the provider key and access |
| Quota or rate limit | Quota exhausted or throttled | Check the quota and retry later |
| Model configuration error | Model missing, disabled, or incompatible | Choose or enable a compatible model |
| Full-text unavailable | The full-text index is broken | Ask an administrator to check retrieval and confirm documents finished processing |
| Provider unavailable | Upstream service problem | Retry; if it persists, check the provider status |
| Unknown error | Anything else | Retry or ask an administrator to check logs |

## Apply to Production

You can save the hit-testing panel configuration as a **local preset** (stored in the browser, not synced across devices), then select **Apply to production** to write side A back to knowledge base settings: retrieval mode, result count, similarity threshold, rerank switch, rerank candidates, and rerank score threshold.

Before applying:

- The embedding model and index dimension must be unchanged (rebuild the index first otherwise).
- The knowledge base should actually be used by Agents/workflows — you are writing **knowledge-base-level** defaults, and a per-attachment result count, threshold, or mode still overrides them.

<Callout type="info" title="Not implemented / roadmap">
  Adjacent-chunk expansion exists in the retrieval service but is **not exposed in the retrieval UI or public API**: the request rejects the parameter and ignores it. Query analysis, retrieval history, and result export are unavailable too.
</Callout>

## Troubleshooting

| Symptom | Check first |
| --- | --- |
| Hybrid returns only keyword results | Whether the team is in the hybrid rollout; whether the degradation reason points at the vector channel |
| Hit testing returns 0 results | Whether documents are Completed; whether the similarity threshold is too high; switch to full-text to verify the keywords exist |
| “Dimension mismatch” | Whether the embedding model was changed; whether the vector dimension matches the index |
| “Full-text unavailable” | Retrieval service status; whether documents finished full-text indexing |
| Reranking has no effect | Whether a rerank model is bound; whether reranking is on; whether candidates are fewer than the result count |
| Results differ from production | Hit testing runs with request parameters, while production also applies the Agent's result count and mode plus the hybrid rollout |

See the [Knowledge base settings reference](/en/reference/knowledge-settings) for common failures and recovery steps, and [Knowledge base optimization](/en/usage/best-practices/kb-optimization) for tuning trade-offs.
