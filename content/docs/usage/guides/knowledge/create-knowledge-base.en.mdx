A knowledge base belongs to a team. Two creation choices are hard to reverse: **the embedding model fixes the vector dimension** (it cannot be changed after documents are processed), and **visibility decides who can read it without sharing**. Names must be unique within the team.

<Callout type="info" title="Prerequisites">
  1) You are a member of the target team and have permission to create knowledge bases; 2) the team has an authorized embedding model (creation is rejected without one, and without a usable model the knowledge base cannot be searched); 3) authorize a rerank model if you want reranking. See [Model management](../models/manage-models.mdx) for authorization and providers.
</Callout>

## Permissions and Visibility

| Action | Who can do it |
| --- | --- |
| View knowledge bases / documents / chunks | Team members matching the visibility rule |
| Hit testing (retrieval) | Anyone with view permission |
| Create a knowledge base | Team members |
| Edit settings, upload/process/delete documents, edit chunks | The creator or a team administrator |
| Delete a knowledge base | Team administrators |
| Share with other teams / revoke sharing | Administrators of the owning team |

Visibility is set in the create/edit dialog:

| Visibility | Who can read | Notes |
| --- | --- | --- |
| **Private** | The creator only | Other team members cannot see it, and it **cannot be shared** with other teams |
| **Team** | Every member of the team | Writes still require the creator or a team administrator |
| Public | Reserved value | Not offered in the UI; kept for compatibility |

Cross-team access is only possible through sharing and is always read-only — see “Cross-team sharing (read-only)” below.

## Knowledge Base List

In the admin console, **Knowledge bases** shows a cross-team table:

| Column | Description |
| --- | --- |
| **Name** | Knowledge base name, with the description as a second line |
| **Team** | Owning team |
| **Documents** | Total documents |
| **Chunks** | Total chunks |
| **Status** | Current status |
| **Created** | Creation time |

The table also has row selection and per-row actions. The list only offers the **Active ↔ Archived** status toggle; the status filter only has **Active** and **Archived**.

The list can also be filtered by team, name keyword, and status; teams that receive shares can choose to see only their own knowledge bases.

## Create a Knowledge Base

1. Go to **Knowledge bases** and select **Create knowledge base**.
2. Fill in the basics:
   - **Name**: `1-100` characters, **unique within the team**; duplicates are rejected.
   - **Description**: up to `500` characters, stating purpose and scope.
   - **Team**: the current team (the admin console form can target another team).
3. Choose models:
   - **Embedding model**: an embedding model authorized for the team. It cannot be changed after creation.
   - **Rerank model**: optional; once bound, results can be re-scored during retrieval.
4. Configure chunking and reranking:
   - **Chunk size**: default `1000` characters, minimum `100` (the UI suggests up to `2000`).
   - **Chunk overlap**: default `100` characters, minimum `0` (the UI suggests up to `500`).
   - **Custom separator**: accepts escaped forms such as `\n\n` as a hard cut boundary.
   - **Enable reranking**: on by default; **rerank candidates** default `10` (`1-100`); **rerank score threshold** is blank by default (`0-1`).
5. Choose **visibility** (**Private** or **Team**).
6. Select **Create knowledge base**, then open the detail page and confirm the status is **Active**.

When editing an existing knowledge base, the dialog also offers an **Enable knowledge base** switch (turning it off archives the knowledge base, and archived knowledge bases are excluded from retrieval).

<Callout type="error" title="The embedding model cannot be changed">
  Stored vectors are bound to the embedding model chosen at creation, so updating it is rejected. The **rerank model can be changed at any time** (team authorization is checked). To switch embedding models, create a new knowledge base and reprocess documents with the new model.
</Callout>

## Models and Vector Dimension

### Embedding model

Embedding models appear in the create form only after being registered on the platform and authorized for the team. A knowledge base references exactly one embedding model; without a usable model, neither document processing nor retrieval works.

### Vector dimension

The vector dimension is **written when the first documents finish vectorizing** and then fixed. After that:

- Documents with a matching dimension index normally;
- Vectors with a mismatched dimension fail to write, and retrieval tells you to check the model and index dimension;
- Changing the embedding model does not rebuild the index — create a new knowledge base or run a full reprocess.

## Chunking and Retrieval Settings

The key items in the create dialog and knowledge base settings are below; field-level definitions and every limit are in the [Knowledge base settings reference](/en/reference/knowledge-settings):

| Setting | Default | Range | Applies to |
| --- | --- | --- | --- |
| Chunk size | `1000` | `>=100` characters | Document processing (on next process/reprocess) |
| Chunk overlap | `100` | `>=0` characters | Document processing |
| Custom separator | Empty | Any string | Document processing, hard cut boundary |
| Enable reranking | On | On/off | Retrieval (requires a bound rerank model) |
| Rerank candidates | `10` | `1-100` | Retrieval |
| Rerank score threshold | Empty | `0-1` | Retrieval |
| Retrieval mode | Empty | Vector / Full-text / Hybrid | Default mode for Agent/workflow retrieval |
| Result count | Empty | `1-100` | Agent/workflow retrieval |
| Similarity threshold | Empty | `0-1` | Agent/workflow retrieval |

<Callout type="warn" title="Knowledge base settings and retrieval requests are separate defaults">
  Retrieval fields in knowledge base settings are **empty** by default and only take effect once set; a **retrieval request** with no parameters runs hybrid retrieval with `5` results and threshold `0`. The hit-testing panel initializes from knowledge base settings and can write them back with **Apply to production**. So “the mode in knowledge base settings” mainly affects Agent/workflow retrieval; see [Retrieval and quality tuning](./retrieval.mdx).
</Callout>

For character semantics, Markdown versus plain text, previews, and failure retries, see [Chunking and document processing](./chunking.mdx).

## Cross-Team Sharing (Read-Only)

Sharing gives **another team** read and retrieval access to a knowledge base but **no edit rights**. It is the only form of cross-team access.

### Steps

1. In the **Knowledge bases** list, hover a knowledge base card, open the **⋯** menu, and select **Share**.
   - The entry only appears for knowledge bases your team owns and requires a team administrator role.
2. Choose the **team** in the **Share** dialog.
   - Candidates come from teams you belong to, excluding the current team and teams already shared with.
   - **Permission level** has a single, unchangeable option: **Read-only**.
3. Select **Share**. The list shows the team, a read-only badge, and “shared by …”.
4. To revoke, click the delete icon on that row under **Shared with** and confirm; the receiving team's list drops the knowledge base immediately.

### Rules and failure reasons

| Rule | Result |
| --- | --- |
| A **Private** knowledge base | Cannot be shared; the UI says private knowledge bases cannot be shared |
| Sharing with your own team | Rejected with a message that you cannot share with your own team |
| Sharing with the same team twice | Rejected as already shared |
| What the receiving team sees | Only knowledge bases with **Team** or public visibility |
| Receiving permission | Read-only: view, search, and attach in Agents/workflows; no settings changes, uploads, processing, or document deletion |
| Revoking a share that does not exist | Reports that the share does not exist |

After sharing, both sides show badges:

- Receiving side: a **From** + team name badge; every write entry is disabled on the detail page.
- Owning side: a **Shared with N teams** badge.

### Using shared knowledge bases in Agents and workflows

- Agents in the receiving team can only attach knowledge bases **shared with that team**; unshared ones do not appear in the picker.
- Per-attachment result count, similarity threshold, and retrieval mode can still be overridden; sharing does not change those override rules.
- Sharing is read-only: the receiver can search, run hit tests, and reference the knowledge base in Agents/workflows, but cannot upload, process, delete documents, or edit chunks. Retrieval runs with the caller's identity and team permissions.

## Document Management

Document management covers upload, processing, reprocessing, and deletion; see [Import documents](./import-documents.mdx) and [Chunking and document processing](./chunking.mdx).

| Capability | Description |
| --- | --- |
| Upload | Documents start as **Pending** and are not processed automatically |
| URL import | After a security check, a URL document is created and you confirm its chunks on the preview page |
| Supported formats | PDF, DOC/DOCX, PPTX, TXT, Markdown, HTML, CSV, XLS/XLSX, JSON, URL, and images (no `.ppt` or archives; image parsing is configured by the site) |
| Bulk actions | Select several documents: **Quick process** pending ones, **retry failed chunks** for failed ones, or **delete** |
| Per-file limit | The site's document upload limit, `50MB` by default, range `1-1024MB` |

<Callout type="warn">
  Upload and processing are separate stages: a document in the list is not necessarily embedded yet. Only **Completed** documents are searchable and suitable for attaching to an Agent.
</Callout>

### Batch completion notifications and recovery entry

- When you bulk-process selected pending documents or submit chunks in bulk from the preview page, **one aggregated notification is sent after every document finishes**, rather than one per document.
- Notifications follow the site notification settings: all succeeded sends an indexing-complete notice, all failed sends a failure notice, and partial success prefers the failure notice (falling back to success if that type is disabled); with both disabled nothing is sent. The link points to the knowledge base.
- A **Pending documents** banner appears at the top of the knowledge base detail page (visible and dismissible only to the creator or an owning-team administrator; hidden for shared knowledge bases). **Continue processing** loads every pending document and jumps to the preview page, so you can resume later.

## Statistics

The knowledge base detail page shows statistic cards (documents, chunks, tokens, per-status counts); **Hit testing** in the dropdown opens the retrieval lab.

- The document count is recomputed from actual documents, not a cached value.
- Chunk and token counts are aggregated per document and written back to the knowledge base.
- Statistics also include document counts by status and type, plus embedding dimension and embedding stats.

<Callout type="info">
  Not implemented / roadmap: retrieval analytics (query volume, response time, cache hit rate, popular queries), storage trends, and statistics export are unavailable.
</Callout>

## Troubleshooting

### Document processing fails

1. Confirm the format is supported, the file is intact, and the size is within limits.
2. Open the document detail to see the error and whether extraction, chunking, or embedding failed.
3. Common causes and fixes:

| Cause | Fix |
| --- | --- |
| Text extraction failed (corrupt, encrypted, image-only without parsing) | Convert, remove the password, or enable [image parsing](./image-understanding.mdx) and reprocess |
| Zero chunks | Confirm the file contains extractable text, or turn off text cleaning and retry |
| Embedding failed (credentials, quota, dimension) | Check model authorization and vector dimension, then retry failed chunks |
| Indexing failed | Ask an administrator to check the retrieval service |

### No results or irrelevant results

1. Confirm documents are **Completed**.
2. Use **Hit testing** to check scores: with zero results, lower the similarity threshold first, then switch retrieval modes.
3. Check whether the Agent overrides result count, threshold, or retrieval mode for this knowledge base.
4. Ask an administrator to check retrieval service health; reprocess documents if needed.

### Cost or performance anomalies

- High cost: avoid unnecessary reprocessing, tune chunking (larger chunks, less overlap), use a cheaper embedding model, and delete redundant documents.
- Slow retrieval: lower the result count, disable reranking for simple queries, narrow the document scope, and ask an administrator to check retrieval service resources.

<Callout type="info">
  Not implemented / roadmap: per-knowledge-base document limits, daily embedding quotas, and cost alerts are unavailable.
</Callout>

## Best Practices

- ✅ Name it by content scope; avoid meaningless names like “Docs” or “Materials”.
- ✅ Start with default chunking (`1000`/`100`) on a representative document, then compare in hit testing.
- ✅ Clean up stale documents regularly; duplicates compete with each other in ranking.
- ✅ Use private knowledge bases for personal drafts and **Team** visibility for shared content.
- ❌ Do not expect manual “metadata” to improve retrieval — metadata is generated by the processing pipeline and has no edit entry.
- ❌ Do not switch embedding models in production, and do not enlarge chunks without verifying retrieval.
