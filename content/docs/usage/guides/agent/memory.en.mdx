Clouisle solves conversation continuity and cost with two layers:

1. **In-conversation context (message branches + single context summary)**: the live history during a conversation. When the assembled request exceeds budget, earlier history is **compressed into one summary** while the most recent turns stay verbatim, keeping the model window from overflowing.
2. **Cross-conversation memory graph (Memory Graph)**: a persistent knowledge network across conversations, capturing user preferences, project background, and core facts as entities and directed relations.

<Callout type="info">
  There is no separate “conversation summary” subsystem and no multi-stage (warning/selective/blocking) compression strategy: compression produces exactly one thing — a model-generated context summary. Memory itself is an entity/relation graph, not an accumulation of raw conversation text.
</Callout>

## Enable Cross-Conversation Memory

1. Open the Agent **orchestration** > **Memory**.
2. Turn on **Enable memory** (off by default).
3. Set the maximum memories per retrieval, range `1-50`, default `10`.
4. Optionally turn on **Automatic memory extraction** (on by default).
5. Save and publish the Agent. As users talk in different conversations, the Agent recalls previously recorded facts.

| Setting | Default | Range | Description |
| --- | --- | --- | --- |
| Max memories per retrieval | `10` | `1-50` | Maximum entities injected into the model per memory retrieval |
| Automatic extraction | On | On/off | Whether memories are extracted and saved from conversations automatically; when off, memory is read-only |
| Importance threshold | Medium | Low / Medium / High | Automatic extraction only saves content meeting this importance |

## Memory Graph

Persistent memory is not flat text; it is a directed knowledge network of **entities** and **relations**.

Explore and manage it under the personal menu > **My memory** (`/app/memories`) or in the admin console (`/memories`).

### Entity types

Ten entity types are predefined to categorize memory content:

| Entity type | Description | Example |
| --- | --- | --- |
| Preference | A personal preference or habit | "Prefers concise code style", "Usually writes TypeScript" |
| Project | A project in progress or joined | "E-commerce rebuild", "Internal knowledge base" |
| Person | A person or role mentioned | "Manager Zhang (product owner)" |
| Organization | A company, department, or team | "R&D department", "Vendor A" |
| Skill | A technology or expertise | "Python", "PostgreSQL performance tuning" |
| Goal | A stage goal or intent | "Ship docs-site i18n this quarter" |
| Fact | An objective fact or specific detail | "Production cluster runs in Tokyo" |
| Concept | A domain concept or term | "RAG hybrid retrieval" |
| Location | A place or physical location | "Shanghai Zhangjiang office" |
| Custom | Anything that does not fit the others | User-defined fact labels |

### Relation types

Entities can be linked by nine directed relation types, used to follow related memories:

| Relation type | Meaning |
| --- | --- |
| Prefers | Prefers something |
| Uses | Uses a tool or technology |
| Works on | Works on or participates in something |
| Works at | Works at an organization |
| Knows | Knows a person or technology |
| Part of | Belongs to a higher-level entity |
| Has goal | Has a certain goal |
| Located in | Is located at a place |
| Related to | Is related to something |

### Graph management

- **Multiple layouts**: grid, hierarchical, and radial layouts, with zoom in, zoom out, and fit view.
- **Entity search and filtering**: search entity names and descriptions by keyword, or filter by one or more entity types.
- **Relation drawer**: click an entity to see its outgoing and incoming relations, edit its properties directly, or delete a specific directed relation.
- **Bulk and safe deletion**: use select mode to delete stale or sensitive entities in bulk; deleting an entity also removes all of its relations.

## Memory Retrieval and Recency

When an Agent retrieves memories, it weighs both **semantic similarity** and **recency**: semantically close memories that were updated recently rank higher. By default a memory not updated for about 30 days has half the weight; newer memories are more likely to be recalled.

- **Filter by time**: retrieve only memories created or updated within the last N days — useful for questions like “what did we discuss last week”.
- **Expand by relation**: after a hit, expand outward 1-3 levels along relations (default 1), starting from at most 5 entities, with direction limited to incoming relations, outgoing relations, or both. Only relations that actually exist are returned; the model does not infer missing links and does not create entities this way.
- **Filter by type**: retrieve only one kind of entity, such as preferences or projects.

With **Automatic memory extraction** off, the Agent can only search and read existing memories and never writes new entities or relations.

## Background Extraction (Admin)

Administrators configure background memory extraction under **Site settings** > **Memory** (`/site-settings/memory`):

| Setting | Default | Constraint | Description |
| --- | --- | --- | --- |
| Background extraction | Off | On/off | Global switch for asynchronous background extraction |
| Extraction model | Empty | An enabled language model | The model that performs extraction; blank uses the default fallback model |
| Cooldown | `180` seconds | `10-3600` seconds | Minimum interval between extractions to avoid repeated triggers in one conversation |
| Pending turn threshold | `6` turns | `1-50` turns | Extraction starts as soon as this many user turns are pending |

<Callout type="info">
  The Agent must have both **Enable memory** and **Automatic memory extraction** checked in its orchestration, and the site-level background extraction switch must be on, before conversations with that Agent queue background extraction.
</Callout>

## How Long Conversations Compress

Context compression is on by default and does exactly one thing: earlier history is handed to the model to **produce a summary**, which replaces that history while the most recent turns stay verbatim.

- **Budget**: the available input budget comes from the model's own context window, minus output reserve and a safety margin; models without a configured window use a default.
- **Keeping recent text**: the latest turn is always kept, and turns with unfinished tool calls are never cut apart. If the request still exceeds budget after compression, the run fails with an explicit error instead of retrying forever.
- **Summary generation**: summary length is capped and truncated to what the budget allows; failures are retried a few times, and the turn ends with an explicit error if all attempts fail.
- **Reuse**: the summary is stored on the conversation, and later turns reuse and incrementally update the same summary instead of stacking new ones.

Compression only affects the current request's context; it never deletes history, which stays visible in the conversation.

## Troubleshooting

- **Preferences are not remembered**: confirm the Agent has memory enabled, the information meets the importance threshold, and you use the same signed-in user.
- **Replies ignore early details**: a long conversation may have compressed early history into a summary; restate the key constraints or start a new conversation.
- **Compression happens too often**: check the model's context window, output reserve, and tool result sizes; large tool outputs fill the budget faster.
- **The memory graph contains a wrong fact**: go to `/app/memories`, search for the entity, click **Edit** to fix the description, or **Delete** it.
- **The same fact is recorded repeatedly**: check the site background-extraction switch and the Agent's automatic extraction setting; with extraction off, memory is read-only.
