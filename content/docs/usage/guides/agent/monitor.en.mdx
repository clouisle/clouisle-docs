The monitoring dashboard summarizes a single Agent's conversation volume, Token consumption, response time, tool calls, execution outcomes, and user interventions. Data comes from the conversations and runs the Agent has already produced, and is the basis for deciding whether to adjust prompts, add Knowledge Bases, or switch models.

<Callout type="info">
  The monitoring page checks **write permission**: only super administrators, the Agent's creator, or owners/administrators of the owning team can access it. Regular team members and viewers cannot see monitoring data even if they can use the Agent, and are redirected to the app list. A private Agent is accessible only to its creator; legacy private Agents without a creator are accessible to team administrators.
</Callout>

## Admin App List

Under **Apps** (admin console, **Resources** group), administrators see Agents from all teams — a different entry point from a single Agent's monitoring page:

| Column | Description |
| --- | --- |
| **Name and description** | Agent name and description |
| **Team** | Owning team |
| **Status** | Draft or published |
| **Model** | Chat model in use |
| **Usage** | Conversation and message counts; no separate stats tab |
| **Created / last active** | Creation date and last activity time |

The list filters by status, visibility, team, and creator, and searches by name or description.

<Callout type="note">
  The admin list shows only conversation and message counts; for conversation volume, Tokens, latency, tool distribution, and execution health over a time range, use the single Agent's monitoring page.
</Callout>

## Opening the Monitoring Page

1. Go to **Apps** or the workspace and open the target Agent.
2. Choose **Monitoring** in the Agent sidebar (alongside **Orchestration**, **API**, and **Logs**).
3. The page title is **Monitoring**, with the subtitle "View usage statistics and performance metrics for this Agent".

## Time Range

The time range selector at the top defaults to **Last 7 days** and offers only three options:

| Option | Trend granularity |
| --- | --- |
| Last 24 hours | Hourly, 24 points |
| Last 7 days | Daily, 7 points |
| Last 30 days | Daily, 30 points |

Point labels follow the site time zone and appear as `HH:00` (hourly) or `MM/DD` (daily).

There is **no refresh button** and no manual granularity control. Switching the time range is the only refresh, and it reloads the overview, trends, and tool usage together.

## Overview Cards

Six metric cards appear at the top. Values at or above `1K` show as `K` and at or above `1M` as `M`; durations under `1` second show milliseconds, otherwise seconds with two decimals.

| Card | Description |
| --- | --- |
| **Conversations** | Total conversations created in the range |
| **Messages** | Sum of user, assistant, and tool messages |
| **Token usage** | Total Tokens, with prompt Tokens (`↑`) and completion Tokens (`↓`) separately |
| **Average response time** | End-to-end average duration |
| **Active users** | Distinct users who had a conversation in the range |
| **Tool calls** | Total tool calls in assistant messages |

## Usage Trends

Three area charts share the same time range:

| Chart | Description | Y-axis |
| --- | --- | --- |
| **Conversation trend** | Conversations and messages over time | Count |
| **Token usage** | Total Token consumption over time | Compact `K`/`M` |
| **Response time** | Average response time over time | Seconds |

Trend data fills the complete grid of time points, showing 0 where there is no data, so curves stay continuous and do not break when a period has no conversations.

## Tool Call Distribution

The **Tool usage** card shows the Agent's tool-call distribution as a donut chart, ordered by call count descending. The legend shows each tool's localized name and call count, and the tooltip is **Call count**.

- At most the top `8` tools are shown; the rest merge into **Other tools** with the combined count.
- With no tool calls, the card shows **No tool usage data**.
- Tool names are localized to the site language.
- Statistics do not enumerate MCP server tools live, so MCP tools may not appear in the distribution.

## Execution Health

The **Execution health** donut shows the outcome distribution of the Agent's finished runs; the tooltip shows count and share.

| Outcome | Meaning |
| --- | --- |
| **Succeeded** | The run finished normally |
| **Failed** | The run ended in failure |
| **Stopped** | The user stopped it |
| **Interrupted** | The service executing the run was lost (crash, restart, or eviction) and the run never finished |

The success rate is **succeeded ÷ finished runs**, labelled "succeeded ÷ finished runs" in the card. Card color changes with the rate:

| Success rate | Color |
| --- | --- |
| `≥ 95%` | Green |
| `≥ 80%` and `< 95%` | Amber |
| `< 80%` | Red |

<Callout type="warn">
  **Interrupted is terminal** and lowers the success rate rather than meaning "still running". In-progress runs are excluded from the denominator, and the page notes "N more in progress, not counted". If no run has ever finished, the card shows **No run records**.
</Callout>

## First Token Latency

The **First token latency** card shows the median (`p50`), `p95`, and average, with a line chart of `p50` and `p95` over time buckets. Buckets without samples are null and the line breaks there, and the card also shows the sample count. With no samples at all it shows **No latency samples**.

First token latency reflects how long users wait for the first character, which differs from **average response time** (total end-to-end duration): high latency usually relates to model first-token speed, context length, or queuing; high total duration may also mean many tool calls.

## User Interventions

The **User interventions** bar chart counts three kinds of user involvement (only non-zero items are shown):

| Label | Meaning |
| --- | --- |
| **Mid-run guidance** | Additional instructions inserted during generation |
| **Manual stop** | The user stopped generation |
| **Follow-up** | Continuing from the previous result |

The card also shows the **intervention rate** = total interventions ÷ finished runs, with two decimals, labelled "based on N finished runs".

<Callout type="note">
  When total interventions are 0 the card shows an empty state; if the chart has data but no run has finished, the rate is not shown. A high intervention rate usually means prompts, tool descriptions, or Knowledge Base recall are not clear enough and users keep correcting the Agent.
</Callout>

## Data Scope and Known Limitations

- Time ranges are last 24 hours, 7 days, and 30 days; the default is 7 days.
- When statistics fail, the page **silently keeps the previous or empty data** with no error message. If charts stay empty while conversations clearly exist, refresh the page, then contact operations to check the statistics service.
- Fewer than 6 cards or blank chart areas usually mean data has not returned yet; skeleton placeholders show while loading.
- Statistics are computed from stored conversations and runs: draft previews produce no official statistics, and direct model calls that bypass the Agent are not counted.

**Not available (Roadmap):** cost breakdown, additional response-time percentiles, statistics export (CSV/PDF) and scheduled reports, and Prometheus metrics.

## Troubleshooting

### The monitoring page will not open or redirects to the app list

1. Confirm you are the Agent's creator or an owner/administrator of the owning team (a private Agent is accessible only to its creator; legacy private Agents without a creator are accessible to team administrators).
2. Confirm the Agent has not been deleted; a deleted Agent redirects to the app list.
3. For a team Agent, confirm you are still a member of that team.

### All metrics are 0

1. Confirm the range actually contains conversations (check **Conversations** first).
2. Confirm you are looking at conversations from a published version; draft previews produce no official statistics.
3. Confirm the caller goes through Agent conversations rather than calling the model directly.

### Low success rate

1. Check the share of **Failed** and **Interrupted** in **Execution health**. A high **Interrupted** share means an unstable execution environment — contact operations instead of changing prompts.
2. Open **Logs**, filter by failed status, and find the error for failed runs.
3. Compare with the **Manual stop** share in **User interventions** to judge whether timeouts or long replies made users give up.

### High first token latency

1. Check the model provider's first-token speed and current load.
2. Shorten the system prompt and injected Knowledge Base context.
3. Compare first token latency across models and switch to a faster chat model if needed.
