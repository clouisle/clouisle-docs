Agent Studio (`/app/apps/{agent_id}`) shows the orchestration area and a live preview side by side on desktop:
- **Orchestration Editor (left)**: configure the model, system prompt, variables, knowledge bases, tools, and runtime parameters.
- **Live Preview Panel (right)**: talk to the draft Agent without leaving the page or publishing changes.
- **Top action bar**: Agent metadata, publish status (`Draft / Published`), the embed entry (`Embed`), and advanced settings (`Settings`).

Mobile hides the side-by-side preview so the editor keeps its width. Select **Preview** in the top toolbar to open the conversation in a full-screen drawer; close it to return to editing.

<Callout type="info">
  The current team must have an enabled chat model authorized. Creating requires permission to create Agents; publishing requires permission to publish Agents.
</Callout>

## Create an Agent

1. Go to **Apps** and select **Create App** > **Agent**.
2. Enter a name (`1-100` characters) and description (up to `500` characters).
3. Choose the owning team.
4. In Agent Studio, open **Agent Settings** (top right) to configure the model, opening message, suggested questions, and visibility.
5. Visibility defaults to **Private** (creator only) and can be switched to **Team**.

**Max iterations** caps how many tool-call rounds the Agent may run in one reply: default `5`, range `1-200`. Too low ends complex tasks early; too high can burn tokens when tools keep failing.

<Callout type="info">
  Agents do not expose per-call sampling parameters (Temperature, Max Tokens, Top P, Frequency/Presence Penalty). Sampling defaults live on the model itself; an Agent only selects a model, writes a system prompt, sets max iterations, and attaches tools and knowledge bases. See [Agent configuration reference](/en/reference/agent-config) for field-level details.
</Callout>

## Writing Prompts and Variables

1. In the **prompt**, state the role, task, constraints, when to use tools, and how to handle failures.
2. Type `{` to open the variable picker. `{query}` is the current user message.
3. In **Variables**, add user input fields. Variable names can be up to `50` characters; configure display name, required, hidden, default value, options, numeric range, or max length.
4. In the preview, fill in the variables and confirm the substitution.

## Configuring Knowledge Bases and RAG

1. In the **Knowledge bases** area, select **Add**.
2. Choose a knowledge base and a **Vector**, **Full-text**, or **Hybrid** retrieval mode.
3. Set the number of results (`1-100`, default `5`) and the similarity threshold (`0-1`, default `0.3`).
4. Optionally enable **Rerank** to improve retrieval precision.
5. Set the overall RAG mode: **Off**, **Auto**, or **Agentic**.

A single knowledge base defaults to **Hybrid** retrieval. Multiple knowledge bases enter the retrieval context in list order, which you can drag to change while editing. With no knowledge base attached, RAG turns off automatically and the RAG mode selector is hidden; it appears once you attach one.

See [Retrieval and quality tuning](/en/usage/guides/knowledge/retrieval) for what each mode means, hybrid rollout, and tuning.

## Adding Tools and Capabilities

In the **Tools** area, select built-in tools, custom tools, MCP, or Skills.

| Tool type | Description | Requirement |
| --- | --- | --- |
| Web Search | Site-managed web search: choose Tavily, Bocha, SearXNG, or DeepSeek; the default option uses the site default engine | An administrator has enabled and configured engines under **Capabilities** > **Configure search** |
| Calculator | Math calculation | None |
| Date/Time | Date and time lookup | None |
| Unit Converter | Unit conversion | None |
| Custom Tool | Custom tool | Create and test it under **Capabilities** first |
| MCP | Model Context Protocol tools | Configure it under **Capabilities** first |
| Skill | Predefined skill | None |

<Callout type="warn" title="Never put search keys in an Agent">
  Agents do not store search credentials and cannot override the search endpoint. The web search engine dropdown lists only engines enabled for the site; even a saved engine is revalidated at execution, so a disabled engine makes that selection unusable. See [Built-in tools](/en/usage/guides/tools/built-in#web-search-site-managed) for engine and credential management.
</Callout>

Create and test custom tools under **Capabilities** first, then enable them per Agent. When a tool shows “needs configuration”, complete its credentials under **Capabilities** (web search is the exception — the site manages it).

Tool timeouts and iteration limits live in Agent settings: a single tool call times out after `30` seconds by default, and the tool-call iteration limit matches max iterations (default `5`).

## Configuring Attachments, Media, and Memory

Turn on the relevant capability in the Agent **editor** before using attachments, image generation, video generation, or cross-conversation memory:

| Capability | Where to configure | Defaults and limits |
| --- | --- | --- |
| Attachments | **Files and images** | `10MB` per file (`1KB-50MB`), `5` per message (`1-10`); supports PDF, Word, PowerPoint, Excel, TXT, Markdown, CSV, JSON, HTML, and images |
| Image generation | **Image generation** | Default `1024×1024` (`256-4096`), up to `4` images per call (`1-10`), reference images enabled by default |
| Video generation | **Video generation** | Default `5` seconds (`1-30`), aspect ratio `16:9` |
| Memory | **Memory** | Up to `10` memories injected per retrieval (`1-50`), automatic extraction on by default |

Two display switches live in **Agent Settings**: **Citations** (off by default) attaches source citations to replies; **Hide artifact list** (off by default) hides the generated-file list under assistant messages — display only, files are not deleted.

Media generation covers **images and videos** only (no audio/TTS generation). Image and video generation both call the team's authorized models; with the switch off, the model does not see these capabilities.

On context: long conversations use **tiered compression** — older history becomes a summary, completed tool results fold into readable references, and large tool catalogs are discovered on demand. Original messages and tool records remain; compression only changes what the model sees. It applies to the current conversation only and is **not** cross-conversation memory. Memory is a separate **entity/relation** knowledge graph that persists across conversations.

Compression is configured under **Context Compression**: on by default; summary token budget defaults to `1000` (`128-8000`); **Show compression progress** is on by default. See [Memory and Context](./memory.mdx).

See [Attachments and media](./media.mdx) and [Memory and context](./memory.mdx) for details.

## Visibility and Publishing

1. Choose **Private** or **Team** visibility.
2. Select **Publish**. The status becomes **Published** and the Agent can receive messages.
3. After publishing you can open the **public page**, **embed** it, or **access the API**.

<Callout type="info">
  **Public** visibility is kept for historical records only; new Agents should use **Private** or **Team**.
</Callout>

<Callout type="warn">
  Agents only have **Draft** and **Published** states. There is no active/inactive or archived state, and no archive/restore flow. To stop using an Agent, unpublish or delete it.
</Callout>

## Saving, Debugging, and Publishing

1. Select **Save**. Validation errors list the specific fields.
2. In **Debug and preview**, send questions that cover both the happy path and failures.
3. With tools attached, verify arguments, failure messages, and the max-iteration stop.
4. Select **Publish**.

The display switches (**Citations**, **Hide artifact list**) are described under “Configuring attachments, media, and memory”; they affect presentation only.

## Monitoring and Statistics

Every Agent has a **Monitor** page (`/app/apps/{agent_id}/monitor`), opened from **Monitor** in the Agent sidebar. It shows overview cards, usage trends, tool-call distribution, **execution health**, **first-token latency**, and **user interventions** for `24h`, `7d` (default), and `30d`.

| Metric | Description |
| --- | --- |
| Conversations and messages | Total conversations, total messages, active users |
| Token usage | Input tokens, output tokens, and total |
| Average response time and first-token latency | End-to-end average; first token `p50`/`p95`/`avg` |
| Execution health and interventions | Run outcome distribution, success rate, intervention count |
| Tool calls | Call count per tool |
| Usage trends | Usage over time |

<Callout type="info">
  Metric definitions, success-rate calculation, and limitations are in [Agent monitoring](./monitor).
</Callout>

<Callout type="warn">
  Not implemented / roadmap: per-Agent cost breakdown, request-level latency percentiles beyond first token, statistics export (CSV/PDF), and scheduled usage reports. There is no Prometheus metrics endpoint either.
</Callout>

## Best Practices

### Agent design

- ✅ Write a clear, specific system prompt
- ✅ Test thoroughly before deploying
- ✅ Pick a model suited to the task
- ✅ Enable RAG to improve factual accuracy
- ✅ Watch usage on the Monitor page
- ✅ Collect user feedback and iterate

- ❌ Use vague system prompts
- ❌ Deploy untested Agents
- ❌ Use expensive models for simple tasks
- ❌ Ignore error rates
- ❌ Skip cost monitoring

### Performance

- ✅ Enable streaming output for a better experience
- ✅ Optimize knowledge base search
- ✅ Set sensible timeouts

- ❌ Process long tasks synchronously
- ❌ Attach too many knowledge bases
- ❌ Set an excessively high output limit

## Troubleshooting

### Agent Does Not Respond

1. **Check Agent status**: confirm it is published; check model availability.
2. **Check model configuration**: verify the API key, test connectivity, and check rate limits.
3. **Check knowledge bases**: confirm indexing finished and search works.
4. **Check the audit log**: filter by resource type `agent` and matching resource ID.

### Poor Reply Quality

1. **Review the system prompt**: make instructions clearer, add examples, set boundaries.
2. **Improve knowledge bases**: add relevant documents, update stale content, tune chunking.
3. **Enable Agentic RAG**: let the Agent decide when to retrieve.

### High Cost

1. **Review usage**: check token usage and conversation counts on the Monitor page to find heavy Agents.
2. **Optimize prompts**: shorten the system prompt, reduce context, use cheaper models for simple tasks.

<Callout type="warn">
  Not implemented / roadmap: per-Agent token limits, daily usage caps, and cost alerts are unavailable; usage on the Monitor page is read-only.
</Callout>

## FAQ

- **The model list is empty**: the team has no authorized chat model, or the model is disabled.
- **Tools are not called**: check the model's function-calling support, whether the tool is enabled, and whether the prompt defines when to call it.
- **Publishing fails**: confirm you have publish permission and that the model, variable references, and capability configuration are valid.
- **The public page is unreachable**: confirm the Agent is published; private/team visibility still requires sign-in and team access.

| Agent template library | Not implemented | Duplicate an existing Agent |

| Cost breakdown / request-level percentiles | Not implemented | The Monitor page provides first-token `p50`/`p95` |
