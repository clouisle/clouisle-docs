工作流问题分为配置问题、数据流问题和运行时问题。先过检查清单，再做一次调试运行，最后看节点追踪和运行指标。

运行记录有两个入口：编辑器左上角工作流菜单里的**日志**页是当前工作流的运行历史；管理后台的**活动日志**页 → **工作流运行**标签是所有工作流的全局视图，只读，可按工作流、状态、触发类型、触发用户与「仅调试运行」筛选。

## 配置校验

**检查清单**在发布前逐项报告：未选择模型、工具或知识库；输入/输出变量没有来源；变量引用不存在；条件分支不完整；决策节点缺少模型、输入状态或判断说明，选项/等级数量或唯一性不合规，连线指向已过期的决策分支句柄；代码或模板为空；迭代/循环缺少开始或处理节点；没有输出节点。

清单里没有对应错误不代表配置正确——它只覆盖结构性问题，"这条分支真的走得到吗"要靠调试运行回答。

## 调试运行

在编辑器选择**运行**，打开**测试运行**抽屉并填入输入参数。抽屉底部有两个按钮：

- **调试（使用草稿）**：始终可用，跑的是当前草稿。
- **开始运行**：工作流发布后才可用，跑的是最新已发布版本。

运行过程中，抽屉里的**追踪**会随节点逐个完成实时追加；运行结束后，**详情**显示状态、运行时间、输入、输出、错误信息与元数据。

<Callout type="info">
  调试运行使用**当前草稿**，不会改动已发布版本；正式运行则加载最新已发布版本。同一个按钮不会同时验证两条路径——改完草稿仍然需要重新发布才能让正式运行生效。
</Callout>

**追踪**列出每个节点的状态、输入、输出、Token（提示词/补全/总计）与耗时；条件分支和决策节点还会显示命中的分支与句柄。

### 调试运行会补全变量类型

每次调试运行完成后，编辑器会根据这次运行的实际输出推断变量类型，并合并进当前草稿：

- 变量选择器和节点配置里的**调试运行推断字段**因此能在一次试跑后给出字段级补全，不必手工声明结构。
- 以 `_` 开头的内部输出会被跳过，不进入推断结果。
- 只有调试运行会写回推断结果；正式运行不会改动编辑器里的类型提示。

<Callout type="warn">
  目前**没有断点或单步调试**，只能整轮运行、事后看追踪。要缩小定位范围，把大段逻辑拆成多个节点，或临时在中间加一个变量赋值/回答节点输出中间值。
</Callout>

## 运行状态

运行级状态：

| 状态 | 含义 |
| --- | --- |
| 等待中（`pending`） | 已创建，等待执行 |
| 运行中（`running`） | 正在执行 |
| 等待输入（`waiting`） | 停在暂停节点，等待人工审批或补充变量 |
| 成功（`success`） | 全部流程成功完成 |
| 失败（`failed`） | 某节点或运行时失败 |
| 已取消（`cancelled`） | 用户取消 |
| 超时（`timeout`） | 达到运行时限制 |

节点级状态多了**已跳过**（`skipped`）：该节点被条件分支或循环跳过。跳过不是失败，也不会出现在运行级状态里。

## 监控指标

工作流**监控**页只对创建者、团队管理员和超级管理员显示。页面内容：

- 顶部卡片：总运行次数、成功率、平均耗时、失败次数。这些数字覆盖该工作流的全部历史，不随下方时间范围变化。
- 图表区可切换**最近 7 天**与**最近 30 天**（默认最近 7 天，按本地日期分桶）：**运行趋势**（每日运行数）、**成功 vs 失败**、**性能趋势**（每日平均执行时长）、**状态分布**。
- **最近活动**列出最近几次运行，点击进入运行抽屉。

**日志**页适合按条件翻查：可按状态与日期范围筛选，并用**按完整运行 ID 搜索**定位单次运行。跨工作流的运行统计与管理员级聚合指标的字段说明见[工作流 API](../../../api/workflow.mdx)；管理端的运行汇总、依赖关系与告警视图见[可观测性参考](../../../reference/observability.mdx)。

## 排查顺序

1. 检查输入变量是否存在且类型正确。
2. 查看**第一个**失败节点，而不是只看最终错误。
3. 对 LLM 检查模型授权、提示词和 Token；对 HTTP 检查 URL、请求头、超时与响应路径；对代码检查包版本、资源限制和产物路径。
4. 对决策节点检查模型是否为决策类型且已授权给团队；看追踪里的命中分支、置信度和概率判断是阈值问题还是判断说明问题（详见[编排工作流 → 决策节点](./orchestrate.mdx#决策节点)）。
5. 对知识库检查文档是否完成处理、是否更换过嵌入模型（更换后必须重建索引），以及检索是否正常；检索整体不可用时联系部署管理员。
6. 若是已发布应用，确认失败发生在已发布版本而不是草稿编辑器。
