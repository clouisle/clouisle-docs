The workflow editor registers the nodes below, organized into four categories in the node panel. Exact input/output fields and settings per node follow the editor and the [node reference](/en/reference/workflow-nodes).

| Category | Nodes |
| --- | --- |
| Model | LLM, media generation |
| Logic | Conditional branch, question classifier, decision, iteration, loop, pause |
| Transform | Code execution, template, file to URL, variable aggregation, variable assignment, parameter extraction |
| Extension | Sub-workflow, Agent, tool, knowledge retrieval, answer |
| Entry and canvas helpers | Start (user input / trigger, chosen at creation), note (static annotation, not executed) |

**Nodes not in the panel**: HTTP request and document extraction have execution logic but no canvas node and only appear in definitions submitted programmatically; the end markers inside iteration/loop containers are not standalone nodes and cannot be connected on their own.

## Choosing Nodes

- Use **LLM** when a chat model must reason; use **Decision** when you must pick one of several options or ordered levels and also want probabilities and confidence; use **Agent** to reuse full Agent behavior.
- Use **Knowledge retrieval** to answer from a knowledge base, then map results into an LLM or the output.
- Use **Tool** to call existing HTTP/MCP/code capabilities; never re-store credentials in the workflow.
- Use **Iteration** to process each array item; use **Loop** to repeat until a condition holds.
- Use **Sub-workflow** to isolate a reusable flow, configuring input/output mappings and the failure policy.

## Decision Node

The decision node is the only node that **returns probabilities**: it hands a state to a decision model, which answers exactly one question with a probability distribution and confidence, and the node routes accordingly. It generates no text, so routes never need parsing model output and a chatty model cannot send the flow down the wrong branch. Full setup and examples are in [Orchestrate a workflow → Decision node](./orchestrate.mdx#decision-node).

### Compared with LLM and question classifier

| Aspect | LLM | Question classifier | Decision |
| --- | --- | --- | --- |
| Underlying model | Chat model | Chat model | Decision model (non-generative) |
| Output | Generated text | JSON requested by the prompt, with the category parsed out | Structured result: option/level + probability distribution + confidence |
| Branching basis | Text content | Parsed category | Highest-probability option/level |
| Branch handles | None | One per category | One per option/level, plus a fallback |
| Uncertainty handling | None | Only the model's self-reported confidence field | Confidence threshold + fallback branch |
| Typical use | Generate, summarize, rewrite | Intent routing | Disposition decisions, priority assignment, binary go/no-go |

Rule of thumb: if “which path” depends on natural-language semantics and you need to know how certain the model is, use the decision node; for pure text generation use LLM; for a fixed set of categories where probability does not matter, the question classifier is lighter.

### Three question types

| Question type | UI label | Options/levels | Branch handles | Confidence | When to use |
| --- | --- | --- | --- | --- | --- |
| Choose an option | Choose one option | 1–255 unique options | One per option, plus fallback | Yes | Mutually exclusive dispositions (refund / technical / billing / other) |
| Score on an ordered scale | Score on an ordered scale | 2–10 **ordered** levels | One per level, plus fallback | Yes | The level is inherently ordered (low/medium/high, P0–P3) and you need a numeric score |
| Yes / no judgment | Yes / no probability | Fixed two | **Yes**, **No**, plus fallback | No | A single binary decision: probability at least `0.5` goes **Yes**, otherwise **No** |

“Yes / no judgment” returns no confidence, so the confidence threshold does not apply; use “Choose an option” or “Score on an ordered scale” when “hand off to a human if unsure” is required.

### Branch handles, fallback, and thresholds

- The option or level text is the output handle name on the canvas; the fallback handle is `default` by default and can be renamed under **Fallback branch**.
- When you change option text without changing the count, the editor remaps existing connections by position; leftover connections after changing the count are reported by the checklist as “stale output handles” and must be reconnected.
- The **confidence threshold** (`0`–`1`, may be blank) reroutes the flow to the fallback only when confidence is **strictly below** it; equal to the threshold still follows the model's choice. The threshold affects routing only: the **judgment result** is always the model's chosen option/level, while the **actual branch** is the one taken.
- Without a threshold, only an unparseable result goes to the fallback. A fallback branch with no downstream connection ends the flow at this node.
- The decision node retries up to 2 times by default (exponential backoff starting at 1 second).

### Outputs and failures

Outputs include the judgment result (the chosen option/level or yes/no), the actual branch, token usage, and — depending on the question type — confidence and the probability distribution.

On failure: missing configuration or invalid options fail validation before the run; a model answer, option set, or probability set that does not match the configuration reports a result mismatch; an unauthorized or disabled model, an address blocked by the allowlist, a timeout (default `60` seconds), or exhausted quota reports the corresponding provider error.

### Debugging decision branches

- The checklist reports, item by item: no model selected, empty input state, empty instructions, too few/too many options or levels, empty or duplicate options, and connections using stale handles.
- In the run trace, check the actual branch (which path was taken), confidence (whether the threshold rerouted it), and the probability distribution (to decide between tuning the threshold and rewriting the instructions).
- A decision node is one call, one result, with no intermediate steps and no breakpoints or single-stepping — debug by running the whole flow.

## Tool Node

The tool node executes built-in tools, custom HTTP/code/database tools, MCP tools, or Skills. Each argument has one mapping whose source is either an upstream variable or a constant.

- **Declare the type of constants**: constants typed in the UI are text, and the mapping type decides the conversion before execution — integer, float, boolean, array, and object each parse accordingly. So `"10"` becomes a number only when declared as an integer. A failed conversion (not a number, invalid JSON) fails the node with an invalid-argument error instead of passing the wrong type to the tool.
- **Choose the engine for web search**: selecting the built-in web search automatically adds an engine mapping and shows a dropdown; the default option uses the site default and the rest list only site-enabled engines. Execution revalidates, so a disabled engine fails immediately.
- **Outputs**: the result, status (success / failure), duration (milliseconds), and any custom output variable names.
- **Permissions**: private tools are available only to their creator; cross-team tools must be shared with the workflow's team, otherwise the node reports that the tool was not found.

Full fields: [Workflow node reference](/en/reference/workflow-nodes#tool-node-tool).

## Pause Node and Approvals

The pause node puts the run into **waiting** until someone handles the request:

- **Variable mode**: wait for members to fill in the declared fields; after submission those fields become the node output.
- **Approval mode**: wait for an **Approve** / **Reject** decision and output the decision, whether it passed, the comment, and the submitter; a rejection fails the run as “approval rejected”.
- **Approvers**: when a list is configured, only those team members may submit (super administrators can override); when empty, it falls back to the workflow creator plus team administrators.
- **Approval policy**: by default one submission decides; with **Require all approvals** enabled, every approver must submit, the run resumes only when all approve, a single rejection fails immediately, and a duplicate submission by the same person is rejected.
- **Description template**: supports `{{variables}}`, resolved before saving; unresolvable references become empty strings, so raw placeholders are never shown to approvers.

The run page shows the node trace live in the run drawer (status, inputs/outputs, and duration per node), and pending pause requests are submitted in the same drawer. See the [Workflow API](/en/api/workflow) for approval endpoints.

## Node-Level Failures

Every run node records inputs, outputs, model, tokens, duration, retry count, error type, and error message. Set realistic timeouts on HTTP, code, MCP, and media nodes, and avoid unconditional retries against side-effecting endpoints that are not idempotent.
