Trigger types are configured under **Workflow Settings** > **Trigger** > **Trigger Method**: **Manual**, **Webhook**, and **Scheduled Task**. Drafts can always be debugged; external triggers (Webhook, embed, schedule) require the workflow to be published.

## Manual Runs

Select **Run** in the editor to open the **Test Run** drawer, fill in the inputs, and select **Start Run**. Before publishing, only **Debug (use draft)** is available.

After publishing, users can also open the run page directly, fill in the inputs, and run it; the run page presentation is chosen at publish time (**Form and result** or **Result with details**). Run records live on the **Logs** page in the editor menu.

## Webhook

1. In **Workflow Settings** > **Trigger**, set **Trigger Method** to **Webhook** and save.
2. Saving generates a **Webhook URL**. To invalidate an old address, click **Regenerate** — the old URL stops working immediately.
3. Open the **Access API** page and copy the Webhook URL together with the call sample it provides; replace `YOUR_API_KEY` in the sample with your own API key.
4. Send the request: the body supplies the workflow's input fields directly — do **not** wrap them in another `inputs` object.

Things to watch:

- The workflow must be published and its trigger method must be Webhook; otherwise the request is rejected with **Invalid Webhook token**, **Workflow not published**, or **Webhook trigger disabled**.
- Calls require API key authentication, and the key must have access to that workflow. Create and revoke keys on the **API keys** page in the user menu; see [API keys](../administration/api-keys.mdx).
- The request immediately returns a run record; follow progress and results on the **Logs** page or in the run drawer.
- A workflow containing a Pause node stops at that point waiting for input or approval instead of holding the connection open.

Complete request and response fields are documented in the [Workflow API](../../../api/workflow.mdx).

## Scheduled Tasks

In **Workflow Settings** > **Trigger**, set **Trigger Method** to **Scheduled Task**, then choose a **Schedule Frequency**:

| Frequency | What to fill in | Resulting expression |
| --- | --- | --- |
| **Run at interval** | **Execution Interval**: 5 / 10 / 15 / 30 minutes, 1 / 2 / 3 / 6 / 12 hours | Expressions such as `*/5 * * * *` or `0 */2 * * *` |
| **Run daily** | Run time | `minute hour * * *` |
| **Run weekly** | Weekday + run time | `minute hour * * weekday`, e.g. `0 9 * * 1-5` for weekdays at 9 AM |
| **Run monthly** | Day of month + run time | The run time on that day each month |
| **Custom Cron** | **Cron Expression** | Fill in `minute hour day month weekday` directly |

Scheduled runs start with empty inputs, and the run record belongs to the workflow creator.

<Callout type="warn" title="Scheduling depends on a scheduler service in your deployment">
  Saving the plan only stores configuration. Scheduled triggers fire only when the deployment has a scheduler service enabled; the bundled default deployment does not enable it, so a saved plan will not run on its own there. If you need scheduled runs, ask your deployment administrator to enable the scheduler and to confirm it recognises the plan format the interface saves (otherwise nothing fires at the appointed time either). For the diagnostic path, see the background-task sections of [Troubleshooting](../../../self-host/operations/troubleshooting.mdx).
</Callout>

## Embedding the Run Page

To embed a published workflow's run page into your own site or internal system:

1. Select **Embed** in the editor toolbar (the **Embed Settings** dialog).
2. Turn on **Enable Embedding**. The switch is unavailable until the workflow is published — publish first.
3. Fill in **Allowed Domains**: `example.com`, `example.com:3000`, or a wildcard subdomain such as `*.example.com`, separated by commas or newlines. **Leaving it empty means no origin restriction** — any site can embed it, so do not leave it empty in production.
4. Adjust **Show Header**, **Show History** (history is stored in the visitor's browser), and **Allow New** as needed, plus **Theme** (auto/light/dark) and **Primary Color**.
5. Choose the **Bubble**, **Fullscreen**, or **Mobile** embed mode; bubble mode also offers a **Bubble Position** (bottom-right/bottom-left) and a **Greeting Message**.
6. Paste a `clou_`-prefixed key into **API Key**; it is filled into the snippet below. Copy the snippet onto your site.
7. Select **Save** and the snippet is ready to use.

Things to watch:

- The embed page reads the published version only; draft edits never appear in it.
- Embedding authenticates with an API key that must have access to the workflow; revoking the key disables the embed.
- Inputs and result presentation follow the presentation mode chosen when publishing. For the full option list, snippet parameters, and authentication details, see [Standalone Runs and Web Embedding](../agent/embed-and-share.mdx) and the [Embed API](../../../api/embed.mdx).

## Status and Cancellation

Run statuses include **Pending**, **Running**, **Awaiting input**, **Success**, **Failed**, **Cancelled**, and **Timeout**; **Awaiting input** means the run stopped at a Pause node awaiting approval or extra variables. The run drawer can cancel tasks still executing; some external API requests already sent cannot be interrupted.

What each status means and the troubleshooting order are covered in [Workflow Debugging and Monitoring](./debugging.mdx).
