Workflow issues fall into configuration issues, data flow issues, and runtime issues. Work through the checklist first, then a debug run, then node traces and run metrics.

Run history has two entry points: the **Logs** page in the workflow menu at the top-left of the editor covers the current workflow's runs, while **Activity Log** → **Workflow Runs** in the admin console is a read-only global view across workflows, filterable by workflow, status, trigger type, triggered user, and debug runs only.

## Configuration Validation

The **Checklist** reports each of these before publishing: unselected models, tools, or knowledge bases; inputs/outputs without a source; nonexistent variable references; incomplete conditional branches; a Decision node missing its model, state, or instructions, with an invalid number or uniqueness of options/levels, or with connections pointing at an outdated decision branch handle; empty code or templates; iterations/loops missing their start or processing nodes; and no output node.

The checklist only covers structural problems — it cannot tell you whether a branch is actually reachable. That is what a debug run answers.

## Debug Runs

Select **Run** in the editor to open the **Test Run** drawer and fill in the inputs. The drawer has two buttons:

- **Debug (use draft)**: always available, runs the current draft.
- **Start Run**: available only after publishing, runs the latest published version.

While the run is in progress, the drawer's **Trace** tab appends each node as it finishes; when the run ends, **Detail** shows status, run time, inputs, outputs, error information, and metadata.

<Callout type="info">
  A debug run uses the **current draft** and never modifies the published version; a production run loads the latest published version instead. One button cannot validate both paths — publishing is the only thing that moves draft edits onto the production path.
</Callout>

**Trace** lists each node's status, inputs, outputs, Tokens (prompt/completion/total), and duration; Condition and Decision nodes also show which branch and handle they matched.

### Debug runs complete variable types

After every debug run, the editor infers variable types from that run's actual outputs and merges them into the current draft:

- The variable selector and the **Inferred fields (from debug run)** panel in node configuration therefore offer field-level completion after a single trial run, instead of forcing you to declare shapes by hand.
- Internal outputs whose names start with `_` are skipped and never enter the inferred result.
- Only debug runs write inference back; production runs never change the editor's type hints.

<Callout type="warn">
  There are **no breakpoints or single-step debugging**, so debugging is always a whole run plus post-mortem tracing. To narrow things down, split large logic into several nodes, or temporarily add a Variable Assignment or Answer node to surface an intermediate value.
</Callout>

## Run Status

Run-level statuses:

| Status | Meaning |
| --- | --- |
| Pending (`pending`) | Created, waiting for execution |
| Running (`running`) | Executing |
| Awaiting input (`waiting`) | Stopped at a Pause node, waiting for an approval decision or extra variables |
| Success (`success`) | All flows completed successfully |
| Failed (`failed`) | A node or the runtime failed |
| Cancelled (`cancelled`) | Cancelled by the user |
| Timeout (`timeout`) | Reached the runtime limit |

Node-level statuses add **Skipped** (`skipped`): the node was skipped by a condition branch or a loop. Skipped is not a failure and never appears as a run-level status.

## Monitoring Metrics

The workflow **Monitoring** page is visible only to the creator, team admins, and superusers. It contains:

- Header cards: **Total Runs**, **Success Rate**, **Avg Duration**, and **Failed Runs**. These cover the workflow's whole history and do not change with the time range below.
- A chart area that switches between **Last 7 Days** and **Last 30 Days** (default 7 days, bucketed by local date): **Run Trends** (runs per day), **Success vs Failed**, **Performance Trend** (average duration per day), and **Status Distribution**.
- **Recent Activity** lists the latest runs; click one to open the run drawer.

The **Logs** page is better for digging by condition: filter by status and date range, and use **search by full run ID** to find a single run. Field-level details for cross-workflow run statistics and admin-level aggregates live in the [Workflow API](../../../api/workflow.mdx); the admin console's run summary, dependency, and alert views are described in the [Observability reference](../../../reference/observability.mdx).

## Troubleshooting Order

1. Check whether the input variables exist and have the correct types.
2. Look at the **first** failed node, not just the final error.
3. For LLMs, check model authorization, prompt, and Tokens; for HTTP, check the URL, headers, timeout, and response path; for code, check package versions, resource limits, and artifact paths.
4. For a Decision node, check that the model is of type decision and authorized for the team, then read the matched branch, confidence, and probabilities in the trace to tell a threshold problem from an instructions problem (see [Orchestrate a Workflow → Decision Node](./orchestrate.mdx#decision-node)).
5. For knowledge bases, check that documents finished processing, that the embedding model was not switched without an index rebuild, and that retrieval works; if retrieval is down entirely, contact your deployment administrator.
6. If it is a published app, confirm the failure happened on the published version rather than in the draft editor.
