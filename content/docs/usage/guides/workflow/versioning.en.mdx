A version record is a snapshot of a workflow definition: the definition, variables, trigger type, and trigger config. It is produced at two moments — the version number increments when the canvas definition changes, and publishing archives the current version number.

## Version Numbers and Snapshots

- **Only canvas definition changes bump the version**: a save that submits a new canvas definition (adding or removing nodes, rewiring edges, changing node configuration) increments the version number by 1. Changing only the name, description, icon, visibility, trigger configuration, or the variable list does not increment it.
- **Publishing archives it**: every publish creates a version record for the current version number holding the definition, variables, trigger type, and config; if that number already has a record, no duplicate is created. The Version History panel states the same: "Versions are automatically saved when publishing".
- **Published runs read the archive, not the draft**: a production run loads the latest published version, so edits on the draft never leak into a published workflow. Only debug runs use the draft.

<Callout type="info">
  The interface has no manual "save version" button: records come from publishing and restoring. To keep a snapshot with your own description, or to compare two versions, use the [Workflow Versions API](../../../api/workflow-versions.mdx).
</Callout>

## Publishing a Version

1. Save the draft and open the **Checklist**.
2. Fix all errors; evaluate warnings before publishing.
3. Select **Publish** and choose the run-page presentation in the **Publish workflow** dialog:
   - **Form and result**: shows inputs, run status, and the final result, without node-level execution details.
   - **Result with details**: prioritises the final result and lets people expand the execution trace and run details.
4. After publishing, the run entry uses the current published version; the version number only moves again when the definition changes.

## Viewing and Restoring

View records in **Workflow Settings** > **Version History**, ordered by version number descending with the current one labelled. Select a version and click **Restore**; the confirmation offers "Restore to `v{version}`" and notes that the current version will be saved automatically. It then:

1. Saves the current workflow state as a new record;
2. Overwrites the workflow with the target version's definition, variables, trigger type, and config, and increments the version number;
3. Creates another record describing the restored state.

Restoring does not delete any other history, and the pre-restore state is itself archived, so it can be restored again.

<Callout type="warn">
  A restore overwrites the whole definition: re-run the input boundaries, conditional branches, decision branches, sub-workflows, and external side-effect nodes afterwards, then decide whether to publish again.
</Callout>

## Legacy Workflows

Workflows created with the old type system load onto the canvas normally, but the run button is disabled and the interface says "This workflow was created by an older version — please re-save to adopt the new type system." Re-saving switches it to the new type system; this is a hard cutover with no automatic migration.

## Other Notes

- Workflow templates have no marketplace page: built-in templates are only instantiated into new workflows in the editor, and you still need to review the model, knowledge-base, and other references after instantiation.
- Each version record carries an auto-generated description. The interface has no field for your own notes; use the [Workflow Versions API](../../../api/workflow-versions.mdx) when you need a custom description.
