A Skill is a reusable capability package that bundles prompt instructions, runtime scripts, dependency declarations, and execution conventions. Unlike a single HTTP or database tool, a Skill can either carry a detailed specification the Agent reads and follows (**instructions mode**) or run a script in an isolated sandbox and produce files (**script mode**).

The entry point is **Capabilities** > **Skills** (`/app/capabilities?tab=skills`). Platform administrators can also review both system and team Skills, and import from there, in **admin panel** > **Capabilities** > **Skills** (`/capabilities?tab=skills`).

<Callout type="info">
Viewing Skills needs skill view permission, importing and maintaining need skill management permission, and sandbox tests need sandbox execution permission. Regular members usually have view access only: they can pick installed Skills while configuring an Agent but cannot import or modify them. Permissions are granted by the platform administrator in roles; see [Roles and permissions](/usage/guides/administration/roles-permissions).
</Callout>

## Skill package structure

Each Skill is a directory in the bundle, and the directory root must contain `SKILL.md` (UTF-8):

```
my-skill/
├── SKILL.md              # Required: metadata and prompt instructions
├── scripts/
│   └── run.py            # Optional: script run by a script-mode Skill
└── assets/               # Optional: templates, rules, or static resources
```

`SKILL.md` combines YAML frontmatter with a Markdown body:

```markdown
---
name: text-summarizer
display_name: Text Summarizer
description: Produces structured summaries, key points, and multilingual comparisons
version: 1.0.0
category: productivity
icon: FileText
x-clouisle:
  execution:
    mode: instructions
  input_schema:
    type: object
    properties:
      text:
        type: string
        description: Raw text to summarize
    required:
      - text
---

You are a professional long-form summarization expert. When the user supplies a long document:
1. Extract 3-5 core conclusions;
2. Output a key-point table;
3. Preserve critical figures and cite each source.
```

**Required**: `name` (lowercase letters, digits, underscores, or hyphens) and `description`. **Optional**: `display_name` (shown in the UI, defaults to `name`), `version`, `category`, `icon`, plus the execution mode and input schema under `x-clouisle`. The Markdown body is what the Agent reads.

### Execution modes

| Mode | How it runs | Typical use |
| --- | --- | --- |
| **Instructions** (default) | No code runs. The `SKILL.md` body is injected into the Agent context as a specification that steers the model. | Writing standards, analysis procedures, code review rules, domain SOPs |
| **Script** | Runs a script declared in the package (Python / Node.js) in an isolated sandbox and returns stdout, stderr, and generated files (artifacts). | Heavy computation, statistics, chart rendering, batch file conversion |

Skill cards and the detail page show the source (**Zip**, **Git**, or **Legacy**); **Legacy** means the Skill was converted from the pre-migration sandbox configuration. The execution mode lives in `SKILL.md` and cannot be changed separately in the UI after import.

### Package limits and validation

- **Zip upload**: `.zip` only, at most **50 MB** for the file, at most **50 MB** uncompressed, at most **500** files, and at most **10 MB** per extracted file.
- **Forbidden content**: no symlinks, nested archives, or path-escape entries such as `../`.
- **Git repository**: must be a public HTTPS repo; you can pin a branch, tag, or commit; cloning times out after **180 seconds**.
- Packages missing `SKILL.md`, with invalid metadata, or with illegal names are marked invalid in the preview and are not installed.

## Importing a Skill package

<Callout type="warn" title="Skills can only be created by importing">
There is **no manual "create Skill" entry point**. The only way to create a Skill is to import a ZIP or Git repository. After importing, only **metadata** (display name, description, icon, category, enabled state, default config) can be adjusted; changing the `SKILL.md` body or scripts requires a re-import.
</Callout>

1. Open **Capabilities** (`/app/capabilities`) and switch to the **Skills** tab.
2. Select **Import Skills** in the top-right corner.
3. Choose a source:
   - **Zip Upload**: pick a `.zip` containing one or more Skill directories.
   - **Git Repository**: enter a public HTTPS repository URL and optionally a **branch, tag, or commit** (such as `main` or `v1.0.0`).
4. Select **Scan Preview**. The preview lists one row per `SKILL.md` directory:
   - **Package path** and **Skill** (display name plus description).
   - **Status**: valid, conflict (a Skill with the same name already exists in the team), or duplicate name (the same name appears twice in one source).
   - **Action**: Install, Update, or Skip.
5. Non-conflicting entries are ticked by default. Conflicting entries start unticked; to overwrite, tick one and choose **Update** (the new package replaces the same-name Skill, keeping its name and ownership). When a source contains duplicate names, only the first is installed by default.
6. Select **Install Selected**. The new Skill appears in the list with the status **Enabled**.

## Viewing Skill details

Select a Skill card (or its name in the admin panel) to open the detail page, which shows:

- **Status** (Enabled / Disabled), **scope** (System / Team), category, version, and source.
- **Package path**, **parameters** (the input parameter names declared in `SKILL.md`), and the last update time.
- The **Instructions** body — the full specification the Agent reads before using the Skill.

Use the detail page to verify the description and parameters the Agent will see before going live.

## Binding and calling a Skill in an Agent

1. Open the target Agent's orchestration page (`/app/apps/{agent_id}`).
2. In the **Tools** area select **Add tool/Skill** and switch to the **Skills** category.
3. Pick the Skill to offer. The picker lists only **enabled** Skills.
4. After saving, the Agent decides during conversations whether to call it, based on the system prompt and the task.
5. Once debugging passes, select **Publish**.

## Enabled state

Cards and the detail page show **Enabled** / **Disabled**:

- A disabled Skill does not appear in the Agent tool picker, and a Skill that gets disabled after being bound is no longer called at runtime.
- The UI only displays the state and offers no switch: to disable or re-enable a Skill, a platform administrator changes it through the [Skills API](/api/skills). Newly imported packages are enabled by default.

## Running a test

A Skill can be exercised in isolation before going live. Tests are started through the test operation of the [Skills API](/api/skills); the UI does not expose a test button yet:

- **Instructions mode**: returns the `SKILL.md` instructions so you can preview the context the Agent will read; no code runs.
- **Script mode**: runs the script in the sandbox and returns success or failure, duration, stdout, stderr, and the artifact list. Artifacts can be downloaded.
- Arguments must match the structure declared in `SKILL.md`; missing or mistyped arguments fail validation immediately.

Script-mode Skills depend on the code sandbox being enabled. When the sandbox is unavailable, both tests and runtime calls fail — see [Code sandbox](/usage/concepts/sandbox).

## Scope and visibility

- **System**: belongs to no team and is available to every team on the platform; only platform administrators can import, maintain, and delete it.
- **Team**: belongs to one team and is visible only to its members; team administrators manage it.
- Skills have **no cross-team sharing dialog**: visibility is determined entirely by system or team ownership. To reuse a Skill across teams, have a platform administrator import it as a system Skill.
- A Skill referenced by an Agent **cannot be deleted**; unbind it in each Agent's configuration first. Only platform administrators can delete system Skills.

## Troubleshooting

### Import fails

1. **File too large**: confirm the ZIP is under `50MB` and expands to under `50MB`.
2. **Missing SKILL.md**: confirm each Skill directory root has an uppercase `SKILL.md` encoded as UTF-8.
3. **Invalid metadata**: check YAML indentation and confirm `name` and `description` are present, with the name limited to lowercase letters, digits, underscores, and hyphens.
4. **Git timeout**: cloning a public repository fails after `180` seconds; confirm the repository is publicly reachable and the `ref` exists.

### Execution errors

1. Read the standard error returned by the test to locate the script failure.
2. For script-mode Skills, confirm the declared dependencies can be installed in the sandbox; the platform sandbox must be enabled by an administrator.
3. Check that arguments match the types and required fields declared in `SKILL.md`.
