Clouisle groups tools into three kinds: **Built-in tools** (registered by the platform, no creation needed — see [Built-in Tools](/en/usage/guides/tools/built-in)), **MCP servers** (connect an external MCP Server — see [MCP Servers](/en/usage/guides/tools/mcp)), and **Custom tools** (created by teams). Custom tools belong to the current team, support the HTTP API, Code, and Database types, and can be configured, tested, and shared with other teams.

## Tool Types

The **Create Tool** menu under **Capabilities** > **Tools** offers four entries (MCP servers have their own page):

| Type | Description | Use Cases |
| --- | --- | --- |
| **HTTP API** | Call external HTTP endpoints, supporting GET/POST/PUT/PATCH/DELETE | Query CRM, create tickets, call third-party APIs |
| **Code Tool** | Execute Python or JavaScript in a restricted sandbox | Data transformation, text processing, custom calculations |
| **Database Tool** | Connect to an external relational/cache database, inspect the schema, then run **read-only** queries | Let the Agent answer questions from business data |

## Naming Rules

Tool names can only contain letters, digits, and underscores, and must start with a letter, for example `lookup_order`. Names must be unique within the team.

## Creating HTTP API Tools

1. In **Capabilities** > **Tools**, select **Create Tool** > **HTTP API**.
2. Set the tool name, display name, description, and category.
3. Configure the HTTP method (default `GET`), URL, headers, query parameters, JSON request body, and response path.
4. Use `{parameter_name}` placeholders in the URL, headers, query parameters, and body.
5. The timeout defaults to `30` seconds, range `1-300` seconds.
6. After saving, select **Run Test** and confirm the result path and error behavior.

<Callout type="warn" title="The URL must be static">
  A custom HTTP tool's **URL allows no placeholders at all**: if the URL contains `{param}`, `{{param}}`, or a bare `{{` / `}}`, execution is rejected outright. Put variables in the **Query Parameters**, **Request Headers**, or **Body Template** fields — those three support `{{param}}` substitution.
</Callout>

<Callout type="info">
  The URL also passes the site security check: private addresses are blocked by default, and only a validated address receives a request. To reach a private service, ask an administrator to add the target to the allowlist.
</Callout>

### HTTP Tool Configuration Example: Customer Lookup

```yaml title="CRM Lookup Tool Configuration"
Name: CRM Lookup
Description: Look up customer information in CRM system
Category: Data
Type: Custom

Endpoint Configuration:
  URL: https://api.crm.example.com/customers
  Method: GET
  Authentication: API Key
  API Key Header: X-API-Key
  API Key: crm_...
  Query Parameters:
    customer_id: "{customer_id}"
  Timeout: 30 seconds

Input Parameters:
  - name: customer_id
    type: string
    required: true
    description: Customer ID to lookup

Response Format:
  type: json
  schema:
    customer_id: string
    name: string
    email: string
    phone: string
    status: string
```

### HTTP Tool Configuration Example: Create Ticket (POST)

```yaml title="Create Support Ticket Tool Configuration"
Name: Create Support Ticket
Description: Create a support ticket in the ticketing system
Category: Communication
Type: Custom

Endpoint Configuration:
  URL: https://api.tickets.example.com/tickets
  Method: POST
  Authentication: Bearer Token
  Token: Bearer tk_...
  Content-Type: application/json
  Timeout: 30 seconds

Input Parameters:
  - name: title
    type: string
    required: true
    description: Ticket title

  - name: description
    type: string
    required: true
    description: Ticket description

  - name: priority
    type: enum
    required: false
    default: medium
    options: [low, medium, high, urgent]
    description: Ticket priority

  - name: assignee
    type: string
    required: false
    description: Assignee email

Response Format:
  type: json
  schema:
    ticket_id: string
    status: string
    created_at: string
```

## Creating Code Tools

Code tools support Python and JavaScript, executed in a restricted sandbox. Python packages must use exact `package==version`; JavaScript packages must use `package@version`. You can configure the command argv, package source address, artifacts, and resource limits.

Default resource limits:

| Resource | Default | Description |
| --- | --- | --- |
| Timeout | 30 seconds | Maximum execution time |
| Disk | 1024MB | Available disk space |
| Standard Output | 256KB | stdout cap |
| Standard Error | 256KB | stderr cap |

Artifact paths must be under `/workspace` and can be marked optional.

## Creating Database Tools

A database tool lets an Agent query an external database directly. The connection details (host, port, credentials, connection URL) stay **hidden from the model** — the Agent only sees the tool name and description, so the description should say what the database holds and which questions it answers.

1. Under **Capabilities** > **Tools**, select **Create Tool** > **Database Tool**.
2. Pick the database type: PostgreSQL, MySQL, Redis, or MongoDB.
3. Fill in the connection, using either mode:
   - **Field mode**: host, port, database, username, password, SSL.
   - **Connection URL mode**: enter the connection address directly (common for Redis / MongoDB); Redis can also set a logical database index, and MongoDB can set an auth database.
4. Set the **query timeout** (default `15`s, range `1-120`) and the **maximum returned rows** (default `100`, range `1-1000`).
5. Select **Test connection** (which also passes the site security check), then save once it succeeds.

### What the Agent can do

| Database type | Capabilities |
| --- | --- |
| PostgreSQL / MySQL | Read the table structure first (optionally for specific tables or with sample rows) so the model learns which tables and columns exist; then run **read-only** SQL queries |
| Redis | Scan keys (with an optional match pattern, 20 per batch by default and at most 100, for at most 100 batches); read a single key (lists/sets/sorted sets return at most the first 50 members); run read-only whitelist commands such as `GET`, `HGETALL`, `LRANGE`, `ZRANGE` |
| MongoDB | List collections with estimated counts, or infer one collection's fields; query documents by filter, count matching documents, or run an aggregation |

Returned rows are always capped by **maximum returned rows**, so an Agent's own limit can only be smaller; queries return 50 rows by default, and MongoDB queries and aggregations return 20.

<Callout type="warn">
  Database tools are read-only.
  - For PostgreSQL / MySQL, write statements (`INSERT` / `UPDATE` / `DELETE` / DDL) and dangerous keywords are rejected; only one statement is allowed per call and SQL is limited to `65536` characters.
  - Redis blocks dangerous commands such as `FLUSHALL`, `CONFIG`, `EVAL`, `SCRIPT`, and `KEYS`; anything outside the whitelist is rejected.
  - MongoDB aggregations may not write results back into a collection.

  Use an HTTP API or code tool when you need writes.
</Callout>

<Callout type="info" title="Timeouts and returned volume">
  **Query timeout** (default `15`s, `1-120`) bounds a single query, connection and execution included; **maximum returned rows** (default `100`, `1-1000`) is the hard cap on records returned by any operation. Redis scanning additionally caps each batch at 100 keys and the scan at 100 batches, preventing unbounded scans on large databases.
</Callout>

<Callout type="error">
  Connection details are stored server-side and never sent to the model, but always use a **read-only** database account with least privilege. Testing connectivity requires permission to create tools.
</Callout>

## Editing and Deleting Tools

### Editing Custom Tools

1. Select the custom tool
2. Select **Edit**
3. Modify tool details, endpoint configuration, parameters, or response format
4. Test the tool
5. Save changes

### Deleting Custom Tools

1. Select the custom tool
2. Select **Delete**
3. Review impact: Agents and workflows using this tool
4. Confirm deletion

<Callout type="error" title="Deletion Impact">
  After deleting a custom tool, Agents and workflows referencing this tool will be unable to execute it. Please confirm no dependencies exist before deleting.
</Callout>

## Testing Tools

### Running a Test

1. Select the tool
2. Select the **Test** button
3. Enter test parameters
4. Select **Run Test**

### Example Test Results

For web search, choose an engine (site default or an enabled engine) and fill in the query and result count.

```yaml title="Web Search Test Result"
Tool: Web Search
Test Parameters:
  query: "artificial intelligence"
  num_results: 5
  engine: site default

Status: Success
```

## Credentials and Sharing

Credentials are stored server-side and injected at call time. Custom tools can be shared with other teams with either **read-only** or **read and execute** permission.

| Permission | Description |
| --- | --- |
| **Read-only** | The receiving team can view the tool configuration but cannot execute it |
| **Read and execute** | The receiving team can view and execute the tool |

<Callout type="warn" title="Sharing limits">
  - Built-in tools cannot be deleted or shared
  - A shared tool's owner configuration cannot be modified by the receiving team
</Callout>

The tool list shows the sharing state and how many teams the tool is shared with.

## Tool Status

Tools are either enabled or disabled:

| Status | Description |
| --- | --- |
| **Enabled** | The tool works and appears in tool selection |
| **Disabled** | The tool cannot be used and is hidden from users |

<Callout type="info">
  Tools only have enabled/disabled states — there is no “testing” or “deprecated” state. Use the **Enable**/**Disable** action in the tool list menu to switch.
</Callout>

## Handling Failures

### HTTP Tool Test Failure

Check the following:
- Whether the URL is correct
- Whether the TLS certificate is valid
- Whether credentials have expired
- Whether the request body is valid JSON
- Whether the response path matches the actual response structure

### Code Tool Test Failure

Check the following:
- Whether packages use pinned versions (`package==version`)
- Whether stdout exceeds the 256KB cap
- Whether disk usage exceeds the 1024MB cap
- Whether execution timed out (default 30 seconds)
- Whether artifact paths are under `/workspace`

## Best Practices

### Tool Configuration

**✅ Recommended:**
- Test tools before enabling them
- Rotate credentials regularly
- Document what each tool is for
- Keep tools up to date
- Handle errors

**❌ Avoid:**
- Enabling untested tools
- Using static credentials long-term
- Skipping documentation
- Ignoring errors

### Security

**✅ Recommended:**
- Use strong authentication
- Rotate API keys regularly
- Limit tool access scope
- Enable audit logs
- Monitor unusual usage
- Use HTTPS only
- Validate response data

**❌ Avoid:**
- Weak authentication
- Long-lived static API keys
- Unrestricted access
- Disabling audit logs
- Ignoring suspicious activity
- Allowing plain HTTP
- Trusting responses blindly

### Performance

**✅ Recommended:**
- Set sensible timeouts
- Cache where possible
- Monitor response times
- Optimize tool calls
- Handle errors gracefully

**❌ Avoid:**
- Excessively long timeouts
- Skipping caching
- Ignoring performance metrics
- Making unnecessary calls
- Ignoring errors

## Tool Naming and Thinking Status Display

When an Agent calls tools mid-conversation, the **thinking panel** at the top recognizes and shows the current tool's intent without being expanded. To keep that display natural and clear, follow these naming conventions:

### 1. Naming Conventions and Recommended Verb Prefixes

| Operation type | Recommended verbs/roots | What the panel shows |
| :--- | :--- | :--- |
| **Data/information lookup** | `query_`, `fetch_`, `get_`, `search_`, `find_`, `check_`, `查_`, `获取_` | `Looking up: {tool name}...` |
| **Sending and notification** | `send_`, `post_`, `push_`, `notify_`, `mail_`, `发_`, `推送_` | `Sending: {tool name}...` |
| **Creating** | `create_`, `add_`, `insert_`, `new_`, `build_`, `建_`, `新增_` | `Creating: {tool name}...` |
| **External API calls** | `api_`, `http_`, `rest_`, `request_`, `接口_`, or parameters containing `url`/`endpoint` | `Requesting API: {tool name}...` |
| **Calculation and analysis** | `calc_`, `math_`, `count_`, `analyze_`, `计算_`, `统计_` | `Calculating and analyzing...` |
| **Artifact collection and export** | `artifact`, `artifacts`, or a name containing `生成下载链接` | `Collecting artifacts...` |
| **File and document operations** | `read_`, `write_`, `open_file`, `save_file` | `Reading/editing file...` |

### 2. Display Name Tips

- **Set a friendly display name**: if the tool has one (for example `查询股票行情` or `发送飞书通知`), the status bar shows it directly, such as `Looking up: 查询股票行情...`.
- **Identifiers are prettified**: if a tool only has an identifier such as `fetch_user_orders` or `syncCrmAccount`, the system turns it into natural words in the status, such as `Looking up: Fetch User Orders...`.
- **Parallel calls are grouped**: when an Agent runs several tools in one thinking round, the panel collapses them into `Calling {N} tools in parallel...`.

## Troubleshooting

### Tool Call Fails

1. **Check the tool configuration:** verify credentials and the endpoint URL, and test connectivity
2. **Check the audit log:** review entries for the team that owns the tool
3. **Common errors:**
   - **Authentication failure:** invalid credentials
   - **Timeout:** increase the timeout or check the endpoint
   - **Invalid parameters:** check the parameter format
4. **Test the tool:** use the test panel to see the result

### Slow Responses

1. Use the test panel to measure response time
2. Optimize: increase the timeout, send less data, improve the endpoint
3. Check the external service status for outages
