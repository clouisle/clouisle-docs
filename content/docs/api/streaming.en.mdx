Clouisle's streaming interfaces return `Content-Type: text/event-stream`. Clients should read each `event:` and `data:` line, handle unknown events, and release resources on `error` or connection close.

## Agent Events

| Event | Description |
| --- | --- |
| `message_start` | Returns `conversation_id` and `message_id` |
| `rag_start` / `rag_context` | Starts retrieval and returns sources |
| `reasoning_start` / `reasoning_delta` / `reasoning_end` | Reasoning (if the model supports it and it is not hidden) |
| `content_delta` | Text delta |
| `tool_call` / `tool_result` | Tool name, arguments, and result |
| `media_result` | UI image/video result; protected URLs require authentication and are not replayed to the model as text |
| `compression_start` / `compression_end` | Context compression details |
| `output_truncated` | Reached the maximum output Token |
| `iteration_cap_reached` | Reached the Agent's tool iteration cap |
| `message_end` | Token usage, elapsed time, and termination status |
| `error` | Error details |
`rag_start` and `rag_context` are emitted only when retrieval actually runs. If retrieval is not executed, persisted `rag_context` is `null`; if retrieval runs and returns no contexts, it is `[]`.

Clients must preserve received event order when rendering the thought-process timeline. Retrieval, compression, reasoning, tool, media, and text events may interleave. Retrieved source payloads may include `citation_id`; use the exact `[[cite:SOURCE_ID]]` marker when citing that source.


## Durable Run Events

Agent chat runs are backed by a durable `AgentRun`. Run-scoped events include `run_id`, `sequence`, `timestamp`, `round_id`, `message_id`, and `type`; reconnect with `after_sequence` to replay without duplicates.

```text
event: run_start
data: {"status":"running","run_id":"run-123"}

event: run_status
data: {"status":"waiting","pending_tool_call_id":"call-123","pending_tool_name":"ask_user","pending_tool_input":{"questions":[...]}}

event: input_accepted
data: {"kind":"steer","content":"..."}

event: run_end
data: {"status":"completed","message_id":"msg-456"}
```

`run_status` enters `waiting` while the model awaits an `ask_user` answer. Use the pending fields to render the question form and submit answers through `POST /api/v1/agents/{agent_id}/chat/runs/{run_id}/answers`. Each run emits exactly one `run_end` with status `completed`, `stopped`, `failed`, or `interrupted`.

Run status values:

| Status | Description |
| --- | --- |
| `queued` | Persisted and enqueued, waiting for a worker to pick it up. |
| `running` | A worker is executing the model loop. |
| `waiting` | Blocked on a structured `ask_user` answer; the event carries the pending tool-call details. |
| `stopping` | A stop request was received; the run is winding down cooperatively. |
| `completing` | The model loop finished and the final message is being persisted. |
| `completed` / `stopped` / `failed` / `interrupted` | Terminal states: finished normally, stopped, failed, or lost with its worker. |

### Reconnection

The run event stream is `GET /api/v1/agents/{agent_id}/chat/runs/{run_id}/stream?after_sequence=N`, where `after_sequence` defaults to `0` and negative values are clamped to `0`:

1. Record the `sequence` of every run event you receive.
2. After a disconnect, resubscribe with the highest processed `sequence` as `after_sequence`.
3. The server replays only events with `sequence > after_sequence` before following the live stream, so nothing is duplicated or lost.
4. For a non-streaming catch-up, read the same buffered events from `GET /api/v1/agents/{agent_id}/chat/runs/{run_id}/events?after_sequence=N`.

On reconnect, reuse the existing `conversation_id` / `run_id` instead of creating new resources, and stop reconnecting once `run_end` arrives.

## Workflow Events

Workflow streams contain status events for run start, node start/output/skipped, run complete, failure, cancel, and timeout. Use the `stream_url` from the initial Webhook response to subscribe; use `from_sequence` to resume reading.

## Client Strategy

- Concatenate `content_delta` in order; do not overwrite earlier fragments.
- Store reasoning separately from text; do not render hidden content where display is not allowed.
- Treat `message_end` as normal message termination, `run_end` as durable-run termination, and `error` as failed termination.
- Configure heartbeats and reconnection for long connections; after reconnecting, use the conversation/run ID instead of creating new resources.
- Send the active JWT or API key when fetching protected image, video, or sandbox-artifact URLs; never fall back to an unauthenticated raw URL.
