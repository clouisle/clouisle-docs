Admin routes are mounted under `/api/v1/admin` and cover dashboards, observability, audit logs, conversations, users, roles, permissions, site settings, models, SSO, notifications, teams, memory, Agents, tools, Skills, workflows, workflow metrics, TOTP, packages, knowledge bases, and messaging deliveries. They are used by the admin panel and return the unified `code`/`data`/`msg` envelope. They are not public APIs for anonymous calls.

## Permission Model

Every endpoint declares the permission code it requires (`admin:*` or `audit:*`) through a dependency:

- **Superusers bypass everything**: an account with `is_superuser` skips all permission-code checks.
- **Everyone else is judged by permission code**: the account must hold the endpoint's declared code through a role. Codes come from the system permission definitions synced at startup and can be freely combined in **roles** (see `/api/v1/admin/roles` and `/api/v1/admin/permissions`).
- **API Keys carry the same checks**: an API Key is validated against its bound user's permission set, so never grant an API Key unnecessary `admin:*` permissions.
- **Knowledge bases are the exception**: `/api/v1/admin/knowledge-bases` reuses the platform knowledge-base routes, but switches the required code to `admin:knowledge-base:{read,test,create,update,delete}` based on the request path prefix and skips team-membership checks so the admin view can work across teams.

<Callout type="warn">
  Authorization is enforced server-side. Hiding a menu entry in the UI is not a security boundary; third-party integrations must request the minimum permission codes.
</Callout>

## Workflow Metrics

Workflow execution metrics are **not** under `/api/v1/workflows`; they live under the admin prefix at `/api/v1/admin/workflows/metrics/*`. The router carries its own `/workflows/metrics` prefix, so it coexists with the `/api/v1/admin/workflows` CRUD routes without colliding.

| Method | Path | Purpose | Permission |
| --- | --- | --- | --- |
| GET | `/api/v1/admin/workflows/metrics/dashboard` | Metrics dashboard summary (includes running workflows) | `admin:dashboard:access` |
| GET | `/api/v1/admin/workflows/metrics/workflows/{workflow_id}` | Execution metrics for one workflow | `admin:dashboard:access` |
| GET | `/api/v1/admin/workflows/metrics/nodes` | Metrics for every node type | `admin:dashboard:access` |
| GET | `/api/v1/admin/workflows/metrics/nodes/{node_type}` | Metrics for one node type | `admin:dashboard:access` |
| GET | `/api/v1/admin/workflows/metrics/running` | Currently running workflows | `admin:dashboard:access` |
| GET | `/api/v1/admin/workflows/metrics/cache` | Metrics cache statistics | `admin:dashboard:access` |
| DELETE | `/api/v1/admin/workflows/metrics/cache` | Clear the metrics cache | `admin:settings:update` |

```bash
curl -X GET "https://your-domain.com/api/v1/admin/workflows/metrics/dashboard" \
  -H "Authorization: Bearer YOUR_ADMIN_TOKEN"
```

## Messaging Delivery Log [#delivery-log]

`GET /api/v1/admin/deliveries` reads the durable outbound queue `integration_deliveries` shared by Feishu and WeChat Agent chat. It is **read-only** and requires `admin:integrations:settings:read`; superusers bypass the check. Message text, provider resource keys (`media_key`), credentials, and file contents are never returned. The admin panel's **Monitoring** > **Delivery log** (`/deliveries`) page uses the same endpoint.

`sent` only means the provider accepted the reply request; it does not mean the recipient read the message, opened a card, or downloaded an artifact.

### Query parameters

| Parameter | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `provider_type` | repeated `feishu` / `wechat` | No | - | Filter by integration; repeating the parameter matches any listed value (OR) |
| `status` | repeated `pending` / `sending` / `sent` / `error` / `unavailable` / `unknown` | No | - | Filter by delivery state; repeating the parameter matches any listed value (OR) |
| `run_id` | string (UUID) | No | - | Exact filter on the originating AgentRun |
| `filename` | string (1–500) | No | - | Case-insensitive substring filter on artifact file names |
| `limit` | integer (1–100) | No | `25` | Page size |
| `offset` | integer (≥ 0) | No | `0` | Page offset |

Values inside `provider_type` and inside `status` are ORed; the two filters are combined with AND. The response is `{items, total, limit, offset}`, ordered by `created_at` and `id` descending.

```bash
curl -X GET "https://your-domain.com/api/v1/admin/deliveries?provider_type=feishu&provider_type=wechat&status=error&status=unknown&limit=25&offset=0" \
  -H "Authorization: Bearer YOUR_ADMIN_TOKEN"
```

### States

| State | Meaning |
| --- | --- |
| `pending` | Queued, not yet claimed by a sender; preserved across restarts and feature pauses |
| `sending` | Claimed by one worker under a lease; an expired lease becomes `unknown` and is never resent automatically |
| `sent` | The provider accepted the reply request |
| `error` | A permanent failure, such as a provider rejection or unavailable artifact |
| `unavailable` | The run finished but the reply must not be sent (channel disabled, access revoked, missing conversation context) |
| `unknown` | A timeout after transmission; the result is uncertain and must not be resent blindly |

### Fields and errors

| Field | Type | Description |
| --- | --- | --- |
| `id` | string (UUID) | Delivery row ID |
| `provider_type` | string | `feishu` or `wechat` |
| `run_id` / `user_id` / `agent_id` | string (UUID) \| null | Originating AgentRun, connected user, Agent |
| `chat_id` / `message_id` | string \| null | Provider conversation ID / message ID |
| `event_key` | string | Event key, such as `received`, `final`, `final-asset`, or `ask:<tool-call>` |
| `sequence` | integer | Chunk order within the same event |
| `kind` | string | `text`, `markdown`, `asset`, and so on |
| `filename` / `content_type` / `size` | string / string / integer \| null | Artifact name, MIME type, and size in bytes |
| `media_type` | string \| null | Provider media type |
| `status` | string | One of the states above |
| `error` | string \| null | Stable failure key used for behaviour and localization |
| `error_detail` | string \| null | Provider's original error: message, HTTP status, code, and response excerpt |
| `has_media_key` | boolean | Whether a provider resource key is stored; the key itself is never returned |
| `created_at` / `updated_at` | string (ISO 8601) | Creation and last update timestamps |

`error` is a stable machine-readable key (for example `feishu_agent_asset_upload_failed`); `error_detail` preserves the provider's original text, HTTP status, and code so operators can diagnose permissions, parameters, or size limits.

<Callout type="warn" title="Not the notification delivery table">
  `GET /api/v1/admin/deliveries` and `integration_deliveries` cover only Feishu/WeChat Agent chat. In-app notifications sent externally through email / webhook / feishu are recorded in `notification_deliveries` and read through `deliveries[]` on the notification admin APIs. WeChat is not a notification channel.
</Callout>

### Upgrade relationship

The single table `integration_deliveries` replaces the former `feishu_agent_deliveries` and `wechat_agent_deliveries`. On first startup the API copies rows from the old tables and drops them, so **the API, every worker, and Beat must run matching versions**; an older process would write to a dropped table. Restoring the old image alone cannot recreate the queue table; rolling back requires the database backup taken before the upgrade.

Page behaviour, filters, and troubleshooting are documented in the [Delivery log](../usage/guides/integrations/delivery-log.mdx).

## Integration Guidance

- Third-party apps should prefer the Agent, workflow, conversation, and knowledge base resource endpoints over admin endpoints.
- Admin automation must pin the Clouisle version, record the required permission codes, and check the OpenAPI Schema before upgrading.
- Audit and user management operations contain sensitive data; use short-lived keys together with minimal rate limits.
- Grant `admin:*` only when cross-team operations are genuinely required; day-to-day work should use team roles with platform permissions such as `workflow:read` or `kb:read`.
