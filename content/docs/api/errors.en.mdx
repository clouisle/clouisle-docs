Every response uses the same envelope for success and failure:

```json
{"code": 0, "data": {}, "msg": "success"}
```

On failure, `code` is non-zero and `data` may be `null` or carry structured detail (the size limit that was exceeded, the remaining login attempts, and so on). `msg` is localized to the request language — **never** branch on `msg` text, always branch on `code`.

<Callout type="info">
  `code` values come from the backend `ResponseCode` enum (`backend/app/schemas/response.py`), which is the single authoritative source for every list on this page. The HTTP status is only a transport-level hint.
</Callout>

## HTTP Status Mapping

HTTP status and business `code` are not 1:1. The same `code` can appear with different HTTP statuses (`2003` is `403` when a JWT cannot be decoded but `400` for a wrong password), so use the HTTP status for coarse classification and the body `code` for precise branching.

| Source | HTTP | Business code |
| --- | --- | --- |
| `BusinessError` (default) | `400` | its own `code` (e.g. `5002` for username exists) |
| Validation errors (Pydantic) | `422` | `1001` |
| No credentials provided | `401` | `2000` |
| Invalid / revoked JWT, or single-session eviction | `401` | `2001` |
| Expired API key | `401` | `2002` |
| Inactive or pending user (auth dependency) | `401` | `2004` |
| JWT cannot be decoded or has expired | `403` | `2003` |
| Permission denied | `403` | `3000` / `3001` / `3002` / `3003` / `3004` |
| Resource not found | `404` | `4000`–`4005`, the `6000` family, `6200`/`6210`/`6211` |
| Model quota exceeded | `429` | `6103` |
| Internal server error | `500` | `1003` |
| Generic `HTTPException` | its status | `1000` / `2000` / `3000` / `4000` |

<Callout type="warn">
  Only `6103` (model quota) reliably returns HTTP `429`. `5400` (email quota) and `5312` (TOTP attempt throttling) both return HTTP `400`. Never infer rate limiting from the HTTP status; read `code`.
</Callout>

## Business Code Reference

The tables below cover every error code defined by the current version. Unused numbers inside a range are reserved — do not implement branches for them.

The HTTP column lists the status the backend actually raises today. `400` means no explicit status was set, which is the `BusinessError` default. A few codes use different statuses on different endpoints (`1004`, `3001`, the `6000` family, `6100`); the table shows the most common value and the response is authoritative.

<Callout type="info">
  Codes marked “reserved” are defined in the enum but have no raise site anywhere in the backend. Do not build integrations that depend on seeing them.
</Callout>

### General errors (1000-1999)

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `1000` | `UNKNOWN_ERROR` | Unclassified error | `400` (`500` on the LLM processing path) |
| `1001` | `VALIDATION_ERROR` | Request validation failed | `422` (Pydantic); `400` when raised manually |
| `1002` | `BAD_REQUEST` | Invalid request format or parameters | `400` (`409` for a few conflict cases) |
| `1003` | `INTERNAL_ERROR` | Internal server error | `500` |
| `1004` | `FORBIDDEN` | Generic forbidden operation | `403` |

For `1001`, `data.errors` is a **dictionary of field name to message array**, not an array:

```json
{
  "code": 1001,
  "data": {
    "errors": {
      "email": ["Invalid email address"],
      "password": ["String should have at least 8 characters"]
    }
  },
  "msg": "Validation error"
}
```

### Authentication errors (2000-2999)

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `2000` | `UNAUTHORIZED` | No credentials provided | `401` |
| `2001` | `INVALID_TOKEN` | JWT revoked/expired, or the API key is invalid or inactive | `401` |
| `2002` | `TOKEN_EXPIRED` | API key has expired (expired JWTs report `2003`) | `401` |
| `2003` | `INVALID_CREDENTIALS` | Wrong username/password, or the JWT cannot be decoded / has expired | `403` (JWT); `400` (wrong password) |
| `2004` | `INACTIVE_USER` | User is deactivated or pending approval | `401` |

`2001` also covers the superseded token in single-session mode (`msg_key` is `session_expired_new_login`) and blacklisted tokens.

### Permission errors (3000-3999)

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `3000` | `PERMISSION_DENIED` | No access to this resource or operation | `403` |
| `3001` | `INSUFFICIENT_PRIVILEGES` | Superuser privileges required | `403` |
| `3002` | `NOT_TEAM_MEMBER` | Not a member of the target team | `403` (`404` for `POST /teams/{team_id}/leave`) |
| `3003` | `TEAM_ADMIN_REQUIRED` | Team owner or admin role required | `403` |
| `3004` | `TEAM_OWNER_REQUIRED` | Team owner role required | `403` |

`3000` is also what an API key receives when its resource binding does not match (`msg_key` is `api_key_no_agent_access` / `api_key_no_workflow_access`); see the [API Keys API](./api-keys).

### Registration and accounts (5000-5099)

| Code | Constant | Meaning |
| --- | --- | --- |
| `5000` | `REGISTRATION_DISABLED` | Open registration is disabled |
| `5001` | `ALREADY_EXISTS` | Resource already exists (generic) |
| `5002` | `USERNAME_EXISTS` | Username already exists |
| `5003` | `EMAIL_EXISTS` | Email already exists |
| `5004` | `EMAIL_NOT_VERIFIED` | Email must be verified before signing in |
| `5005` | `VERIFICATION_CODE_INVALID` | Verification code or reset token is invalid |
| `5006` | `VERIFICATION_CODE_EXPIRED` | Verification code or email token has expired |

| `5008` | `EMAIL_SEND_TOO_FREQUENT` | Emails requested too often (60-second cooldown) |

This range always returns HTTP `400`. `5007` may carry `data` and `5008` carries `data.remaining_seconds` for a precise message.

### Duplicate conflicts (5100-5199)

| Code | Constant | Meaning |
| --- | --- | --- |
| `5100` | `ROLE_NAME_EXISTS` | Role name already exists |
| `5101` | `PERMISSION_CODE_EXISTS` | Permission code already exists |
| `5102` | `TEAM_NAME_EXISTS` | Team name already exists |
| `5103` | `ALREADY_TEAM_MEMBER` | User is already a team member |
| `5104` | `DUPLICATE_NAME` | Duplicate name (generic) |

This range always returns HTTP `400`. Retrying cannot succeed — rename the resource or switch to the update endpoint.

### Login security (5300-5399)

| Code | Constant | Meaning |
| --- | --- | --- |
| `5300` | `ACCOUNT_LOCKED` | Account locked after repeated login failures (5 attempts, 15 minutes by default) |
| `5301` | `TOO_MANY_LOGIN_ATTEMPTS` | Too many login attempts (reserved) |
| `5302` | `CAPTCHA_REQUIRED` | Human verification is required |
| `5303` | `CAPTCHA_INVALID` | Human verification failed or the proof expired |
| `5304` | `PASSWORD_EXPIRED` | Password has expired (reserved) |
| `5305` | `FORCE_PASSWORD_CHANGE_REQUIRED` | Password change is required (reserved) |
| `5306` | `PASSWORD_MIN_AGE_NOT_MET` | Minimum password age not reached; cannot change yet |
| `5307` | `PASSWORD_RECENTLY_USED` | New password matches a recent password (reserved) |
| `5310` | `TOTP_REQUIRED` | Two-factor authentication required (reserved) |
| `5311` | `TOTP_INVALID` | TOTP code or backup code is incorrect |
| `5312` | `TOTP_RATE_LIMITED` | Too many failed TOTP attempts, temporarily throttled (HTTP `400`) |
| `5313` | `TOTP_NOT_ENABLED` | Two-factor authentication is not enabled for this account |
| `5314` | `TOTP_ALREADY_ENABLED` | Two-factor authentication is already enabled |
| `5315` | `TOTP_SETUP_EXPIRED` | The TOTP enrollment session expired |

<Callout type="info">
  An expired password or an admin-forced password change is **not** an error: login still returns `code: 0` with `force_password_change: true` and a `reason` in `data`. A deployment-wide TOTP requirement returns `requires_totp_setup: true`. See the [Authentication & Login API](./auth).
</Callout>

### Rate limiting (5400-5499)

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `5400` | `RATE_LIMITED` | Email quota exhausted or a provider rate limit mapped to this code | `400` |

`5400` carries the dimension that was exceeded, for example `{"limit": 100, "period": "hour"}` for bulk email or `{"requested": 3, "remaining": 1}`.

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `6000` | `KB_NOT_FOUND` | Knowledge base not found | `404` |
| `6001` | `KB_NAME_EXISTS` | Knowledge base name already exists | `400` |
| `6002` | `DOCUMENT_NOT_FOUND` | Document not found | `404` |
| `6003` | `INVALID_DOCUMENT_TYPE` | Document type is not supported | `400` |
| `6004` | `DOCUMENT_PROCESSING_FAILED` | Document processing failed (reserved) | — |

`6007` mirrors `6201` for Agents: the resource exists but the current user or API key is outside its access scope. Surface a permission request instead of retrying.

### Models (6100-6199)

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `6100` | `MODEL_NOT_FOUND` | Model not found | `404` |
| `6101` | `TEAM_MODEL_NOT_FOUND` | Team model authorization not found | `404` |
| `6102` | `TEAM_MODEL_EXISTS` | The model is already authorized for this team | `400` |
| `6103` | `MODEL_QUOTA_EXCEEDED` | Team model quota (tokens or requests) exceeded | `429` |
| `6104` | `MODEL_NOT_AUTHORIZED` | The team is not authorized for this model | `400` |
| `6105` | `MODEL_VISION_NOT_SUPPORTED` | The model does not support vision input (reserved) | — |
| `6106` | `MODEL_DISABLED` | The model, or the team authorization, is disabled | `400` |

`6103` is the only code that reliably returns HTTP `429`. `6104` and `6106` both mean “unavailable right now”, but `6104` requires adding a team model authorization while `6106` only requires re-enabling `is_enabled` on an existing one.

### Agents and conversations (6200-6299)

| Code | Constant | Meaning | HTTP |
| --- | --- | --- | --- |
| `6200` | `AGENT_NOT_FOUND` | Agent not found | `404` |
| `6201` | `AGENT_ACCESS_DENIED` | No access to this Agent | `403` |
| `6202` | `AGENT_NOT_PUBLISHED` | Agent is not published (reserved) | — |
| `6210` | `CONVERSATION_NOT_FOUND` | Conversation not found or not owned by the caller | `404` |
| `6211` | `MESSAGE_NOT_FOUND` | Message not found | `404` |

<Callout type="warn">
  The backend does not check Agent publish status, so `6202` is reserved and never raised. Do not branch on it: unauthorized access returns `6201`/`3000`, and an unusable model returns `6104`/`6106`.
</Callout>

| Code | Constant | Meaning |
| --- | --- | --- |
| `6300` | `SSO_PROVIDER_NOT_FOUND` | SSO provider is missing or disabled |
| `6301` | `SSO_SESSION_EXPIRED` | SSO login session expired (reserved) |
| `6302` | `SSO_REGISTRATION_DISABLED` | SSO auto-registration is disabled |
| `6303` | `SSO_AUTHENTICATION_FAILED` | SSO authentication failed (reserved) |

## Handling Table

| HTTP / business scope | How to handle |
| --- | --- |
| `401`, `2000`-`2002`, `2004` | Log in again, refresh the JWT, or replace the expired/invalid/inactive API key; `2004` needs an administrator to restore the account |
| `403`, `3000`-`3004` | Check roles, team membership, owner/admin requirements, and the API key's Agent/Workflow bindings |
| `404`, `4000`-`4005`, `6000`/`6002`/`6005`/`6200`/`6210`/`6211` | Confirm the resource ID, owning team, and current team context |
| `400`, `1001`-`1004` | Fix the JSON, required fields, types, or business validation; for `1001` read `data.errors` field by field |
| `5000`-`5008` | Walk the user through registration, account creation, or email verification |
| `5100`-`5214` | Do not auto-retry: rename, change the flow, or switch to an update/transfer endpoint |
| `5300`-`5316` | Follow the lockout, captcha, password policy, or TOTP prompt |
| `5400` | Back off and retry; for bulk email, reduce the recipient count |
| `6000`-`6007` | Check knowledge base permissions, document type, processing status, and chunk IDs |
| `6100`-`6106` | Check team model authorization, quota usage, and enabled state |
| `6103` (HTTP `429`) | Back off, lower concurrency, or wait for the quota window to reset |
| `6200`/`6201` | Confirm the Agent ID and access scope (team visibility or API key binding) |
| `6300`-`6306` | Check the SSO provider configuration, callback, auto-registration switch, and whether password login is disabled |

## Retryable and Non-Retryable

Network timeouts, `503`/`504`, temporarily unavailable providers, `5400` and `6103` throttling, and some background task failures can be retried with exponential backoff.

Do not blindly retry:

- `1001`-`1004` — the request itself is invalid; a retry returns the same result.
- `3000`-`3004`, `6007`, `6201` — permission problems; fix the authorization first.
- `2001`, `2002`, `2004` — credential or account state problems.
- `4000`-`4005` — the resource does not exist; verify the ID and context.
- `5100`-`5214` — constraint conflicts; the request must change.
- `6104`, `6106` — model authorization or enabled state.
- `6306` — this deployment has disabled password login.

<Callout type="success">
  Idempotent reads are always safe to retry. Before retrying a `POST` (sending a message, running a workflow, creating a resource), query the current state first to avoid duplicate writes or duplicated external side effects.
</Callout>

## SSE Error Handling

Streaming endpoints cannot change the HTTP status once the response headers are sent, so mid-stream failures arrive as error events inside the stream:

- After an Agent stream `error` event, keep the text received so far and the `message_id`, then decide whether to retry or surface it. The message may already be persisted, so check conversation messages before retrying to avoid duplicate questions.
- After a workflow stream disconnects, resume with `stream_url` and the last received event sequence number instead of calling `POST /workflows/{workflow_id}/run` again.

The full event list for both streams is in [Streaming Events](./streaming).
